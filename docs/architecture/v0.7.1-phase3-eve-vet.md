### E4 — BE-25-iit-phi error prose regressed from "must be a finite probability in [0, 1]" to "must be a finite in range [0, 1] number" — MEDIUM

**Files:** `src/bridges/equations/be-25-iit-phi.ts:255-256`, helper `_be-helpers.ts:75-95` (`describeRange`).

Pre-extraction (from `git show 288a45c:src/bridges/equations/be-25-iit-phi.ts`):
```
evaluateIntrinsicInformation: p_cond must be a finite probability in [0, 1], got -0.1
```

Post-extraction (from the current `describeRange` for `{ min: 0, max: 1, allowZero: true }`):
```
evaluateIntrinsicInformation: p_cond must be a finite in range [0, 1] number, got -0.1
```

Two regressions:
1. **Lost domain-specific noun** "probability" — IIT validation message no longer signals the variable's *meaning*, only its *range*. This is a small caller-facing UX regression.
2. **Awkward English**: "must be a finite in range [0, 1] number" is grammatically clumsy ("a finite … number" with a parenthetical between).

The migration is test-class-preserving (`be-25-iit-encoding.test.ts:188-227` asserts only `toThrow(RangeError)`), but this is exactly the silent-prose-drift the v0.6.1 "behavior preservation" goal flags. None of the helper's existing test cases pin "probability"-class noun-substitution.

The migration commit (`da98b98`) flagged BE-25-iit-phi's *cross-field KL-divergence* check as the inline-preserved bespoke prose, but missed the simpler in-range prose loss.

**Mitigation:** Either (a) extend `FieldSpec` with an optional `noun?: string` ("probability") to splice into describeRange's output, or (b) revert the `p_cond/p_marg` migration to inline (single callsite, low value-from-helper, lossy at the message layer).

### E5 — `FieldSpec.excludeMax` is dead code (helper-design surface fabrication) — LOW

**File:** `src/bridges/equations/_be-helpers.ts:61`

Helper exposes `excludeMax?: boolean` but `grep -rn "excludeMax" src/bridges/equations/` returns ZERO callsites. Only the helper unit test (`_be-helpers.test.ts:191-198`) exercises it. By the v0.6.1 export-audit precedent ("drop unused exports"), `excludeMax` should be removed until a real BE callsite needs it.

Related, less severe: `FieldSpec.allowZero` (helper line 63) has only two callsites (`be-25-iit-phi.ts:255-256`) where it's **logically a no-op**: when `max:` is set (as it is for both callsites), the describeRange branch that consults `allowZero` (line 83, gated on `!hasMax`) is never entered, AND the actual validation logic (lines 136-154) never reads `allowZero`. So `allowZero: true` is **purely decorative** at both callsites — it changes neither validation nor error text. Misleading API: the field appears to be controlling something but isn't.

**Mitigation:** drop `excludeMax` from `FieldSpec`; either drop `allowZero` (currently no-op) or actually wire it into the validation predicate (so `min: 0, allowZero: false` would reject zero — currently it doesn't).

### E6 — `_equationLabel` is a load-bearing-by-convention-only parameter (speculative API surface) — LOW

**File:** `src/bridges/equations/_be-helpers.ts:181-194`

`validateBEDimensions(lhs, rhs, _equationLabel)` accepts `equationLabel` but the underscore-prefix signals "unused". All 30+ callsites pass real labels (`'BE11'`, `'BE21'`, …). The helper JSDoc explicitly defers ("reserved for future error-context enrichment"). The unit test at `_be-helpers.test.ts:278-285` pins that the label has zero observable effect.

This isn't a bug, but per the design hygiene the v0.7.1 sprint is built around (the M-1/M-3 unused-exports purge), an accepted-but-unused parameter that every callsite is forced to populate is the wrong direction. Two options reduce the speculative surface:
- Drop the parameter entirely (callsites still build via the label-elision overload),
- OR actually inline the label into the error path (the report-shape already has no label slot, but a thrown error could).

The decision was visible to the design (Decision #3 cites it), so flagging as LOW not MEDIUM. Just don't let it survive to v0.7.2 without a concrete consumer.
