### PC-3 — `scanForMetricPair` does not walk v0.5.0 curvature-layer node kinds (MEDIUM)

**File**: `src/numerical/metric-inverse.ts:73-83`

**Finding**: `scanForMetricPair` walks `op`, `tensor-product`, `integral`, `derivative`, and `tensor-partial-derivative`. It does NOT walk `covariant-derivative`, `riemann-tensor`, `ricci-tensor`, `einstein-tensor`, or `bianchi-residual` (all v0.4.0 + v0.5.0 additions). Exact code:

```
const walk = (n: ExprNode): void => {
  if (n.kind === 'metric-tensor') metrics.push(n);
  else if (n.kind === 'op') n.args.forEach(walk);
  else if (n.kind === 'tensor-product') n.args.forEach(walk);
  else if (n.kind === 'integral') { walk(n.over); walk(n.integrand); }
  else if (n.kind === 'derivative') { walk(n.of); walk(n.wrt); }
  else if (n.kind === 'tensor-partial-derivative') {
    walk(n.of as ExprNode); walk(n.wrt as ExprNode);
  }
  // tensor-symbol / kronecker-delta / symbol: leaves, no metric inside
};
```

Effect: any AST whose only `metric-tensor` references live inside a `CovariantDerivativeNode.gLower/gInverse`, `RiemannTensorNode.gLower/gInverse`, or `EinsteinTensorNode.gLower/gInverse` will silently NOT trigger the `InverseMetricInconsistencyWarning` from `evaluateNumerical`. Users get no warning if they pass an inconsistent g/g⁻¹ pair through the entire v0.5.0 GR pipeline.

**Severity**: MEDIUM — silent degradation of an existing diagnostic, not wrong results per se (the lowering still uses whatever the user supplied), but a real correctness-warning gap.

**Fix**: Extend the walk to: `case 'covariant-derivative'`: walk `n.of as ExprNode`, `walk(n.gLower)`, `walk(n.gInverse)`. `case 'riemann-tensor'`: walk `n.gLower`, `n.gInverse`. `case 'ricci-tensor'`, `case 'bianchi-residual'`: walk `n.riemann` (recursive). `case 'einstein-tensor'`: walk `n.riemann`, `n.gLower`, `n.gInverse`.

**Verified**: Yes — grep `kind:\s*'(riemann|ricci|einstein|bianchi|covariant)` confirms all 5 kinds exist as ExprNode kinds in `src/dimensional/` per `src/dimensional/connection-validators.ts:44,168` and `src/dimensional/curvature.ts:47,182,322`. None are mentioned in `scanForMetricPair`.

### PD-2 — `schwarzschildRiemannFn` fixture is pragmatic-minimum (8/256 entries) (MEDIUM)

**File**: `tests/fixtures/schwarzschild.ts:292-324`

**Finding**: The fixture only populates two component pairs:
- `R[0][1][0][1] = Rt_rtr = r_s / (r² (r − r_s))` and its antisymmetric partner `R[0][1][1][0] = −Rt_rtr` (line 313-315).
- `R[2][3][2][3] = Rth_pthp = (r_s/r) sin²θ` and `R[2][3][3][2] = −Rth_pthp` (line 318-320).

That's 4 explicit `R[...]` assignments → 8 entries in the 4×4×4×4 = 256-component tensor (counting the antisymmetric `μ↔ν` doubles). Carroll Ch. 3 / Hartle Ch. 9 list the Schwarzschild independent non-zero components as: `R^t_{rtr}`, `R^t_{θtθ}`, `R^t_{φtφ}`, `R^r_{trt}`, `R^r_{θrθ}`, `R^r_{φrφ}`, `R^θ_{tθt}`, `R^θ_{rθr}`, `R^θ_{φθφ}`, `R^φ_{tφt}`, `R^φ_{rφr}`, `R^φ_{θφθ}` — 12 distinct slot configurations, each with antisymmetric partner → 24+ non-zero entries; with first-pair symmetry of the all-lower form, the lowering pipeline (`src/numerical/curvature-lowering-helpers.ts`) produces 16+ legitimate non-zero `R^ρ_{σμν}` components at any off-axis point.

The fixture's own JSDoc (lines 285-290) honestly admits this: *"This fixture populates ONLY the components required to support [the M7 pin]. Every other entry is zero."* So the fixture is correct for what it pins but cannot be the analytic reference for the full lowering output.

**Severity**: MEDIUM — pinning test passes; future component-by-component cross-checks against the full lowering would fail not because lowering is wrong but because the fixture is incomplete.

**Fix**: Backfill at least the 12 independent Carroll components. Suggested target: introduce `schwarzschildRiemannFullFn(M_kg)` that returns the analytic closed form for all 24+ non-zero `R^ρ_{σμν}` entries with full antisymmetric-partner expansion. Keep `schwarzschildRiemannFn` as the "pin only" closure for backward compat.

**Verified**: Yes (line count + JSDoc quoted).

### PD-7 — 4th-order FD only in `curvature-lowering-helpers.ts`; `pderiv.ts` still uses 2nd-order (HIGH)

**Files**:
- `src/numerical/pderiv.ts:44-49` (centered FD via `(flat[f+step] − flat[f−step]) / (2 * h)` — classic 2nd-order O(h²))

**Finding**: The 4th-order centered stencil was a Task 6 fix isolated to `curvature-lowering-helpers.ts` (the ∂Γ → R pipeline). Every OTHER FD call site (covariant-derivative lowering, BE-37 eikonal, geodesic Christoffel derivatives) still goes through `pderivNumericalFn` at 2nd-order. Any future bridge that differentiates a `c²·g_tt`-scale quantity at 2nd-order will hit the same ~3e-6 relative error floor that Task 6 had to work around.

Latent risk sites (functions that call `pderivNumericalFn` on metric-derived fields):
- `src/numerical/connection-lowering-helpers.ts:computeChristoffelTensor` — uses `pderivNumericalFn`-derived `∂g` to build Γ. Cycloid radial-infall test (v0.5.0 Task 3) caught a sign error here but not the precision floor.
- `src/numerical/lowering.ts:tensor-partial-derivative` — public path consumers (BE-37 covariant-eikonal) feed metric derivatives through.

**Severity**: HIGH — known precision floor that v0.5.0 worked around in one place but did not propagate. Future BE-XX additions exercising `g_tt(c²)` differentiation at 2nd-order will silently hit ~3e-6 noise.

**Fix**: Two options. (a) Add a `pderivNumericalFnOrder4` variant alongside `pderivNumericalFn`; document the c²-cancellation rationale; consumers opt in. (b) Make the order a parameter (`order: 2 | 4 = 2`); preserves backwards-compat. Recommend (b) — minimal API churn, opt-in precision.

**Verified**: Yes (2nd-order stencil at `pderiv.ts:45` confirmed; 4th-order at `curvature-lowering-helpers.ts:60-80` confirmed).
