### C1: `flattenNA` / `flattenNestedArray` — thin wrapper in lowering.ts

**Files**: `src/numerical/connection-lowering-helpers.ts:28` (canonical), `src/numerical/lowering.ts:92` (wrapper)

**Current state**: `flattenNestedArray` in `lowering.ts` is a private function that calls `flattenNA` and adds an `expectedSize` check. The Task 12 review comment at line 27 of `connection-lowering-helpers.ts` says "Exported as the single canonical flatten helper — `flattenNestedArray` in lowering.ts was a duplicate and has been removed in favour of this function." — but `flattenNestedArray` still exists as a private wrapper with validation logic on top.

**Assessment**: The wrapper is NOT dead — it adds a meaningful invariant check (`out.length !== expectedSize` throws `NumericalBackendError`). The wrapper is 8 LOC including comment. The comment is slightly misleading ("was a duplicate and has been removed" when it is still present). This is not a consolidation target, but the comment should be updated to: "Delegates to `flattenNA`; adds size-assertion guard."

**Verdict**: NOT a DRY problem — wrapper serves a real purpose. COMMENT FIX only (2 LOC).

**Risk**: PRESERVING.

### C3: AD classes — Float64 vs MathTS isomorphism

**Files**: `src/numerical/float64-engine.ts` (private `EngineDualTensor`, `EngineTape`, `EngineTapedTensor`), `src/numerical/mathts-engine.ts` (wraps `@danielsimonjr/mathts-tensor` public `DualTensor`, `Tape`, `TapedTensor`)

**Current state**: The private AD classes in `float64-engine.ts` are structurally isomorphic to the public types in mathts-tensor. However, `float64-engine.ts` has a hard **zero-dep invariant** — it must run without any optional dependency. Consuming mathts-tensor here would break that invariant. The design doc at `ARCHITECTURE.md:102` explicitly states `MathTSEngine` lives behind an `optionalDependency`.

**Verdict**: NOT a consolidation target for v0.4.5. The algorithmic isomorphism is intentional and documented. Flag for v0.5.0+ when the zero-dep constraint may be revisited.

**Risk**: If attempted: BREAKING (removes zero-dep guarantee).

### C4: Bridge test boilerplate — shared `tests/bridges/_helpers.ts`

**Files**: 40+ `tests/bridges/be-NN-encoding.test.ts` files

**Current state**: Each encoding test contains a repeated 4-part structure:
1. `BRIDGE_EQUATIONS.find((e) => e.id === NN)` catalog lookup
2. `validate(BE_NN_RHS).ok === true` dimensional check
3. `format(validate(BE_NN_RHS).inferredDimension!) === be.dimensional_signature` round-trip pin
4. `evaluateNN({...})` numerical evaluation

The index-entry + dimensional validation sections (parts 1-3) are near-identical across all 40+ test files. Extracting them to a helper like:

```typescript
// tests/bridges/_helpers.ts
export function expectBridgeDimensionalRoundTrip(id: number, rhs: ExprNode, expectedSig: string) { ... }
```

would save roughly 8-12 LOC per test file (~320-480 LOC total across the suite), reduce copy-paste bugs on new bridge additions, and make the test intent clearer.

**Assessment**: The repetition is real and the helper is well-scoped. However, reformulation tests (`be-NN-reformulation.test.ts`) have a significantly different structure (index metadata checks, no AST/evaluate), so they would not benefit from the same helper.

**Proposed change**: Add `tests/bridges/_helpers.ts` with two helpers:
- `expectBridgeInIndex(id, status?)` — asserts existence + optional status pin
- `expectDimRoundTrip(rhs: ExprNode, sig: string)` — asserts `validate(rhs).ok && format(inferredDim) === sig`

**Estimated impact**: ~8 LOC saved per encoding test file × 40 files = ~320 LOC, plus 25 LOC for the helper module. Net: ~295 LOC reduction in test directory.

**Risk**: PRESERVING (test-only change; no src impact). Requires touching 40 test files — moderate churn but mechanical.

**Recommendation**: Include in v0.4.5 Phase 1 as the highest-impact consolidation.

## Category D: Benchmark scaffold proposal

UPT has no `bench/` directory. v0.4.5 Phase 2 should establish the benchmark infrastructure.

- **Tool**: Use Vitest 4.x native `bench()` API (vitest@4.1.4 is already installed and supports `describe.bench` / `bench()`). No new devDependency required. Add `"bench": "vitest bench"` to `package.json` scripts. The bench files live at `bench/*.bench.ts` and are excluded from the normal `vitest run` by adding `include: ['tests/**/*.test.ts']` to `vitest.config.ts` (or equivalent inline config in `package.json`).

- **Workloads to benchmark (priority order)**:
  1. `Float64ReferenceEngine.einsum` — the core contraction kernel. Input: rank-3 × rank-3 Schwarzschild Christoffel symbol (4×4×4) contracted with a velocity 4-vector. Measures the hot path hit by every numerical geodesic step.
  2. `integrateGeodesic` (Schwarzschild radial infall, 1000 steps) — end-to-end RK4 geodesic. Measures the full numerical pipeline including the per-step Christoffel callback. Baseline for v0.5.0 Faraday-cascade regression detection.
  3. `evaluateBE37CovariantEikonalNumerical` (BE-37 Shapiro delay, single evaluation) — measures the AST → lowering → engine roundtrip for the most complex current bridge.
  4. `MathTSEngine.einsum` (same workload as #1) — allows direct engine comparison once the optional dep is present; skip gracefully if `@danielsimonjr/mathts-tensor` is absent.

- **Directory layout**:
  ```
  bench/
    engine-einsum.bench.ts      # workloads 1 + 4
    geodesic-rk4.bench.ts       # workload 2
    be37-eikonal.bench.ts       # workload 3
    _fixtures.ts                # shared bench fixtures (Schwarzschild params, etc.)
  ```

- **npm scripts**: Add `"bench": "vitest bench"` and `"bench:ci": "vitest bench --reporter=json --outputFile=bench/results.json"` to `package.json`. CI script produces a JSON artifact for trend tracking without failing the build on regression (thresholds come in v0.5.0+).

- **No threshold gates in v0.4.5**: Vitest bench reports median / p99 / ops-per-sec to stdout. Threshold-based CI gates (fail on >10% regression) are v0.5.0 scope — v0.4.5 only establishes the infrastructure and records a baseline.
