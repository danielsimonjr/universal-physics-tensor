> options scoped for a future implementation session.

## Status at HEAD

`computeKretschmann` (`src/numerical/kretschmann.ts:62`) works at
`r ≥ 3·r_s` but breaks near `r = r_s` because Schwarzschild
coordinates have a coordinate singularity at the event horizon:
`g_rr = 1/(1 − r_s/r) → ∞`. The Christoffel evaluator `Γ^r_{rr} =
−r_s/(2 r (r − r_s))` diverges, finite-difference Riemann assembly
suffers catastrophic cancellation, and the numerical `K` returned
at `r = 1.0001 r_s` is IEEE-finite but ~10¹⁴ off the reference
value (`K_ref(r_s) ≈ 1.58e-13`).

The limitation is **physically real, not a bug**: the curvature
itself is smooth at the horizon (the true singularity is at `r=0`).
The numerical failure is a coordinate-system artifact.

`tests/numerical/kretschmann-horizon.test.ts:193` pins ONLY that
`K_num` is finite (not accurate). This is the honest test posture
— no over-assertion.

## Two implementation paths

| Coord system | Pros | Cons |
|---|---|---|
| **Painlevé-Gullstrand** `(T, r, θ, φ)` | Diagonal-ish; metric regular at horizon; intuitive "river" picture; reuses (r, θ, φ) angular structure | Off-diagonal `g_{Tr} = √(r_s/r)`; existing fixtures need a translation layer |
| **Kruskal-Szekeres** `(U, V, θ, φ)` | Maximally extended; covers all four spacetime regions; no horizon discontinuity anywhere; canonical for global geometry | Heavy implicit-function transcendental `(U, V) ↔ (t, r)`; existing tests can't be converted directly — new fixtures required |

**Recommendation**: Painlevé-Gullstrand for v0.7.1 or v0.8. The
metric is in textbooks (MTW §31.4; Carroll §5.7); the coordinate
transformation `T = t + 2√(r r_s) + r_s ln|(√r − √r_s)/(√r + √r_s)|`
is a closed-form rewrite (no implicit-function solve). Kruskal-
Szekeres remains the longer-term path for maximally-extended
geometry work; defer to whenever the framework needs to evaluate
inside the horizon.
