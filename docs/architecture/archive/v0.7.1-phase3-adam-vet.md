### `validateFiniteInputs` semantic drift (S-1) — 2 LOW findings

#### LOW #1 — BE-48 GRW default-injection `?? DEFAULT` vs `= DEFAULT`

**File:** `src/bridges/equations/be-48-grw-localization.ts:110-114`

Pre-migration used parameter-destructure defaults
(`{ m_0_kg = DEFAULT_M_0_KG } = input`), which fall back to the default
**only when the value is `undefined`**. Post-migration uses nullish
coalescing (`input.m_0_kg ?? DEFAULT_M_0_KG`), which falls back **when
the value is `null` or `undefined`**.

```ts
const resolved = {
  m_kg: input.m_kg,
  m_0_kg: input.m_0_kg ?? DEFAULT_M_0_KG,           // ← drift
  lambda_0_per_s: input.lambda_0_per_s ?? DEFAULT_LAMBDA,  // ← drift
};
```

**Impact:** TypeScript callers using the `?: number` interface cannot
pass `null`, so this is invisible at the type-level. A JS caller
passing `{ m_kg: 1, m_0_kg: null }` would previously have thrown
`RangeError: m_0_kg must be a finite positive number, got null`; now
the default is silently substituted and the call proceeds. Behavior
preservation is technically violated for ill-typed JS callers only.

**Recommendation:** non-blocking; either accept the drift (the new
behavior is more forgiving and matches `??`-idiomatic TS) or revert to
the destructure-default form (`const { m_kg, m_0_kg = DEFAULT_M_0_KG,
lambda_0_per_s = DEFAULT_LAMBDA } = input; validateFiniteInputs({ m_kg,
m_0_kg, lambda_0_per_s }, [...], 'evaluateGRWLocalization');`).

#### LOW #2 — Error-message prose drift across all migrated modules

**Files:** every BE-NN migrated (43 modules)

The helper format `"<eval>: <field> must be a finite <range>number,
got <v>"` differs slightly from the pre-migration per-evaluator prose
in word order and the unbounded case:

| Pre-migration phrasing                                  | Post-migration helper phrasing                  |
|---------------------------------------------------------|--------------------------------------------------|
| `"… must be finite, got …"`                             | `"… must be a finite number, got …"`             |
| `"… must be a positive finite number, got …"` (BE-53)   | `"… must be a finite positive number, got …"`    |
| `"… must be a non-negative finite number, got …"` (BE-53) | `"… must be a finite non-negative number, got …"` |
| `"… must be finite and non-negative, got …"` (BE-20)    | `"… must be a finite non-negative number, got …"`|
| `"… must be a finite probability in [0, 1], got …"` (BE-25 IIT-Phi) | `"… must be a finite in range [0, 1] number, got …"`|

**Impact:** the bridges tests check only `RangeError` class (no message
regex) — verified by `grep -rEn "toThrow" tests/bridges/`. No test
breakage. The drift is visible to end-users only.

**Recommendation:** non-blocking. The BE-25 IIT-Phi case
(`"finite in range [0, 1] number"`) reads slightly ungrammatical
("a finite in range" is awkward); if you care about prose polish,
consider tightening `describeRange()` at `_be-helpers.ts:75-95` to
emit `"in [0, 1]"` without the leading "finite". Cosmetic only.

### `rg-flow` Task 3.3 migration — NONE (cosmetic prose drift only)

**File:** `src/dimensional/rg-flow.ts:103-111, 231-239`

(case-insensitive regex) — both old and new pass.

**Recommendation:** non-blocking. If prose polish matters, tweak the
explanation strings to read as standalone sentences (drop "must be")
or have the helper omit "must be ${expected}" when an explanation is
supplied.
