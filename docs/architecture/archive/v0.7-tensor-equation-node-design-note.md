# `TensorEquationNode<LHS, RHS>` Generalization — Design Note

> Carry-forward from v0.6.0 "Deferred" (item E-6). Surfaces the
> design space for generalizing `EinsteinFieldEquationNode` into
> a parametric `TensorEquationNode<LHS, RHS>` that future field-
> equation predicates (Maxwell, Yang-Mills, etc.) can reuse.

**Date:** 2026-05-23.
**HEAD reference:** `src/dimensional/einstein-equation.ts:52-59`
(the concrete shape) + `src/dimensional/stress-energy-validators.ts`
(the related rank-2 validators).
**Status:** Design-only. No code, no tests, no breaking changes.

---

## 1. What exists today (the concrete pattern)

`EinsteinFieldEquationNode` (v0.6.0 Phase 2 Task 2.3):

```ts
interface EinsteinFieldEquationNode {
  readonly kind: 'einstein-equation';
  readonly lhs: EinsteinTensorNode;          // G_μν
  readonly cosmological: CosmologicalConstantNode | null;
  readonly metric: MetricTensorNode;          // for Λ g_μν
  readonly rhs: StressEnergyTensorNode;       // T_μν
  readonly coupling: 'einstein';              // tag for 8πG/c⁴
}
```

`validateEinsteinFieldEquation(node)` enforces three structural
invariants (per v0.6.0 Decision #3):
1. Free-index agreement (G_μν and T_μν same labels + variance)
2. Per-component dimensional equality (all terms reduce to [L⁻²])
3. Symmetry agreement (both sides symmetric in (μ,ν))

## 2. The generalization candidates

What other field-equation predicates would benefit from the same
node-+-validator pattern?

| Equation | Form | LHS shape | RHS shape | Coupling |
|---|---|---|---|---|
| Maxwell (sourced) | `∇_μ F^{μν} = μ₀ J^ν` | divergence-of-rank-2 | rank-1 current | `μ₀` |
| Maxwell (Bianchi) | `∂_[α F_{μν]} = 0` | antisymmetrized derivative | 0 | none |
| Yang-Mills | `D_μ F^{aμν} = J^{aν}` | gauge-covariant divergence | rank-1 charged current | `g_{coupling}` |
| Klein-Gordon (free) | `(□ + m²) φ = 0` | wave-operator scalar | 0 | `m²` |
| Klein-Gordon (sourced) | `(□ + m²) φ = J` | wave-operator scalar | rank-0 source | `m²` |
| Dirac | `(i γ^μ ∂_μ − m) ψ = 0` | matrix-valued operator | 0 | `m` (mass) |
| Continuity | `∂_μ J^μ = 0` | divergence | 0 | none |
| Einstein-Cartan | `G_μν + Λ g_μν − Q_{μν} = κ T_μν` | rank-2 + torsion | rank-2 | `κ = 8πG/c⁴` |

**Common structure**: predicate equating two tensor expressions
of the same rank + free-index pattern + dimensional shape, with
optional coupling-constant tags and optional additive corrections.

## 3. Three implementation paths

### (a) Parametric generic `TensorEquationNode<LHS, RHS>`

```ts
interface TensorEquationNode<LHS, RHS> {
  readonly kind: 'tensor-equation';
  readonly equationClass: string;  // 'maxwell-sourced', 'einstein-field', etc.
  readonly lhs: LHS;
  readonly rhs: RHS;
  readonly additiveTerms?: ReadonlyArray<unknown>;  // optional Λg, torsion, etc.
  readonly coupling?: string;  // tag like 'einstein', 'maxwell', 'yang-mills'
}
```

**Pros**: extreme reuse; one validator handles all cases via the
LHS/RHS generic params.
**Cons**: lose ALL static type-narrowing — every consumer has to
re-cast LHS/RHS to their concrete kinds. The `additiveTerms`
unknown-array is a code smell. Validator becomes a giant
dispatch on `equationClass`. **Anti-pattern per v0.5.0 ricci-slot
trap lesson.**

**Verdict: REJECT.** Too generic; loses the discriminated-union
guarantees v0.6.1 explicitly invested in (validator-registry).

### (b) Discriminated-union expansion (one node kind per equation class)

```ts
type FieldEquationNode =
  | EinsteinFieldEquationNode      // existing
  | MaxwellEquationNode            // new
  | KleinGordonEquationNode        // new
  | YangMillsEquationNode          // new
  | ...
```

Each new node carries its specific LHS/RHS kinds, validates via
its own `validate*` function, dispatches through the v0.6.1
validator-registry pattern.

**Pros**: type-safe per-equation narrowing; mirrors the
curvature-composite + validator-registry patterns already shipped.
Predictable per-equation cost: ~80-120 LOC per new node (mirrors
`EinsteinFieldEquationNode` size).
**Cons**: code duplication on the 3 structural invariants
(free-index agreement, per-component dim equality, symmetry
agreement). Each new equation re-implements them.

**Verdict: PROCEED-WITH-EXTRACTION.** This is the v0.6.1 pattern
applied; the duplication smell should be mitigated by extracting
the 3 invariant checks as reusable helpers.

### (c) Helper-extraction-first refactor

Before adding any new equation node:
1. Extract from `validateEinsteinFieldEquation` three helpers:
   - `validateFreeIndexAgreement(lhsIndices, rhsIndices)`
   - `validatePerComponentDimEquality(termDims: Dimension[])`
   - `validateSymmetryAgreement(lhs, rhs)`
2. Make the helpers operate on `LHS | RHS = { freeIndices,
   dim, symmetry }` shape — i.e., the COMMON contract any
   field-equation LHS/RHS must satisfy.
3. Then layer (b) — new nodes get the helpers for free.

**Pros**: prevents future divergence; first new equation
(MaxwellEquationNode?) becomes ~30-40 LOC instead of 80-120.
**Cons**: refactor + tests for the existing
`validateEinsteinFieldEquation` BEFORE any payoff from the new
equations. Standard "investment cost upfront" trade-off.

**Verdict: RECOMMENDED PATH.** Costs ~1 hour upfront; saves
multiples on each new field equation. Same shape as v0.6.1's
validator-registry investment (cost upfront, saved 11 arms of
silent-miscompute risk).

## 4. What to ship if/when this lands

**Phase 0 — Extraction (no new equations)**:
- New file `src/dimensional/field-equation-helpers.ts` exporting
  the 3 invariant-checker functions.
- Refactor `validateEinsteinFieldEquation` to delegate to them.
- Suite passes unchanged (the extraction must be behavior-preserving).
- ~80 LOC new, ~30 LOC removed from einstein-equation.ts.

**Phase 1+ — Per new equation**:
- New file `src/dimensional/maxwell-equation.ts` (or whichever
  first new node). Each ~30-40 LOC.
- New test file `tests/dimensional/maxwell-equation.test.ts`.
- Wire through the validator-registry's discriminated-union
  dispatch (same shape as the 11 curvature arms).

Sequencing dependency: **none.** Phase 0 lands standalone; new
equations land independently when their use cases arrive.

## 7. Not in scope here

- No `kind: 'tensor-equation'` parametric generic (path (a) explicitly rejected).
- No speculative new equation nodes (Maxwell etc.) — those land per-equation when use cases arrive.
- No changes to runtime behavior of the existing Einstein equation node.

## 8. Honest scope note

The v0.6.0 deferred entry simply said "deferred; the EFE-specific
node is sufficient for v0.6.0 use cases." That assessment remains
correct at v0.7 — no new field equation has been requested. This
note exists to document **WHAT the generalization would look like
if/when needed**, not to justify shipping it preemptively.

If the next sprint needs a Maxwell or Klein-Gordon node, the path
is: ship Phase 0 (extraction) first, then add the new node. The
"copy-paste from einstein-equation.ts" shortcut is the temptation
the v0.6.1 validator-registry pattern was built to prevent.
