## A-1 (HIGH) — Task 0.2 callsite regex MISSES variable-indexed callsites

**Design section:** Phase 0 Task 0.2 — "O-1 callsite re-grep".

The design's prescribed re-grep is:

```
grep -rnE "(gInv|dgInv|dg)[A-Za-z]*\s*\[[0-9]+\]\[" src/ tests/ bench/
```

That regex only matches LITERAL-INTEGER index forms (`gInv[0][1]`, `dg[1][2][3]`). It does NOT match VARIABLE-index forms (`gInv[mu][nu]`, `dg[lambda][mu][nu]`).

At HEAD the literal-index hits are 76, but **variable-index hits add another 33** (e.g., `src/numerical/gl4-integrator.ts:227` `dxStage += gInvAtXj[mu][nu] * P[j][nu]`; `:236` `dpStage += dgInvAtXj[mu][nu][rho] * ...`; `:303`, `:341`; plus `src/numerical/weyl-lowering.ts:79`, `src/numerical/perihelion-finder.ts:88,417`, `src/numerical/killing.ts:212`, and ~26 test-side occurrences). **Combined ~109 raw matches across 20 unique files**, not the design's "~20 callsites." The 5–6 callsites inside the HOT PATH (`solveGL4Stage`, `updateFromStages`, `updateMomentumFromStages`) are exactly the ones that MUST migrate for the bench-gate to fire — they're the read sites — and the design's regex misses every one of them.

**Severity rationale:** HIGH because the regex is explicitly named as the Phase 0 baseline gate; a fork-point worktree agent will run it verbatim, get "76 hits — matches the design's 'about 20 callsites'-magnitude estimate," conclude scope is right-sized, and proceed. The hot-path variable-index callsites then surface as compile errors mid-Phase 1 (tsc failure on `Float64Array[mu][nu]`), forcing the agent to widen scope mid-sprint — exactly the failure mode the design says it's mitigating.

**Recommendation:** Replace the Task 0.2 regex with the union form:

```
grep -rnE "(gInv|dgInv|dg)[A-Za-z]*\s*\[([0-9]+|[a-z]+)\]" src/ tests/ bench/
```

and explicitly enumerate the hot-path files (`gl4-integrator.ts`, `weyl-lowering.ts`, `perihelion-finder.ts`, `killing.ts`, `null-ic.ts`, `be37-covariant-eikonal.ts`) in the design's Phase 1 Task 1.3 scope — the design currently lists only three of these (`einstein-equation.ts`, `kretschmann.ts`, `perihelion-finder.ts`).

## A-3 (HIGH) — Decision #3's "runtime adapts via flattenNA" claim glosses the typed-input contract

**Design section:** Decision #3.

`flattenNA` (`src/numerical/connection-lowering-helpers.ts:31`) is:

```ts
export function flattenNA(data: NestedArray): number[] {
  if (typeof data === 'number') return [data];
  const out: number[] = [];
  const walk = (n: NestedArray): void => {
    if (typeof n === 'number') out.push(n);
    else for (const c of n) walk(c);
  };
  walk(data);
  return out;
}
```

The runtime IS Float64Array-safe at the leaf level (`for (const c of float64Arr)` yields numbers; the `typeof === 'number'` branch fires). BUT the type `NestedArray = number | NestedArray[]` (`src/numerical/types.ts:11`) **explicitly excludes typed arrays**. Passing a `Float64Array` to `flattenNA` is a TS error at every callsite (`curvature-lowering-helpers.ts:147,148,156` etc.). The design needs to widen `NestedArray` to `number | NestedArray[] | Float64Array` or introduce `FlatOrNested = NestedArray | Float64Array` and retype `flattenNA`. The design says neither — it treats the runtime safety as if it implies type-level safety.

Also: the hot-path direct-index callsites in `gl4-integrator.ts:227,236,303,341` and `updateMomentumFromStages` consume the metric closures **without** going through `flattenNA`. They directly do `gInv[mu][nu]` — which on a `Float64Array(16)` is `flat[mu]` (the wrong value; should be `flat[mu*4+nu]`). These five callsites must be rewritten, not "auto-adapted." Decision #3 should call this out.

**Severity rationale:** HIGH because the "runtime adapts" framing is the design's central argument for why the migration is a TYPE-LEVEL change with minimal call-site churn. It's wrong on two counts: (a) the `NestedArray` type doesn't admit Float64Array; (b) the hottest-path consumers bypass `flattenNA` entirely.

**Recommendation:** Rewrite Decision #3 to distinguish three categories of consumer:
1. **`flattenNA`-mediated** (curvature-lowering FD pipeline): runtime works post type-widening; type alias must be union-widened.
2. **Direct-indexed in src/** (`gl4-integrator.ts`, `weyl-lowering.ts`, `perihelion-finder.ts`, `null-ic.ts`, `killing.ts`, `be37-covariant-eikonal.ts`): **must** rewrite `[μ][ν]` → `[μ*4+ν]` at every callsite.
3. **Direct-indexed in tests/bench**: same as (2), batched as the design's 1.4/1.5.

Move category (2) into an explicit Phase 1 sub-task (e.g., 1.3a) and re-scope 1.3 around the type-alias widening only.

## A-4 (MEDIUM) — Phase ordering (Decision #5) is defensible but inverted relative to risk

**Design section:** Decision #5, §2 Phase architecture.

The design pins Phase 1 (Schwarzschild, large) FIRST, Phase 2 (PG, small) SECOND, on the reasoning that Phase 2 inherits Phase 1's `MetricFnFlat` alias. This is technically correct: if both touch the alias in parallel, the merge is hostile.

But: PG's surface is **5 callsites in 2 files** (1 src + 1 test); Schwarzschild's surface is ~109 callsites in ~17 files. The lower-blast-radius migration is PG. Landing PG first would: (a) establish the `MetricFnFlat` alias under low-risk validation; (b) flush the type-system surprises early; (c) leave the high-volume Schwarzschild migration as a mechanical follow-on. The design rules this out only because it assumes parallel landing — but the design ALSO commits to serial (Decision #5). Once you're serial anyway, smaller-first is the strictly safer order.

**Severity rationale:** MEDIUM because the design's ordering is not wrong, just suboptimal. The argument "Phase 1 establishes the type alias for Phase 2 to reuse" works in both directions — whichever phase lands first is the one that establishes the alias.

**Recommendation:** Consider swapping: Phase 1 = O-6 PG (low-blast); Phase 2 = O-1 Schwarzschild (high-volume mechanical). Keep Decision #5's serial constraint; document the ordering swap with the "smaller-first lowers blast radius if the alias design needs revision" rationale.

## A-5 (MEDIUM) — Mid-cycle Adam+Eve vet positioned AFTER Phase 1+2; should be BETWEEN them

**Design section:** §2 Phase architecture; Phase 3; Decision #5.

The design puts the HIGHEST-STAKES vet at Phase 3, AFTER Phase 1 (Schwarzschild, ~109 callsites) AND Phase 2 (PG, ~5 callsites) both land. The argument: catch correctness regressions on the combined diff. But the reviewer brief asks: if the vet surfaces a HIGH issue in Phase 1 (e.g., an index-arithmetic typo in the migrated `dg[lambda*16+mu*4+nu]` consumer), does that retroactively invalidate Phase 2's work?

Answer: only partially. Phase 2 builds on Phase 1's `MetricFnFlat` type alias and the consumer-side widening pattern. A Phase 1 index-arithmetic bug in `gl4-integrator.ts` would not invalidate Phase 2's PG-specific work, because PG and Schwarzschild are independent fixtures. BUT a Phase 1 bug in the type alias itself (e.g., the alias is mis-shaped, or the runtime-vs-type asymmetry from A-3 surfaces) WOULD invalidate Phase 2's reliance on the alias.

**Severity rationale:** MEDIUM because the cost of a Phase-1-bug + Phase-2-already-landed scenario is one re-pinned commit, not a full revert. Manageable, but adds friction. The design could do better.

**Recommendation:** Split the vet into two cheaper gates:
- **Phase 1.5 (post-Schwarzschild) vet** — Adam reviews the type-alias landing + Schwarzschild migration. Lightweight; pure correctness. ~30 min of subagent time.
- **Phase 3 (post-PG, before Phase 4) vet** — confirms PG followed the established pattern; final correctness gate. ~15 min.

Total subagent time is roughly the same as one combined vet; the early gate catches type-alias bugs before they propagate.

## A-6 (MEDIUM) — R-2 bench gate of "≥ 2.0×" is achievable but tight; risk asymmetry not flagged

**Design section:** Decision #6, Risk R-2, §6 sprint baseline gate (PO-1 row).

The brainstorm projection was "2-5× combined" for O-1+O-2; O-2 alone delivered 1.27× (measured). For the combined to hit 2.0×, O-1 standalone must deliver at least **1.57×** (since 1.27 × 1.57 ≈ 2.0 assuming multiplicative). BR-2's analogous migration (christoffelFn flat) delivered 5–6×, but that was on the RK4 path (16 christoffel-evals per step). GL4's gInverseFn/dgInverseFn evaluation density is ~35 picard-iters × 4 closures × 2 stages = 280 closure-calls per step — slightly HIGHER density than BR-2's christoffel.

The Amdahl analysis in `benchmarks.md` v0.6.0 BR-2 section bounds the post-migration speedup by the closure-allocation fraction: 14%–64% of total wall time. If the fraction is at the LOW end (14%), Amdahl ceiling for the closure-only migration is only 1.16×; 2.0× is then unreachable regardless of how clean the migration is. If at the HIGH end (64%), ceiling is 2.77× and 2.0× lands easily.

The design says (Decision #6): "If the bench shows <1.5× after Phase 1 lands, the migration may have introduced a subtle memory-locality or cache-line issue invisible to the suite. STOP and diagnose." That's correct but asymmetric — it conflates "migration was buggy" with "Amdahl ceiling was lower than the brainstorm projected." Diagnosis of the latter doesn't fix anything; it just teaches us the closure-fraction was 14% not 64%.

**Severity rationale:** MEDIUM. The 2× target is plausible but not guaranteed; the design treats sub-1.5× as a code defect, when it could also be an Amdahl ceiling.

**Recommendation:** Distinguish the two failure modes explicitly:
- < 1.0× (i.e., regression): STOP and diagnose. Pure bug.
- 1.0× to 1.5×: investigate Amdahl ceiling. Re-run the Christoffel-fraction analysis pattern from `benchmarks.md` v0.6.0 (lines 195-220) on the gInverseFn closure. If ceiling is the constraint, ship as-is and lower the gate to "≥ 1.3×."
- ≥ 1.5×: ship.
- ≥ 2.0×: design's stated success.

Lower the §6 sprint-baseline gate to "≥ 1.5× (HIGH gate; sub-1.5× requires Amdahl-ceiling investigation, not a Phase 5 STOP)." Document the Amdahl band as a sub-decision.

## A-8 (MEDIUM) — S-9 risk tier of "LOW" is defensible but understates the deferred-registry hazard

**Design section:** §1 sprint goals; Phase 4; Decision #7.

S-9 collapses 5 `lowerNode` arms (killing-vector, conserved-charge, stress-energy, cosmological-constant, einstein-equation) into a registry-driven default arm. The reviewer brief flags: "If a deferred-evaluator registry dispatch has a subtle bug, every AST consumer using one of the 5 deferred kinds breaks."

Verification: all 5 arms at HEAD (`src/numerical/lowering.ts:534-587`) THROW. They are not "lowered to a value" — they are explicit error paths pointing the caller to the canonical evaluator. Their consumers in the test suite use `expect(() => ...).toThrow(/X/)` patterns. So the "every consumer breaks" failure mode is bounded: if the registry mis-dispatches, the message text changes but the throw still fires. Tests that pattern-match the message text would fail (caught by suite green); tests that only check `.toThrow()` without a pattern would pass-through silently.

The brainstorm flagged this risk implicitly (line 250-251 of `v0.7.1-brainstorm-simplify.md`): "Pure error-message consolidation. The redirected `Use X() from Y` prose is preserved verbatim per-entry in the registry; tests pattern-matching on the redirect target stay green." The design (Decision #7) requires Phase 4 to re-grep the actual arm count and explicitly carries the v0.7.1 Eve E4 lesson (prose drift caught by override).

**Severity rationale:** MEDIUM-LOW (not flagging as LOW because the v0.7.1 E4 precedent shows prose drift CAN escape suite-green if test pattern-matching is weak). The design's mitigation (Eve E4 awareness) is appropriate.

**Recommendation:** Tighten Phase 4 Task 4.2 acceptance: "Before merging, run `grep -rn 'is not yet implemented' tests/` and verify every matching test asserts on the FULL throw-message pattern, not just `.toThrow()`. If any test uses an unscoped matcher, add a per-kind-message regex assertion." Optional: add an exhaustiveness test (`forEach over all 5 deferred kinds; assert each throws a registry-dispatched message containing the expected canonical-evaluator name`).

## A-9 (MEDIUM) — R-1 test is too narrow; misses transpose typos

**Design section:** Risk register R-1.

R-1 says: "Phase 1 includes a regression sub-test that asserts a known closed-form value of `gInv[1*4 + 1]` (the `g^{rr}` diagonal) at r = 3·r_s — pinned to machine precision." This is good for **catching wrong-index-formula bugs** (`[μ+4ν]` instead of `[4μ+ν]`), but it does NOT catch transpose typos.

The reviewer brief notes: "What about `gInv[0*4 + 1]` vs `gInv[1*4 + 0]` (off-diagonals for symmetric metric should both be zero, so a transpose typo wouldn't be caught)?" Correct. For diagonal Schwarzschild, every off-diagonal is zero. A transpose typo in `dg` lookup (`dg[lambda*16 + nu*4 + mu]` vs `dg[lambda*16 + mu*4 + nu]`) is **silent** on Schwarzschild because `∂_r g^{mu nu}` is only non-zero on the diagonal (`mu == nu`), where transpose is a no-op.

The PG metric IS off-diagonal in the (T, r) block (`g_Tr = √(r_s/r) ≠ 0`). So Phase 2 (PG) is the natural transpose-typo detector — and the design's bench gate for PG is correct, BUT the design doesn't require an asymmetric-element regression sub-test there.

**Severity rationale:** MEDIUM. The Schwarzschild-only diagonal-pin won't catch transpose bugs that would only manifest on Kerr (off-diagonal) or PG (off-diagonal). The PG migration is the right place to add it.

**Recommendation:** Strengthen R-1 with two additions:
- (a) Phase 1 sub-test: pin `gInv[0*4 + 0]` (g^{tt}, c²-scaled — catches the c² omission class) AND `gInv[1*4 + 1]` (g^{rr}, diagonal). Diagonal-only is enough to catch index-FORMULA typos.
- (b) Phase 2 sub-test: pin `gInv[0*4 + 1]` AND `gInv[1*4 + 0]` for PG at r = 3·r_s; **assert they are EQUAL** (symmetry) AND **both non-zero** (sqrt(r_s/r) ≈ 0.577). This catches transpose typos that Schwarzschild masks.

## A-13 (LOW) — Decision #4 worktree preamble script has a soft failure mode

**Design section:** Decision #4.

The preamble:

```
git fetch origin claude/changelog-todo-sync-9PdMg
test "$(git rev-parse HEAD)" = "$(git rev-parse origin/claude/changelog-todo-sync-9PdMg)" \
  || git reset --hard origin/claude/changelog-todo-sync-9PdMg
```

This force-resets to the remote tip. If a previous agent committed locally but hadn't pushed, that work is silently discarded. The v0.7.1 worktree-fork-point lesson was that worktrees fork from `master` not the working branch; the fix is to align with the working branch's remote tip. But the script's hard-reset is destructive against an agent that legitimately has uncommitted local work in the worktree.

**Severity rationale:** LOW. Worktrees are ephemeral; agents are not supposed to commit in the worktree (commits land on the main checkout). But "supposed to" is not "enforced by the script."

**Recommendation:** Add a `git status --porcelain | grep -q . && echo "FATAL: worktree has uncommitted changes; aborting" && exit 1` guard before the hard-reset. Cheap safety net.

## Summary verdict — YELLOW

**3 HIGH findings, 7 MEDIUM, 3 LOW, 1 NIL-axis confirmation.**

The HIGH findings (A-1 grep regex, A-2 sibling fixtures, A-3 type/runtime asymmetry) are interconnected: all three are symptoms of the design treating the migration as primarily a runtime/value-shape change when it is in fact a TypeScript-side type-contract change. The Phase 1 plan as written will produce tsc errors at unanticipated callsites mid-sprint, exactly the failure mode the design's stale-carry-forward discipline is meant to prevent.

**None of these are foundational design flaws** — the migration is sound; the leverage projection is plausible; the bench gate is principled. But the design needs revision in three places before planning:

1. **Task 0.2 regex must cover variable-indexed callsites** (A-1).
2. **Sibling fixtures must be explicitly in-scope or explicitly deferred with type-alias union widening** (A-2).
3. **Decision #3 must distinguish flattenNA-mediated consumers from direct-indexed consumers; the direct-indexed src/ callsites need their own Phase 1 sub-task** (A-3).

The MEDIUM findings are nice-to-fix; the design is still actionable with them unresolved (Phase 0 baseline verification will surface most of the count errors at runtime).
