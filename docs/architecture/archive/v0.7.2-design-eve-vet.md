## E3 — Bench-gate dishonesty (the 2× target calibration) — MEDIUM

Brainstorm projections (`v0.7.1-brainstorm-optimize.md`):

- O-1 alone: "**2-5× on PO-1**; potential 1.5-3× end-to-end" (line 142).
- O-2 alone: "1.5-2.5× on PO-1" (line 31).
- O-1+O-2 combined target: "0.365 ms → ≤0.15 ms (**2.4× win**)" (line 543).

Observed: O-2 alone delivered **1.27×** — below the brainstorm's "1.5-2.5×"
lower bound. This is in the CHANGELOG as "honest framing" — the
brainstorm overshot, O-2 underdelivered against its own range.

The design's gate is "**≥2.0× on top of v0.7.1 post-O-2**", which
implies combined ≥2.54× (vs v0.6.1 baseline) — within the brainstorm's
combined 2-5× envelope, BUT relies on O-1 alone delivering a 2×
multiplier on top of the already-allocator-relieved post-O-2 baseline.

**The Amdahl problem**: the post-O-2 baseline has ALREADY captured
~21% of the wall-time reduction. O-1's allocation surface (~140
nested-array closure calls per Picard pass) overlaps with O-2's already-
reduced surface (per-iter buffer ping-pong). Multiplicative composition
of 1.27× and 2× is OPTIMISTIC — the residual allocator pressure that
O-1 targets is smaller in absolute terms post-O-2. A more honest
projection: **1.5×-2× combined on top of post-O-2** (1.9×-2.5× total
vs v0.6.1).

The design has a STOP gate at <1.5× (R-2 + Decision #6) but no
intermediate "**1.5-2× = SHIP with note, ≥2× = STRETCH win**" tier.
Falling between 1.5× and 2× would be a real result that the current
binary gate ("≥2× or STOP") punishes.

**Recommendation**: introduce a 3-tier gate in §6 / Decision #6:
- ≥2.0× on post-O-2: STRETCH (cite brainstorm prediction met).
- 1.5×-2.0× on post-O-2: SHIP with CHANGELOG note honestly framing
  Amdahl headroom exhaustion (mirrors v0.7.1's "1.27× honest framing"
  precedent).
- <1.5×: STOP + diagnose per existing Decision #6.

**Severity: MEDIUM.** Doesn't block plan-drafting but encourages
optimistic interpretation under uncertainty. The v0.7.1 brainstorm-
miss precedent strongly argues for the calibrated tier.

## E4 — Semver honesty (Decision #2 patch-version BREAKING) — MEDIUM

CLAUDE.md is explicit: "SemVer applies from v0.1.0 (2026-05-12) onward."

Decision #2 acknowledges the BREAKING-on-signature nature of the change
and proposes shipping under `v0.7.2` with "a BREAKING-CHANGE prefix on
the relevant commit." The decision text itself says: "the BREAKING-on-
signature nature of the change argues for a minor version bump
(0.7 → 0.8) BUT we defer that escalation to the user."

Strict-SemVer reading:
- A patch release (`x.y.Z`) is for **backward-compatible bug fixes only**
  (semver.org definition).
- Changing a `@public` function's return type from `number[][]` to
  `Float64Array` is **not backward-compatible** — TypeScript types narrow
  AND runtime behaviour changes for any consumer doing
  `result[i][j]` (which works on `number[][]` but fails on `Float64Array`
  since `result[i]` is `undefined`).
- Therefore strict-SemVer demands a **MINOR bump (0.7 → 0.8)** at
  minimum; an argument exists for **MAJOR (0.x → 1.x)** but the v0.x
  prefix gives some latitude per semver §4.

The design's deferral-to-user pattern is reasonable for the tag-strategy
question (which is genuinely user-owned per todo.md line 41-56), but the
**version-number choice itself is a technical-correctness question, not
a tag-strategy preference question.** A patch number on a BREAKING
change is a SemVer violation independent of when/whether the tag gets
pushed.

Additionally, **package.json currently sits at `0.6.0`** (per todo.md
line 81 + the v0.7-series tag-strategy queue item) — the publish
pipeline is blocked on NPM_TOKEN, so the on-disk version doesn't reflect
the v0.7 / v0.7.1 / v0.7.2 work at all. This MASKS the SemVer violation
because no npm consumer will see the patch-vs-minor distinction until
the token rotates. **That doesn't make the violation OK** — it makes
it a deferred-time-bomb at npm-publish time.

**Recommendation**: in Decision #2, explicitly say "the BREAKING change
makes `v0.7.2` a SemVer violation; the design SHOULD ship as `v0.8.0`.
Defer the tag-strategy question (single tag vs split) to the user, but
document the BREAKING ≥ MINOR-bump constraint as non-negotiable." Add a
note in §8 ("What this design is NOT") that says: "NOT a patch-class
release; v0.7.2 numbering is a placeholder for v0.8.0 once tag strategy
unblocks."

**Severity: MEDIUM.** Not blocking (no npm consumer impact while token
expired) but the design currently RATIONALIZES the patch-version choice
rather than calling it out as a violation requiring escalation.

## E7 — Mid-cycle vet timing (Phase 3 after Phase 1+2) — MEDIUM

Phase 3 (mid-cycle Adam+Eve vet) runs after BOTH Phase 1 AND Phase 2
land. The design defends this in §2 framing as "Phase 1 + Phase 2 touch
the canonical Schwarzschild fixture + the PG fixture — every GR-related
test depends on these. A subtle bug here propagates silently."

The structural concern Eve raises: **if Phase 1 introduces an index-
arithmetic typo that the tests DON'T catch (because both metric and
consumer have the same wrong indexing → the math cancels), Phase 2
inherits the bug at the type level.** R-1's mitigation is a pinned
closed-form assertion at `gInv[1*4 + 1]` (g^{rr} diagonal) at r=3·r_s.
That's good for the diagonal slot but DOES NOT cover:

- **Off-diagonal slots** (PG has g^{tr} = √(r_s/r) on the off-diagonal;
  if `mu*4+nu` vs `nu*4+mu` is transposed, a symmetric matrix won't
  detect it numerically, even though semantically the encoding has
  swapped row/column convention).
- **The `dg` 4×4×4 layout**: the design picks `flat[lambda*16 + mu*4 +
  nu]` — but no R-1-class pinned assertion verifies the LAMBDA ordering
  vs the MU ordering. A typo there fails silently in tests that derive
  ALL their indices from the same wrong convention.

The vet running AFTER Phase 2 means: if a Phase-1 index typo propagates
to Phase 2's PG migration via the shared `MetricFnFlat` alias contract,
the vet catches it ONCE for both — but the rollback cost is now 8
commits instead of 5.

**Recommendation**:
1. **Run the Adam+Eve vet between Phase 1 and Phase 2**, not between
   Phase 2 and Phase 4. The PG migration in Phase 2 has its own index
   correctness (off-diagonal slots) that benefits from a clean
   substrate, and the rollback surface is smaller if Phase 1 fails.
2. **Add an R-1b mitigation**: pin BOTH a diagonal AND an off-diagonal
   assertion (`gInv[0*4+1] === gInv[1*4+0]` symmetry check on PG would
   fail-loudly on a row/col transposition). For `dg`, pin a known-zero
   slot AND a known-nonzero slot at distinct (lambda, mu, nu) triples
   (e.g., `dg[1*16 + 1*4 + 1]` (`∂_r g^{rr}`) NON-ZERO + `dg[0*16 +
   0*4 + 0]` (`∂_t g^{tt}`) ZERO for Schwarzschild).

**Severity: MEDIUM.** Adam will likely also surface this; Eve's framing
is the operational-cost version ("rollback surface is now 8 commits").

## E11 — "This design is NOT" precision — LOW

§8 claims "NOT a behaviour change." This is qualified-true but reads
as absolute.

Strict reading:
- **Semantic behaviour** (test outputs, math results): PRESERVED. ✓
- **Perf behaviour** (wall-time): EXPLICITLY CHANGED — that's the whole
  point of O-1+O-6.
- **Memory-layout behaviour**: CHANGED (typed-array vs nested-array
  cache lines).
- **Allocation pattern** (GC pressure): CHANGED.

If Phase 5's bench shows a regression (R-2), THAT is a behaviour change
at the perf level. The "NOT a behaviour change" claim should be
qualified.

**Recommendation**: §8 bullet 2 rewrites to: "NOT a SEMANTIC behaviour
change. Every test assertion that passed at HEAD `b9d720f` must pass at
the v0.7.2 release HEAD. The migration is representational (memory
layout + per-call allocation), not semantic. Wall-time IS expected to
change — that's the goal."

§8 bullet 1 also has a small inaccuracy: "NOT a public API change.
`MetricFnFlat` is the only new exported type; all existing `@public`
symbols remain exported with widened types."

- "widened types" is the SemVer-MINOR-bump trigger discussed in E4.
  A widened type signature in TypeScript-strict mode IS an API change
  for consumers using narrow types. The design's framing ("not a
  public API change ... with widened types") is contradictory in one
  bullet.

**Severity: LOW.**
