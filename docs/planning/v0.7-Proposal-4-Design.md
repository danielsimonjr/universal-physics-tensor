# UPT v0.7 — Proposal 4 — Bridge DSL Building on `compileExpr` — Design

> **Scope:** Introduce a text-based DSL for authoring bridge equations,
> compiling through `@danielsimonjr/mathts-expression`'s `parse()` /
> `compileExpr()` and a UPT-side lift to the existing v0.6 physics AST.
> The DSL is **strictly additive** to the existing hand-written
> `src/bridges/equations/be-NN-*.ts` modules — no existing bridge is
> re-authored, deleted, or moved as part of this proposal.
>
> **Source proposal:** `docs/planning/UPT v0.70 - Proposals.md` §5
> "Proposal 4 — Bridge DSL Building on `compileExpr`" (2026-05-22),
> sequenced under §11 "v0.7 — Foundation Consolidation".
>
> **Effort estimate carried from §5/§0:** 2-3 weeks medium-risk. Risk
> is concentrated in (a) the DSL surface design across 42
> heterogeneous bridges; (b) the runtime-dependency precondition (the
> proposals doc assumes `mathts-expression` is "available"; this doc
> reads the actual repo state and finds it NEITHER installed NOR
> listed in `optionalDependencies`); (c) the behaviour of `compileExpr`
> itself, treated here as **UNVERIFIED** until a sister-repo
> source-read confirms it.
>
> **House-style reference:** `docs/planning/v0.6.1-Design.md`.

## Goal

Land a feature-flagged, additive Bridge-Equation DSL whose surface
covers the dimensional-AST shapes already used by the 42-bridge catalog
and that compiles via `mathts-expression`'s `parse()` plus a UPT-side
`liftToUptAst()` pass to the existing `ExprNode` union in
`src/dimensional/validator.ts`. The proposal succeeds if:

1. A new `src/dsl/` subtree exists with `BridgeSum`, `BridgeDraft`,
   `liftToUptAst`, and security-policy primitives, and is exposed via a
   new public-API entry point in `src/index.ts` guarded by the same
   `optionalDependencies`-installed-at-runtime check that
   `numerical/mathts-engine.ts` already uses for `mathts-tensor`.
2. **`mathts-expression` is added to `optionalDependencies`** and an
   `mathts-expression.ambient.d.ts` shim is added under
   `src/dsl/` mirroring the `mathts-tensor.ambient.d.ts` pattern from
   v0.6.1 Phase 0, so the build does not regress for environments that
   have not installed the peer (this environment is one such — see
   "Dependency precondition" below).
3. The DSL admits exactly the constructs enumerated in **Decision #2**
   (security policy) and rejects every construct the
   `mathts-expression` v0.2.0 security release rejects at parse-time —
   plus an additional UPT-side rejection layer for the `FunctionNode`
   call-targets that are NOT in the UPT bridge-DSL allow-list.
4. **At least three pilot bridges** are re-expressed in the DSL **as a
   parallel encoding**, NOT as a replacement: the existing
   hand-written modules under `src/bridges/equations/be-NN-*.ts`
   continue to be the canonical encoding for v0.7. The pilots
   demonstrate the round-trip claim from §5.4 of the proposals doc on
   a controlled subset, without committing the catalog to a manual
   rewrite of 42 modules.
5. A new test `tests/dsl/dsl-vs-handwritten-ast.test.ts` pins the
   structural-equivalence claim by running the dimensional analyzer on
   both the hand-written AST and the DSL-compiled AST for each pilot
   and asserting `inferredDimension` agreement.
6. The DSL touches **no** physics — every encoded bridge that already
   passed the v0.5.1 42-bridge `BRIDGE-PHYSICS-AUDIT.md` keeps its
   audited form. This is a re-authoring layer over the existing
   catalog, not a re-encoding of the physics.

## Architectural Decisions (locked)

### Decision #1 — ADDITIVE feature, not a replacement

The DSL is an **additive authoring layer** for v0.7. Concretely:

- **Existing 40+ hand-written bridge-equation modules under
  `src/bridges/equations/be-NN-*.ts` are NOT modified.** They remain
  the canonical encoding, the source of `BRIDGE_EQUATIONS` registry
  entries' `dimensional_signature`, and the test target for
  `tests/bridges/be-NN-encoding.test.ts`.
- **NEW bridges authored after v0.7.0** MAY use the DSL OR the
  hand-written AST style at the author's discretion. There is no
  enforcement either way; the catalog stays bilingual.
- **Three pilot bridges (BE-25 IIT-Φ, BE-37 Shapiro, BE-13
  Einstein-trace)** get a **parallel DSL encoding** under
  `src/bridges/equations-dsl/` (new directory) plus a structural-
  equivalence test under `tests/dsl/`. This is the round-trip
  acceptance criterion from §5.4, scoped down from "every v0.6
  bridge" to a 3-bridge demonstration, because:

  - The proposals doc's "all 42 bridges re-expressed" criterion is
    stated in §5.4 without an effort budget. Authoring 42 DSL
    bridges + 42 round-trip tests is itself a 1-2 week task,
    overshooting the §5 / §0 "2-3 weeks medium risk" envelope.
  - The pilots span the catalog's encoding-pattern diversity:
    log-ratio + product (BE-25), prefactor + log-stub (BE-37), and
    metric-trace + cosmological-constant (BE-13 — touches
    `CurvatureCompositeNode`'s scalar reduction).

**Rejected alternative:** wholesale REPLACEMENT of all 42 modules.
A manual 42-bridge rewrite would re-run every per-bridge disposition
history (Wave P-D R-D2 BE-25 → IIT, Wave Z-F BE-37 → Shapiro, Wave
P-B R-B2 BE-13 → Jacobson, etc.) on text-DSL ground. Transcription-
error risk is high; the upside (uniform authoring style) is aesthetic.

### Decision #2 — Security policy: explicit allow-list, not deny-list

`mathts-expression` v0.2.0 is a **security release**. Per the
proposals doc §1.1 (sourced from the MathTS CHANGELOG), the v0.2.0
pre-compile validator rejects, AT PARSE TIME:

- `AssignmentNode` (no `x = expr` mutation)
- `FunctionAssignmentNode` (no `f(x) := expr` function-definition)
- `FunctionNode` calls to forbidden builtins: `import`, `createUnit`,
  `evaluate`, `parse`, `compile`, `simplify`, `derivative`, `help`,
  `chain`.

**[UNVERIFIED]** — this list is taken from the CHANGELOG text quoted
in the proposals doc; Phase 0 reads the published source and
reconciles against the actual rejected set.

The UPT bridge-DSL inherits all of these upstream rejections AND
adds an additional `liftToUptAst` rejection layer. The UPT-side rule
is **explicit allow-list, not deny-list**:

**ALLOWED at the bridge-DSL surface:**

- `ConstantNode` — numeric literals; lifted to `{ kind: 'symbol',
  name: <stringified literal>, dim: DIMENSIONLESS }`.
- `SymbolNode` — bare symbol identifiers; lifted to
  `{ kind: 'symbol', name, dim: <from declared parameters> }`. If
  the symbol has no declared dimension, the lift FAILS with
  `UnknownSymbolError` — explicit declaration is required.
- `OperatorNode` for binary `+ - * /` and `^` (with integer or
  rational exponents only) — lifted to `{ kind: 'op', op, args }`.
- `OperatorNode` for unary `-` — lifted to a synthetic
  `{ kind: 'op', op: '*', args: [{ kind: 'symbol', name: '-1',
  dim: DIMENSIONLESS }, operand] }` to fit the v0.6 grammar (which
  does not have a unary-minus arm).
- `ParenthesisNode` — transparent; the lift recurses into its
  `content` field.
- A short, **closed allow-list of `FunctionNode` call-targets**
  that are mapped to UPT primitives:
  - `pderiv(of, wrt, wrtIndex)` → `kind: 'tensor-partial-derivative'`
    (existing UPT primitive from `src/dimensional/metric.ts`).
  - `contract(...args)` → `kind: 'tensor-product'` (existing UPT
    primitive from `src/dimensional/tensor.ts`).
  - `raise(operand, gInverse, idx)` / `lower(operand, g, idx)` →
    existing UPT helpers in `metric.ts`.
  - `integral(integrand, over)` → `kind: 'integral'`.
  - `derivative(of, wrt)` → `kind: 'derivative'`.
  - `log(arg)` / `ln(arg)` / `exp(arg)` — DSL surface only.
    These do NOT lift to a UPT primitive (there is no `log`/`exp`
    node in `ExprNode`); they emit a **dimensionless-stub** symbol
    (`log_<arg-hash>`, `exp_<arg-hash>`) and expose the inner
    argument as a separate lemma, mirroring the BE-25 / BE-37 /
    BE-45 dimensionless-stub idiom. The lift attaches a JSDoc-style
    comment listing the suppressed function so the round-trip is
    auditable.

**REJECTED at the bridge-DSL surface (in addition to the upstream
v0.2.0 rejections):**

- Any `FunctionNode` whose target is NOT in the allow-list above
  (UPT-side, throws `UnsupportedFunctionError` BEFORE the AST
  reaches `compileExpr`). This is the load-bearing security gate:
  even if the upstream sandbox loosens, UPT's DSL still rejects
  `system`, `exec`, `child_process`, `fs.*`, and every other token
  by construction. **The DSL has no escape hatch into JS at all.**
- `AccessorNode`, `IndexNode`, `RangeNode`, `BlockNode`,
  `ConditionalNode`, `ArrayNode`, `ObjectNode`, `RelationalNode` —
  every other node in the `mathts-expression` 16-node AST. None of
  these have a physics-AST counterpart in v0.6. **[UNVERIFIED]** —
  the 16-node list is sourced from the CHANGELOG quote in
  `Proposals.md`:46. Phase 0 verifies the list against published
  source; any extra node kind is added to this rejection set, not
  the allow-list.
- The Operator `=` (equality / assignment) — bridges express
  equations via two `ExprNode` trees (LHS, RHS) at the
  `BridgeDraft` API surface, not as a single AST. This mirrors the
  v0.6 `validateEquation(lhs, rhs)` convention.

**Why allow-list, not deny-list:** a deny-list would have to enumerate
every dangerous identifier that might appear in an `evaluate(...)`-
style call. An allow-list inverts the question to "what physics
primitives are we actually willing to support?" — finite, auditable,
and aligned with the catalog's existing encoding patterns. A DSL
that accepted arbitrary `evaluate(...)` would be a code-execution
vulnerability the same way `new Function(userString)` is.

### Decision #3 — Dependency precondition: `mathts-expression` must be installable AND optionally installed at consume-time

Two facts about the current repo state, verified against
`/home/user/universal-physics-tensor/package.json` and
`/home/user/universal-physics-tensor/node_modules/@danielsimonjr/`:

- **`@danielsimonjr/mathts-expression` is NOT listed in
  `optionalDependencies`** (the listed optional peers are
  `mathts-tensor` and `mathts-autograd` only).
- **No `@danielsimonjr/*` package is currently installed in this
  environment's `node_modules/`** — the `node_modules/@danielsimonjr/`
  directory exists but is empty.

This means the proposals doc's premise — "`compileExpr` is available
from `@danielsimonjr/mathts-expression`" — is FALSE in this repo's
current shipping state. Three steps are needed before any DSL code can
actually `import { parse } from '@danielsimonjr/mathts-expression'`:

1. **Add `mathts-expression` to `optionalDependencies`** in
   `package.json` with an explicit `^0.2.0` version constraint
   (matching the security release the proposals doc cites).
2. **Add `src/dsl/mathts-expression.ambient.d.ts`** following the v0.6.1
   Phase 0 pattern that introduced
   `src/numerical/mathts-tensor.ambient.d.ts`. The shim declares the
   module so `tsc` does not fail with TS2307 in environments without
   the peer installed. The shim body declares the minimum types the
   DSL actually consumes: `parse(input: string): MathTSNode` and the
   `MathTSNode` discriminated union over the 16 node kinds. **The shim
   is intentionally lossy** — `MathTSNode` resolves to `any`-shaped
   structural members at type-check time when the real package is
   absent. When the real peer IS installed at the maintainer's machine
   (per the maintainer's primary dev env), the real `.d.ts` takes
   precedence.
3. **Add a runtime presence check** at the entry point of `BridgeSum`
   that mirrors the lazy `await import(...)` pattern from
   `src/numerical/mathts-engine.ts:145,186`. If the peer is absent at
   runtime, the DSL surface throws `DslPeerNotInstalledError` with an
   actionable install hint:

   ```text
   The universal-physics-tensor bridge DSL requires the optional
   peer @danielsimonjr/mathts-expression. Install with:

     npm install --save-optional @danielsimonjr/mathts-expression@^0.2.0

   The DSL is an additive authoring layer; the rest of UPT (including
   the hand-written bridge catalog under src/bridges/equations/)
   works without this peer.
   ```

   This pattern was established in v0.5.1 TS-4 for `mathts-autograd`
   and reused in v0.6.1 Phase 0 for `mathts-tensor`. v0.7 Proposal 4
   makes it the third instance.

**Implication for goal #2:** the ambient shim alone is NOT
sufficient. It only fixes the typecheck. A FEATURE that actually
calls `parse()` at runtime needs the real package. Per Decision #1
the DSL is additive and feature-flagged, so the absence of the peer
degrades gracefully to "DSL not available; hand-written AST still
works" — but the published `0.7.0` release MUST be testable end-to-end
on at least one CI environment that has the peer installed.

### Decision #4 — `compileExpr` vs `parse` — design picks `parse`

The proposals doc §5.1 mentions both `parse()` and `compileExpr()`;
§5.2's code sketch uses `parse(d.equation)`. **This design picks
`parse`.** Rationale:

- The UPT bridge-DSL is an **authoring** layer, not an **evaluation**
  layer. `liftToUptAst` converts text → UPT `ExprNode` so the v0.6
  dimensional analyzer + numerical lowering do the evaluation.
- `compileExpr` (per the CHANGELOG description) returns a tree-walking
  compiler routing through `getSafeProperty`/`setSafeProperty`/
  `getSafeMethod`. Routing bridge evaluation through that would
  bypass UPT's dimensional + lowering passes — NOT what's wanted.
- **[UNVERIFIED]** — both names cited from the proposals doc's
  reading of the CHANGELOG. Phase 0 reads the published exports list;
  if `parse` is an alias-of / member-of `compileExpr`, the plan
  adjusts imports.

The proposal-doc title is preserved as the headline; implementation
pivots to `parse` once the source-read confirms the surface.

### Decision #5 — `liftToUptAst` is a 16→4 (+tensor primitives) lossy projection

The UPT v0.6 `ExprNode` union is **4 kinds** (`symbol | op | integral
| derivative`, per `src/dimensional/validator.ts:65-69`), plus the
tensor-shaped kinds in `tensor.ts` / `metric.ts` / `connection.ts`
(`tensor-symbol`, `tensor-product`, `metric-tensor`, `kronecker-delta`,
`tensor-partial-derivative`, and the v0.4.0+
`CovariantDerivativeNode`).

The MathTS v0.2.0 AST is **16 kinds** (per §1.1 of the proposals doc).
The lift is a 16-into-(4+tensor) **projection**, not a bijection. The
allow-list in Decision #2 enumerates exactly which 16-kind subset
projects and what each projects to.

**Mapping table (illustrative — pending Phase 0 verification of the
actual mathts-expression export names):**

| mathts-expression node | UPT `ExprNode` projection | Notes |
|---|---|---|
| `ConstantNode` | `{ kind: 'symbol', name, dim: DIMENSIONLESS }` | Numeric literal → dimensionless symbol; the literal's text is the `name`. |
| `SymbolNode` | `{ kind: 'symbol', name, dim: <declared> }` | Requires `parameters: { <name>: { dim } }` declaration in the `BridgeDraft`. Undeclared symbol → `UnknownSymbolError`. |
| `OperatorNode` (`+`,`-`,`*`,`/`) | `{ kind: 'op', op, args }` | Direct. |
| `OperatorNode` (`^`) | `{ kind: 'op', op: '^', args: [base, exp] }` | Exponent must lift to a literal-`symbol` ConstantNode; symbolic exponents are rejected (UPT validator enforces this independently). |
| `OperatorNode` (unary `-`) | `op: '*'` × `(-1)` | UPT grammar has no unary-minus arm. |
| `ParenthesisNode` | recurse into `content` | Transparent. |
| `FunctionNode` (`pderiv`, `contract`, `raise`, `lower`, etc.) | matching UPT primitive | Closed allow-list per Decision #2. |
| `FunctionNode` (`log`, `ln`, `exp`) | dimensionless-stub symbol + lemma arg | Mirrors BE-25 / BE-37 / BE-45 idiom. |
| `AssignmentNode` | REJECTED (upstream + UPT) | Bridge-DSL has no `=`. |
| `FunctionAssignmentNode` | REJECTED (upstream + UPT) | No user-defined functions in the DSL. |
| `AccessorNode`, `IndexNode`, `RangeNode`, `BlockNode`, `ConditionalNode`, `ArrayNode`, `ObjectNode`, `RelationalNode` | REJECTED (UPT-side) | No physics-AST counterpart in v0.6. |

**Lossiness is intentional.** A bridge that wants to use a feature
outside the allow-list — say, `BlockNode` for a multi-statement
derivation — should not be authored in the DSL. The hand-written AST
remains the escape hatch, by Decision #1.

### Decision #6 — Interaction with Proposals 2 and 3 (typed L/B/E + sparse catalog)

Per §11 the v0.7 release lands Proposals 1, 2, 3, and 4 together.
This design proposes Proposal 4's surface to be **agnostic to**
Proposals 2 and 3 by routing all DSL output through the existing
`BridgeEquationEntry` interface in `src/bridges/index.ts`:

- **Proposal 3 (typed L/B/E `Cell` discriminated union)** introduces a
  new `Cell` type whose `bridge` arm wraps a `BridgeEquationEntry` (or
  its replacement). Proposal 4 produces `BridgeEquationEntry`-shaped
  output unchanged; if Proposal 3 reshapes the registry entry type
  later in v0.7, Proposal 4 needs a one-line adapter on the
  `BridgeSum.compile()` return type — nothing structural.
- **Proposal 2 (sparse semantic catalog `Map<IndexTuple, Cell>`)** is
  a storage-layer change. Proposal 4 emits one `BridgeEquationEntry`
  per `BridgeDraft`; whether those entries land in the existing
  `BRIDGE_EQUATIONS: BridgeEquationEntry[]` array or in a
  `Map<IndexTuple, Cell>` is decided by Proposal 2 independently.
- **Proposal 1 (Intelligent Index layer)** introduces
  `UniversalIndex<Axis>`. The DSL surface in Decision #2 takes
  `from` and `to` regime identifiers as `BridgeDraft` fields.
  Initially these are strings (matching the v0.6
  `BridgeEquationEntry.bridges: [string, string]` shape); the
  Proposal 1 lift to `UniversalIndex` is a one-line type substitution.

**Sequencing implication:** within v0.7, Proposal 4 lands AFTER
Proposal 3 if Proposal 3 reshapes `BridgeEquationEntry`; otherwise
in any order. The Phase architecture below assumes Proposal 4 is
LAST among the four v0.7 proposals — soft ordering, ships
independently if Proposals 2/3 are deferred.

### Decision #7 — Adam+Eve adversarial review uses Opus subagents

Per the v0.6.1 Decision #9 precedent (no llm-gemini/llm-openai MCPs
in this remote-execution environment). Per the v0.6.1 retrospective,

## Phase 2 — `liftToUptAst` lift pass

### Motivation

The lift is the heart of the proposal. Per Decision #5, it's a
16→(4+tensor) lossy projection with a closed allow-list. Per
Decision #2, the lift is the load-bearing security gate.

### Components

- **Task 2.1 — Scaffold + ConstantNode + SymbolNode.** Create
  `src/dsl/lift.ts` exporting `liftToUptAst(node: MathTSNode,
  ctx: LiftContext): ExprNode`. `LiftContext` carries the declared
  `parameters` map. Lift the two leaf kinds first; structural
  recursion throws `UnsupportedNodeKindError`.
- **Task 2.2 — OperatorNode `+ - * /`.** Four binary arms; each
  asserts arity = 2 (validator's `^`-arity guard is the model).
- **Task 2.3 — OperatorNode `^` + unary `-` desugaring.** `^` arm
  with literal-exponent guard; unary-`-` desugaring to `op: '*'` ×
  `(-1)`.
- **Task 2.4 — ParenthesisNode transparency.**
- **Task 2.5 — `FunctionNode` UPT-primitives allow-list.** Closed-set
  mapping for `pderiv`, `contract`, `raise`, `lower`, `integral`,
  `derivative`. Each arm validates arity + argument shape.
- **Task 2.6 — `FunctionNode` `log`/`ln`/`exp` dimensionless-stub.**
  Emit stub symbol; expose inner argument as `lemma` field for
  round-trip testing.
- **Task 2.7 — Rejection paths.** Eight rejected-kind arms
  (`AccessorNode`, `IndexNode`, `RangeNode`, `BlockNode`,
  `ConditionalNode`, `ArrayNode`, `ObjectNode`, `RelationalNode`).
  Each throws `UnsupportedNodeKindError` with kind name + Decision
  #2 cross-reference.
- **Task 2.8 — Switch-exhaustiveness `never` arm.** Mirror
  `src/dimensional/validator.ts` `infer()`. If Phase 0 reveals > 16
  upstream kinds, additions go to the rejection set, not the allow-
  list; the `never` arm is the compile-time safety net.

### Tests

- `tests/dsl/lift-basic.test.ts` — per-kind round-trip tests on
  hand-crafted `MathTSNode` literals (the lift's input is structural,
  so we don't need the real peer installed at test time — we can
  build the input from the ambient-shim types).
- `tests/dsl/lift-rejections.test.ts` — every rejected kind has its
  own assertion-throws test.

### Deliverable

- LOC budget: `src/dsl/lift.ts` ≤ 400 LOC (the v0.6.1 large-file

## Risks

1. **Dependency-availability risk** (Decision #3). The
   `mathts-expression` peer is neither installed nor in
   `optionalDependencies` at design-time. If not published at
   `^0.2.x` on npm, Phase 1 stalls. **Mitigation:** Phase 0 Task 0.2
   `npm view` check; if absent, defer to v0.8 with sister-repo
   coordination to ship `mathts-expression` first.
2. **Lift-surface mismatch risk** (Decision #5). 16-node count + the
   rejected-builtins list are **[UNVERIFIED]**. **Mitigation:**
   Phase 0 Task 0.3 reconciliation gate; no Phase 2 code until
   reconciled.
3. **Round-trip fidelity risk** (Phase 4). Three pilots cover log-
   stub + prefactor + scalar-trace patterns. Uncovered patterns:
   covariant derivatives (BE-26/BE-37 eikonal), curvature composites
   (BE-17/BE-51/BE-52), integral primitives (BE-26 WKB, BE-44 soft-
   hair). **Mitigation:** `UnsupportedNodeKindError` messages are
   actionable; v0.7.x patch can extend the allow-list non-breakingly.
4. **Security-policy drift risk** (Decision #2). If upstream loosens
   (e.g. `evaluate` re-enabled), UPT's DSL must NOT inherit.
   **Mitigation:** UPT allow-list is independent + explicit; Phase
   2 Task 2.7 test pins the rejection set as a regression gate.
5. **`compileExpr` vs `parse` confusion risk** (Decision #4).
   **Mitigation:** Phase 0 Task 0.1 source-read.
6. **Bridge-DSL adoption risk.** A half-adopted catalog increases
   reader cognitive load. **Mitigation:** Phase 5 README states
   prominently that both encodings are first-class and hand-written
   remains canonical for the v0.6 catalog. v0.8 may migrate; that's
   its own design.

## Non-goals

Explicitly NOT in scope for v0.7 Proposal 4:

- **Re-encoding the 42-bridge catalog into the DSL.** Per Decision
  #1, only three pilots ship under `src/bridges/equations-dsl/`;
  all existing `src/bridges/equations/be-NN-*.ts` modules are
  untouched.
- **Evaluating bridges via `compileExpr`'s tree-walking compiler.**
  Per Decision #4 the DSL stops at `parse → lift → ExprNode`. UPT's
  numerical pipeline (`lowering.ts` + engines) does the evaluation,
  unchanged.
- **Embedding LaTeX / Mathematica / SymPy syntax.** The DSL's
  surface is `mathts-expression`'s grammar; LaTeX export remains
  the existing `BridgeEquationEntry.formula_latex` field, populated
  by hand at draft time.
- **Inheriting from `mathts-expression`'s `Node` base class.** Per
  the proposals doc §3.4 + §10.2 question 1: whether the upstream
  `Node` is open for extension is **[UNVERIFIED]**. The UPT
  physics AST does not extend it; the lift is a one-way projection.
- **Workbook integration** (Proposal 7). The `.mtsw`-as-bridge-artifact
  story is sequenced for v0.9. v0.7's DSL produces in-process
  `BridgeEquationEntry` values, not workbook files.
- **Differentiable DSL bridges** (Proposal 8). AD over DSL-authored
  bridges is sequenced for v0.9 alongside the workbook integration.
- **CI on a peer-installed environment.** v0.7's tests work via the
  ambient shim (the lift's tests build `MathTSNode` literals
  structurally). End-to-end CI against a real installed peer is a
  v0.7.x follow-up once the maintainer's CI tier is upgraded.

## Open questions for Adam+Eve review

(For the upcoming `v0.7-Proposal-4-Review-Findings.md` pass.)

1. **Does `parse()` accept multi-line input with newlines?** If so,
   does that admit `BlockNode` implicitly? Decision #2 rejects
   `BlockNode`; if `parse` cannot return a non-`BlockNode` tree for
   multi-line input, the DSL needs an explicit single-line guard.
2. **Is `compileExpr`'s sandbox sufficient on its own, or must the
   UPT `UnsupportedFunctionError` arm fire BEFORE upstream compile?**
   Phase 0 verifies whether `parse()` runs the security validator
   itself, or only `compileExpr` does.
3. **What's `parse()`'s error type?** Decisions #2/#3 assume a thrown
   typed error; if it returns `null` or a `Result`, error-handling
   reshapes.
4. **Are integer-exponent constraints enforced upstream?** If
   `parse('x ^ 2.5')` succeeds, the lift needs the rational-exponent
   guard at the `OperatorNode('^')` arm.
5. **Multi-character + underscore-bearing identifiers** like `R_far`,
   `M_kg`, `log2_ratio_ii`. The BE-37/BE-25 hand-written ASTs rely
   heavily on these; Phase 0 confirms upstream grammar accepts.

## Summary

Proposal 4 is a **2-3 week medium-risk additive feature** that adds a
text-DSL authoring layer for bridge equations, compiling through
`@danielsimonjr/mathts-expression`'s `parse()` and a UPT-side
`liftToUptAst()` to the existing v0.6 `ExprNode` grammar. The DSL is:

- **Additive** — three pilot bridges parallel-encoded; existing 40+
  modules untouched.
- **Security-policy-explicit** — UPT-side allow-list of 7 node kinds
  (plus a closed-set of `FunctionNode` call-targets), rejecting the
  other 9 mathts-expression node kinds by construction, in addition
  to the upstream v0.2.0 security rejections.
- **Dependency-precondition-explicit** — `mathts-expression` is
  currently NEITHER installed NOR in `optionalDependencies`; Phase 1
  adds both, with the ambient-shim + lazy-import pattern from v0.6.1
  Phase 0.
- **Forward-compatible with Proposals 1-3** — emits
  `BridgeEquationEntry`-shaped output; one-line adapter if Proposal
  3 reshapes the registry entry type.

The proposal's headline phrase "Building on `compileExpr`" is
preserved, with the implementation pivoting to `parse()` per
Decision #4 once Phase 0 verifies the actual upstream export shape.
Several **[UNVERIFIED]** claims throughout this doc — the 16-node
count, the rejected-builtins list, the `parse`-vs-`compileExpr`
distinction — are queued for resolution in Phase 0 BEFORE any code is
written.
