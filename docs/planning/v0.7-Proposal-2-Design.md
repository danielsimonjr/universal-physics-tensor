## Goal

The sprint succeeds if all of the following are true at the tagged
commit:

1. `UniversalTensor` exposes a `Map`-backed sparse catalog readable
   through `populatedCells()`, `populatedCount()`,
   `unpopulatedNeighborhoods()`, and `fluxDiagnostics()`. The exact
   storage decision is Decision #1 below; whichever side of the fork
   wins, there is **exactly one** authoritative `Map` (not two
   parallel `Map`s — the SHOWSTOPPER from Eve-R2).
2. A `FluxRule` registry on the tensor enforces three v0.7 rules at
   `addCell` time: (a) catalog-dimensional consistency, (b) L/B/E
   diagonal-vs-off-diagonal type-coordinate matching, (c) causality
   (warning tier). Rule bodies use only field names that exist on
   `Cell` variants at HEAD (Adam-V2 / Adam-V3 / Eve-R12 lessons).
3. All 42 bridges in `src/bridges/index.ts` flow through a new
   `catalog-adapter` module that constructs `BridgeCell` values from
   `BridgeEquationEntry` rows and feeds them to `addCell`. The
   adapter has a defined partial-failure policy (Eve-R14).
4. Existing `addLaw` / `addBridge` / `addEmergence` / `addCell`
   semantics from P3 remain green; the full pre-P2 test suite
   passes at or above the Phase 0 baseline (Adam-V11).
5. Query benchmarks: single-coordinate lookup average O(1); full
   iteration O(populated); both reported in
   `docs/architecture/benchmarks.md` (matches the proposals doc
   §3.5 acceptance criterion verbatim).
6. Public-surface delta is explicit (Phase 4 snapshot regen). Every
   new symbol is JSDoc-tagged `@public` or `@internal` before
   merge; no symbol relies on implicit re-export visibility
   (Adam-V9 / Eve-R11).

## Architectural Decisions (locked)

### Decision #1 — Storage shape: EXTEND legacy `tensorData`, NOT a parallel `cells` Map

**Resolves Eve-R2 (SHOWSTOPPER).** The previous design wrote
`this.cells.set(canonicalize(tuple), cell)` into a NEW
`Map<TupleKey, Cell>` while leaving the legacy `tensorData:
Map<string, Set<string>>` (`tensor.ts:130`) populated by `addLaw`
/ `addBridge` / `addEmergence`. Two Maps with two incompatible
key serializations (legacy `serializeIndices` uses insertion order
`scale|force|sym|info|dim|topo` at `tensor.ts:488-499`; the new
draft used alphabetical) silently drift: `getCellContents` queries
one, `populatedCells` returns the other.

**Locked: option (a) — extend `tensorData` to be the single source
of truth.** Retain the existing `Map<string, Set<string>>` shape
and the existing `serializeIndices` key serializer unchanged. The
new P2 surface (`populatedCells`, `populatedCount`,
`unpopulatedNeighborhoods`, `fluxDiagnostics`) reads from the same
`tensorData` plus the existing per-kind ID→object maps
(`knownLaws`, `bridgeEquations`, `emergentPhenomena`):

- `populatedCount()` returns `tensorData.size` (matches existing
  `getStats().occupiedCells`).
- `populatedCells()` walks `tensorData`, resolves cell-IDs via
  the per-kind maps, then wraps as `LawCell` / `BridgeCell` /
  `EmergenceCell` (inverse of the existing `cellToLaw` /
  `cellToBridge` / `cellToEmergence` adapters at
  `tensor.ts:64–116`; Phase 2 adds the forward direction).

**Why not option (b):** replacing `tensorData` outright with
`Map<TupleKey, CellSlot>` is the cleaner long-term shape but
forces rewriting all five legacy methods (`getCellContents`,
`getBridgeCellContents`, `queryLaws`, `findBridges`, `getStats`)
plus every test that asserts on them. That is a v0.8 sprint.

**Consequence:** P2 does NOT ship `canonicalize`, `TupleKey`, or
a new key serializer. The proposals doc §3.3 `Map<TupleKey, Cell>`
sketch is conceptually adopted but structurally deferred. The
redraft trades architectural purity for showstopper avoidance.

### Decision #2 — `BRIDGE_EQUATIONS` shape is unchanged

`src/bridges/index.ts` (1793 lines, 42 entries — verified
`grep -cE "^\s+id: [0-9]+," src/bridges/index.ts` returns 42 at
HEAD) remains the catalog source-of-truth. The
`BridgeEquationEntry` interface at lines 116–149 is not modified.
P2's catalog-adapter *reads* this catalog and constructs
`BridgeCell` values; it does not migrate the catalog format.
Catalog migration is a future sprint concern (v0.8 territory) and
would force a major bump under SemVer.

This matches Adam-V4's verdict on the previous design (✅
VERIFIED).

### Decision #3 — Rule 1 (Dimensional Consistency) fires on `BridgeEquationEntry`, not on `Cell`

**Resolves Adam-V3 (compile-blocking).** The previous design wrote
`if (cell.dimensional_signature === null) { ... }`, but **no
`Cell` variant carries a `dimensional_signature` field** (verify
against `src/core/cell.ts:68–141`). That field exists only on
`BridgeEquationEntry` (`src/bridges/index.ts:140`).

**Locked: option (a) — Rule 1 is a CATALOG rule, not a CELL rule.**
The rule fires at catalog-ingestion time inside the
`catalog-adapter` module (Phase 3), not inside `addCell`. It reads
`BridgeEquationEntry.dimensional_signature` directly. The adapter
emits a `FluxDiagnostic` per entry whose signature does not match
the expected shape for its declared `bridges: [from, to]` regimes,
and a different `FluxDiagnostic` per entry whose
`dimensional_signature` is **structurally `null`** (not "null
inside a `notes:` prose string" — see the Empirical-Claims
discipline below).

We do **not** add `dimensionalSignature: Dimension | null` to
`BridgeCell` (option (b)). That would be a breaking change to the
P3 surface and would conflate catalog metadata (a property of the
spec-extraction step) with cell semantics (a property of the
tensor slot). P3's surface stays clean.

**Empirical-claims discipline (Eve-R1 HIGH).** The previous design
claimed "1 null `dimensional_signature` in BE-15" — Adam-V5
ratified it ✅ VERIFIED. Eve falsified the claim at the field
level. Re-verified at this redraft's writing:

```text
$ grep -cE "^\s+dimensional_signature: null" src/bridges/index.ts
0
$ grep -cE "^\s+dimensional_signature:" src/bridges/index.ts
43   # 42 entries + 1 interface declaration at index.ts:140
```

BE-15 has `dimensional_signature: '[area]'`. The "null" matches
Adam found were inside BE-36's `notes:` string-literal prose, NOT
the structural field. **At HEAD, the structural count of
`dimensional_signature: null` is ZERO.** The warning-vs-error
tier choice in the previous design ("warning to avoid breaking on
1 null entry") loses its premise.

**Re-justified rule tier:** Rule 1 fires at ERROR tier when (i) a
structural `dimensional_signature: null` is present, OR (ii) the
field is non-null but the parsed dimension does not equal the
shape inferred from `bridges: [from, to]` (uses the existing
`inferDimensionForBridge` + `EXPECTED_DIMENSION_BY_BRIDGE` table
at `src/dimensional/bridge-check.ts`). The tier is ERROR because,
at the empirical-zero-nulls HEAD state, no catalog entry can
trigger (i); only true mismatches under (ii) fire, and those are
bugs. If a future spec edit lands a `null` signature without
remediation, the rule correctly halts the next adapter run.
UNVERIFIED: whether `EXPECTED_DIMENSION_BY_BRIDGE` covers all 26
unknown-unknown bridges — see Risk §3 and the Phase 0 grep gate.

### Decision #4 — Rule 2 (L/B/E coordinate matching) reads only field names on `Cell` variants

A `LawCell` is diagonal-in-regime: the rule fires inside `addCell`
(`'law'` arm). For each `scale` in `cell.scales` (note: `scales`
is `ReadonlyArray<PhysicalScale>` per `cell.ts:90` — plural, not
singular; see Decision #6 for the multi-scale policy), the rule
asserts that the L cell's declared regime axes are consistent
(no forbidden cross-scale wiring at the same `id`). A
`BridgeCell` is off-diagonal: the rule asserts
`cell.source !== cell.target` by at least one axis (this is
**already enforced** by `addBridge` at `tensor.ts:217–226` —
Rule 2 piggybacks on existing logic for bridges). An
`EmergenceCell` spans the multiple-coordinate domain defined by
`cell.indices` (plural, per `cell.ts:131`); the rule asserts
`cell.indices.length >= 2` (otherwise the entry is structurally
a Law).

Rule 2 violations are ERROR tier. Each violation throws
`FluxViolationError` from `addCell`. Partial-state recovery is a
Phase 3 / Decision #11 concern for catalog ingestion; single-cell
`addCell` calls fail-atomic.

### Decision #5 — Rule 3 (Causality) uses `BridgeCell.source`/`.target`, not `from`/`to`

**Resolves Adam-V2 (compile-blocking).** The previous design read
`cell.from.scale` / `cell.to.scale`. `BridgeCell` at
`src/core/cell.ts:107–114` exposes `source: TensorIndices` and
`target: TensorIndices`. `TensorIndices.scale` is `PhysicalScale
| undefined` (`src/core/types.ts:77`). Rule 3 must handle
missing-axis gracefully.

**Locked rule body sketch** (Phase 1 Task 1.3 TDD spec):

1. Read `src = cell.source.scale`, `dst = cell.target.scale`.
2. If `src === undefined || dst === undefined`, return
   `{ ok: true, diagnostic: { severity: 'info', ruleName: 'causality',
   cellId: cell.id, message: 'scale axis unspecified; check skipped' } }`.
3. Look up `arrow = SCALE_ARROW[src][dst]` (private map; coarser→finer
   = `'reverse'`, finer→coarser = `'forward'`, equal = `'lateral'`).
4. If `arrow === 'reverse'`, return a `'warning'` diagnostic naming
   the source/target scales and recommending audit.
5. Otherwise return `{ ok: true }`.

Rule 3 emits **warnings only** in v0.7 (matches the proposals doc
§3.3.3). Promotion to error is deferred to v0.8 after the
catalog is audited.

**SCALE_ARROW** is a private map inside the flux-rule module,
encoding the partial-order `quantum < mesoscopic < classical <
cosmological` (existing `PhysicalScale` union in `types.ts:10-14`).
The earlier draft suggested adding a `timeReversalAnnotation:
true` field to `BridgeCell` to suppress the warning (Eve-R12); we
drop that suggestion — `BridgeCell` does not carry such a field
and adding one contaminates the public type. Suppression is
per-cell-ID in a private `causalityWhitelist: ReadonlySet<string>`
inside the rule module (zero entries in v0.7; entries earn their
place via design review).

### Decision #6 — Multi-scale `LawCell.scales`: per-scale expansion in storage, single `Cell` value at the API

**Resolves Eve-R13 (MEDIUM).** `LawCell.scales:
ReadonlyArray<PhysicalScale>` (`cell.ts:90`) is plural — a single
law can apply at multiple scales (e.g., a continuity law at
quantum AND classical). The legacy `addLaw` already iterates the
cross-product `scales × forces` and writes one cell-key per
`(scale, force)` pair (`tensor.ts:198–203`). P2 preserves that
behavior.

**Locked semantics:**

- `addCell(lawCell)` writes one cell-ID per `(scale, force)`
  pair into `tensorData`. The `LawCell` object itself is stored
  once in `knownLaws` keyed by `id`. There is no fan-out at the
  `Cell`-object level; only at the cell-key level.
- `populatedCells()` returns one `LawCell` per unique cell-ID, NOT
  per cell-key. Walking `tensorData` therefore needs an outer
  de-duplication step: collect all IDs across all keys, look up
  each ID once, return.
- Rule 2 (Decision #4) operates on the `LawCell` object once per
  `addCell` call, not once per expanded cell-key.

**Rejected alternatives:** (i) emit N `LawCell` objects with one
`scales` entry each — fragments the cell-identity contract;
(ii) use an `'all-scales'` virtual coordinate — introduces a
sentinel value into the `PhysicalScale` union, breaking
exhaustiveness checks across the dimensional validator. Both
are off-table.

### Decision #7 — Bridge cells use the legacy composite key `'<sourceKey> -> <targetKey>'`

**Resolves Eve-R4 (HIGH).** The previous design's `extractTuple(cell:
Cell): TupleKey` would collapse a bridge to a single tuple — a
quantum→classical bridge keyed at `quantum` would collide with a
quantum-scale Law at the same key. The existing
`bridgeCellKey(source, target)` at `tensor.ts:289–291` already
addresses this with `'<sourceKey> -> <targetKey>'` (literal `' -> '`
substring as the discriminator).

**Locked: P2 preserves the existing two-shape key scheme.**
Diagonal cells (Laws, Emergences) use `serializeIndices(indices)`.
Off-diagonal cells (Bridges) use `bridgeCellKey(source, target)`.
The new `populatedCells()` walks `tensorData` and resolves each
key back to the appropriate `Cell` variant. The walk distinguishes
the two key shapes by the literal `' -> '` substring (the legacy
discriminator — already in use at `tensor.ts:402`).

This is option (b) from the redraft brief (composite key
`${sourceKey}→${targetKey}`), already the legacy behavior. No new
key-encoding code lands. Option (c) (two separate Maps) is
rejected under Decision #1's "one source of truth" rule.
Option (a) (`extractTuples` returns a pair) is rejected because it
implies a new public surface that we don't need.

### Decision #8 — `FluxRule` registry uses a discriminated union with `_exhaustive: never` dispatch

**Resolves Eve-R9 (MEDIUM).** Mirroring the
`UniversalTensor.addCell` switch at `tensor.ts:370–384` and the
`statusToConfidenceNumber` switch at `tensor.ts:47–58`, the
flux-rule dispatcher uses an explicit discriminated union plus an
exhaustiveness guard. Type shapes (Phase 1 Task 1.1):

- `FluxRuleKind = 'dimensional-consistency' | 'lbe-coordinate' |
  'causality'` (`@internal`).
- `FluxRule { kind: FluxRuleKind; check: (cell: Cell) =>
  FluxRuleResult }` (`@internal`).
- `FluxRuleResult { ok: boolean; diagnostic?: FluxDiagnostic }`
  (`@internal`).
- `FluxDiagnostic { severity: 'info' | 'warning' | 'error';
  ruleName: FluxRuleKind; cellId: string; message: string }`
  (`@public`).
- `FluxReport { diagnostics: ReadonlyArray<FluxDiagnostic>;
  errorCount: number; warningCount: number; infoCount: number }`
  (`@public`).
- `class FluxViolationError extends Error` (`@public`) — carries
  `ruleName: FluxRuleKind` + `cellId: string`.

Severity comparison uses string literals through the
discriminated union, never raw `===` against an untyped string.
Any future addition of a new rule kind forces a compile-time
update to every switch over `FluxRuleKind` (the `_exhaustive:
never` default arm catches it).

### Decision #9 — Public-surface buckets are explicit before merge

**Resolves Adam-V9 + Eve-R11 (MEDIUM).** v0.6.1 dropped 24
internal exports for surface discipline. P3 added 7 (`Cell`,
`CellBase`, `CellConfidence`, `LawCell`, `BridgeCell`,
`EmergenceCell`, `compose`). P2 must not silently double that.

**Locked surface buckets:**

| Symbol | Bucket | Justification |
|---|---|---|
| `FluxRule` (interface) | `@internal` | Registry implementation detail. |
| `FluxRuleKind` (union) | `@internal` | Coupled to registry shape. |
| `FluxRuleResult` (interface) | `@internal` | Internal IPC of the registry. |
| `FluxDiagnostic` (interface) | `@public` | Returned by `fluxDiagnostics()`. |
| `FluxReport` (interface) | `@public` | Top-level return shape. |
| `FluxViolationError` (class) | `@public` | Thrown from `addCell`. |
| `UniversalTensor.populatedCells` | `@public` | Acceptance-criterion method. |
| `UniversalTensor.populatedCount` | `@public` | Same. |
| `UniversalTensor.unpopulatedNeighborhoods` | `@public` | Same. |
| `UniversalTensor.fluxDiagnostics` | `@public` | Same. |
| `catalogToCells` (function) | `@public` | Adapter consumers call. |
| `scanCatalog` (function) | `@public` | Best-effort variant. |
| `CatalogIngestionReport` | `@public` | Adapter return shape. |
| `CatalogIngestionError` | `@public` | Thrown by strict adapter. |

Net public-surface delta: **+8 type/class symbols** (re-exported
from `src/index.ts`) plus 4 method additions on
`UniversalTensor`. The 3 `@internal` symbols are NOT re-exported
from `src/index.ts` and carry `@internal` in their JSDoc — matching
v0.6.1's minimize discipline.

We do **not** introduce `IndexTuple`, `TupleKey`, `canonicalize`,
or `extractTuple` (Eve-R5 / Eve-R6 dissolved under Decision #1).

### Decision #10 — `unpopulatedNeighborhoods()`: single-axis-flip semantics

**Resolves Eve-R7 (MEDIUM).** The previous design's Decision #4
contradicted Task 3.3 (wildcard vs. ±1). `TensorConfig` has no
range field for "± 1 within declared range".

**Locked semantics:** A neighborhood of a populated cell at index
tuple `t` is the set of tuples `t'` that differ from `t` in
exactly ONE axis, where the differing axis value is **drawn from
the config-declared set** for that axis (`config.scales`,
`.forces`, `.symmetries`, `.informationMeasures`). The integer
axes (`dimension`, `topology`) are not enumerable from
`TensorConfig` (no declared range exists) and are treated as
**wildcards** — single-axis flips along those axes are NOT
generated. UNVERIFIED: whether this generates a useful
research-roadmap signal; the proposals doc §3.4 asserts it without
an example. Phase 4 benchmarks output a sample.

The method returns `TensorIndices[]` (the existing partial-axis
type at `types.ts:76–83`), NOT a new `IndexTuple` type (Eve-R6
resolution: don't duplicate the coordinate shape).

### Decision #11 — `catalog-adapter` partial-failure policy: two-pass collect-then-commit

**Resolves Eve-R14 (LOW).** If the adapter hits a malformed entry
on row 7 of 42, rows 1–6 must not be left in the tensor while the
caller sees an exception. **Locked policy:**

1. Scan all 42 entries, building `BridgeCell` candidates in memory.
2. Run Rule 1 (dimensional consistency) per candidate without
   mutating tensor state; accumulate into
   `CatalogIngestionReport.errors`.
3. If `errors.length === 0`, call `addCell` per candidate (Rules
   2/3 still fire but at warning/info tier; Rule 2 ERROR on
   bridges is pre-empted by the adapter's `source !== target`
   guarantee).
4. If `errors.length > 0`, return the report and throw
   `CatalogIngestionError(report)`. Tensor remains untouched.

Consumers wanting best-effort ingestion call `scanCatalog()`,
which returns the report without throwing.

### Phase 1 — Flux-rule scaffolding (`src/core/flux-rules.ts`)

**Motivation:** Defining the rule types and Rules 2 + 3 in
isolation, before wiring into `UniversalTensor`, lets Phase 1
tests run purely against the type definitions and pure-function
rule bodies, with no risk of regressions in existing tensor
methods. Rule 1 ships in Phase 3 alongside the catalog adapter
(it needs the `BridgeEquationEntry` input shape).

**Tasks:**

- **Task 1.1 — Type scaffolding.** Define `FluxRuleKind`,
  `FluxRule`, `FluxRuleResult`, `FluxDiagnostic`, `FluxReport`,
  `FluxViolationError`. JSDoc-tag each per Decision #9.
- **Task 1.2 — Rule 2 implementation (L/B/E coordinate
  matching).** Pure function over `Cell`. Dispatches by
  `cell.kind`. The `'bridge'` arm asserts
  `serializeIndices(source) !== serializeIndices(target)` (note:
  identical to the existing rejection at `tensor.ts:217–226` —
  Rule 2 is a re-statement, not a new constraint, but the
  registry needs an explicit entry for exhaustiveness). The
  `'law'` arm asserts the `scales × forces` cross-product is
  non-empty. The `'emergence'` arm asserts
  `cell.indices.length >= 2`. Exhaustive `_exhaustive: never`
  default arm.
- **Task 1.3 — Rule 3 implementation (causality).** Pure function
  over `BridgeCell` (the dispatcher passes only the
  `cell.kind === 'bridge'` arm to it). Body per Decision #5.
  Warning tier in v0.7.
- **Task 1.4 — Rule registry dispatcher.** A pure function
  `runRules(cell: Cell, rules: ReadonlyArray<FluxRule>):
  FluxReport`. Exhaustive switch over `FluxRuleKind` with
  `_exhaustive: never` default (Decision #8).

**Tests:** `tests/core/flux-rules.test.ts` (new). Covers:
  - Rule 2 with a diagonal `LawCell` returns `ok: true`.
  - Rule 2 with a `BridgeCell` whose `source === target` returns
    `ok: false`.
  - Rule 3 with a quantum→classical bridge returns `ok: true`,
    no diagnostic.
  - Rule 3 with a cosmological→quantum bridge emits a warning
    diagnostic with exact message text pinned.
  - Rule 3 with `source.scale === undefined` emits an `info`
    diagnostic (not a warning) — the "scale-unspecified skip".
  - Rule registry exhaustiveness: adding a new `FluxRuleKind`
    arm without updating the switch is a compile error
    (`@ts-expect-error` test).

**Deliverable:** `src/core/flux-rules.ts` + tests, 4 commits.

### Phase 2 — `UniversalTensor` integration

**Motivation:** Wiring the rule registry, the new query methods,
and the diagnostic accumulator into `UniversalTensor` is the
sprint's primary observable deliverable. Strictly additive to the
existing class — no legacy method changes shape.

**Tasks:**

- **Task 2.1 — `populatedCount()` + `populatedCells()`.** Both
  delegate to the legacy `tensorData` map per Decision #1.
  `populatedCells()` resolves cell-IDs back to `Cell` values by
  walking the per-kind ID→object maps and wrapping each through
  inverse adapters (forward adapters at `tensor.ts:64–116`;
  inverses are new in this task).
- **Task 2.2 — `unpopulatedNeighborhoods()`.** Implementation per
  Decision #10. Single-axis-flip enumeration; dimension/topology
  axes are wildcards.
- **Task 2.3 — Rule registry + `fluxDiagnostics()`.** Add a
  private `fluxRules: FluxRule[]` field plus a public
  `fluxDiagnostics(): FluxReport` method. Default rule set:
  Rules 2 and 3 (Rule 1 fires from the adapter, not from
  `addCell`). Modify `addCell` to invoke `runRules(cell,
  this.fluxRules)` AFTER the legacy `addLaw` / `addBridge` /
  `addEmergence` dispatch. Rule violations at ERROR tier throw
  `FluxViolationError` (Phase 1 Task 1.1); the existing typed
  methods are wrapped so they roll back on throw.

  We do NOT add `pendingDiagnostics: DiagnosticReport[]` as a
  mutable accumulator (Eve-R8). Diagnostics are computed
  on-demand by `fluxDiagnostics()`, which re-runs the rule set
  across all populated cells (one-time cost; ≤ 42 cells in v0.7).
- **Task 2.4 — Cross-method consistency tests.** Add tests that
  exercise the "no cross-map string compare" invariant (Adam-V7
  carry-forward): assert `getCellContents`,
  `getBridgeCellContents`, `populatedCells`, `getStats` all
  reflect the same underlying state after a sequence of
  `addLaw` / `addBridge` / `addEmergence` / `addCell` calls.
  This is the SHOWSTOPPER-prevention test.

**Tests:** `tests/core/populated-cells.test.ts` (new) +
`tests/core/flux-integration.test.ts` (new). Existing suite stays
green (≥ Phase 0 baseline).

**Deliverable:** Updated `src/core/tensor.ts`. 4 commits.

### Phase 3 — Catalog adapter (`src/bridges/catalog-adapter.ts`)

**Motivation:** Feeding all 42 bridges through `addCell` is the
"42 v0.6 bridges fit through the three v0.7 flux rules"
acceptance criterion from the proposals doc §3.5.

**Tasks:**

- **Task 3.1 — `catalogToCells(entries:
  ReadonlyArray<BridgeEquationEntry>):
  ReadonlyArray<BridgeCell>`.** Pure function. Maps each entry to
  a `BridgeCell` by reading `entry.bridges: [from, to]`, looking
  up the corresponding `PhysicalScale` values (with the

## Risks

1. **Decision #1 (extend-not-replace) leaves option (b) for v0.8 —
   accumulates legacy.** The "two key serializers, one Map" world
   we keep is structurally less clean than `Map<TupleKey, Cell>`.
   v0.8 will need to clean it up; v0.7's discipline must not add
   further legacy.
   **Mitigation:** No new code reads or writes `tensorData` with a
   different key shape. The rule registry consumes `Cell` directly,
   not keyed lookups. Phase 2 Task 2.4's "cross-method
   consistency" test pins this.

2. **Multi-scale `LawCell` fan-out (Decision #6) inflates the
   cell-key count for a single law.** A law with 3 scales × 4
   forces writes 12 cell-keys. `populatedCount()` reflects key
   count, not catalog-object count — easy to misread.
   **Mitigation:** `populatedCount()` is named accurately
   ("cells", not "catalog entries"). `getStats().knownLaws`
   already exists for the catalog-object count
   (`tensor.ts:472`). Phase 4a docs spell out the distinction.

3. **26 catalog entries have `bridges: ['unknown', 'unknown']`
   (Adam-V5 corrected from 30).** Half the catalog. Until the
   spec-editing pass annotates these with concrete regimes, the
   adapter submits zero of them to `addCell`. Rule 1 cannot fire
   on them; the warning-tier signal is muted.
   **Mitigation:** `CatalogIngestionReport.unsubmitted` exposes
   the list. Carried as a v0.7.x follow-up: a spec-edit sprint to
   annotate the 26. UNVERIFIED: whether
   `EXPECTED_DIMENSION_BY_BRIDGE` already covers them — Phase 0
   Task 0.3 grep-checks the coverage count.

4. **Rule 3 (causality) emits warnings on legitimate
   coarsen→refine bridges (e.g., effective-theory matching
   coefficients).** v0.6 catalog audits may produce noise in this
   tier.
   **Mitigation:** Warning tier in v0.7 (not error). Decision
   #5's private `causalityWhitelist` provides per-cell-ID opt-out
   without contaminating the `BridgeCell` type.

5. **Public-surface snapshot regeneration is easy to forget.** A
   forgotten regen causes a CI failure that looks like a test
   bug (P3 review found the same risk).
   **Mitigation:** Phase 4a Task 4a.2 explicitly names snapshot
   regen as a required step in its task title.

6. **Phase 0's `git merge-base --is-ancestor` P3 verification
   assumes a single canonical P3 commit-SHA.** If the P3 branch
   was squash-merged (loses the original SHA) or P3 was reverted
   and re-applied (different SHA), the gate may fail spuriously.
   **Mitigation:** The gate falls back to symbol-existence checks
   (`Cell` importable, `compose` importable) if the SHA check
   fails. Both must pass; either passing on its own is
   insufficient.

7. **`unpopulatedNeighborhoods()` could produce a combinatorially
   large output as the catalog grows (Decision #10 single-axis
   flips).** For N populated cells with K declared values per
   axis across 4 enumerable axes, output size is bounded by
   `N × ((K_scale-1) + (K_force-1) + (K_sym-1) + (K_info-1))` —
   for default v0.6 config (4/5/5/4) at N=42, ≈ **588** entries.
   Manageable in v0.7; may need pagination later.
   **Mitigation:** documented as a v0.8 scaling concern.

## Non-goals

The following are explicitly out of scope for this sprint:

- **No changes to the 42-bridge catalog** (`src/bridges/index.ts`).
  `BridgeEquationEntry` stays as-is (Decision #2).
- **No replacement of `tensorData` with `Map<TupleKey, Cell>`.**
  Decision #1 defers to v0.8.
- **No new public coordinate types.** `IndexTuple`, `TupleKey`,
  `canonicalize`, `extractTuple` are NOT shipped. Existing
  `TensorIndices` serves both legacy and new code paths.
- **No `confidenceToStatus` adapter.** P3 rejected it (Eve-R3
  there); P2 does not resurrect it.
- **No `encodingDebt`, `timeReversalAnnotation`, or any other
  catalog-metadata field on `Cell` variants.** Migration state
  lives in private maps inside the rule module.
- **No `pendingDiagnostics: DiagnosticReport[]` mutable
  accumulator on `UniversalTensor`.** Diagnostics are
  recomputed-on-demand by `fluxDiagnostics()` (Eve-R8).
- **No removal of `addLaw`, `addBridge`, `addEmergence`** from
  `UniversalTensor`'s public API.
- **No merger with Proposals 1 or 4.** `AxisCoordinate`,
  `UniversalIndex`, AST-typed `equation` field, Bridge DSL —
  none of those land in P2.
- **No promotion of Rule 3 to ERROR tier.** Warning-only in v0.7;
  v0.8 promotion after the 26 unknown-bridges are audited.
- **No version-prefixed key brand (`v1:...`).** Eve-R5 is
  dissolved by Decision #1 (no `TupleKey` ships).
