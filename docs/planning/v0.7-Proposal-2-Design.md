# UPT v0.7 — Proposal 2: Sparse Semantic Catalog Storage — Design

> **Scope:** Refine `UniversalTensor`'s internal `tensorData: Map<string, Set<string>>`
> storage into a formally defined sparse semantic catalog. Introduce typed `IndexTuple`
> keys, a `Cell` value type (shared with Proposal 3's discriminated union), and three
> `FluxRule` enforcers. No new physics. No breaking change to any `@public` API in
> `src/index.ts`.
>
> **Proposals doc reference:** `docs/planning/UPT v0.70 - Proposals.md` §3.
> **Precedent / house style:** `docs/planning/v0.6.1-Design.md`.

---

## Goal

The current `UniversalTensor` class in `src/core/tensor.ts` stores catalog entries as
`Map<string, Set<string>>` where keys are freeform serialized strings and values are
sets of entity IDs. This is sparse — only populated slots exist — but it is not
*semantically indexed*. The axis axes (scale, force, symmetry, information, dimension,
topology) have no typed identity at the key level; they are collapsed into string
concatenation.

This proposal promotes the storage to a `Map<TupleKey, Cell>` where `TupleKey` is a
canonicalized string derived from a fully-typed `IndexTuple`, and `Cell` is the
Proposal 3 discriminated union (`LawEntry | BridgeEntry | EmergenceEntry`). Three
`FluxRule` checkers run at insertion time and emit warnings or errors when a cell
violates semantic consistency constraints.

The sprint succeeds if:

1. `UniversalTensor.add(cell: Cell)` replaces the three separate `addLaw / addBridge /
   addEmergence` entry points, accumulating cells into the typed `Map<TupleKey, Cell>`.
   The old methods become deprecated shims for the v0.7.x migration window.
2. All 42 existing v0.6 bridge entries in `BRIDGE_EQUATIONS` pass through the three
   flux rules without a rule violation — or any violations are documented as
   intentional exceptions before tagging.
3. `populatedCells()`, `populatedCount()`, `unpopulatedNeighborhoods()`, and
   `fluxDiagnostics()` are exposed and covered by tests.
4. Existing consumers of `BRIDGE_EQUATIONS` — `tests/bridges-index.test.ts`,
   `tests/bridges/dimensional-signature-catalog.test.ts`, and the 42+ per-bridge
   encoding tests — keep working without modification.
5. Full test suite stays ≥ the v0.6.1 baseline.

---

## Tag Decision

**Target: `v0.7.0` — minor release.** The addition of new public API (`add`,
`populatedCells`, `populatedCount`, `unpopulatedNeighborhoods`, `fluxDiagnostics`,
`FluxRule`, `Cell`) and the deprecation of `addLaw / addBridge / addEmergence` are
backward-compatible changes under SemVer (the old entry points remain callable). A
patch tag is inappropriate; a minor tag is correct.

## Architectural Decisions (locked)

### Decision #1 — Proposal 3 is a prerequisite, not a parallel track

The proposals doc (§3.3 sketch) shows `UniversalTensor` holding a `Map<TupleKey, Cell>`
where `Cell` is the typed discriminated union from Proposal 3. That coupling is real
and not optional: the flux rules in this proposal dispatch on `cell.kind`
(`'law' | 'bridge' | 'emergence'`) to classify diagonal vs. off-diagonal vs. multi-scale
placement. Without the discriminated union those dispatches cannot be typesafe.

**Dependency contract:**
- Proposal 3 must be **fully landed** (the `Cell` union defined, all 42 bridge entries
  re-expressed as typed cells) before this proposal's TDD cycles begin.
- Proposals 2 and 3 may be designed in parallel and planned in the same release, but
  their implementation ordering is: Proposal 3 first, then Proposal 2.
- If Proposal 3 slips to v0.8, this proposal slips with it. There is no independent
  fallback that preserves the flux rules' type safety.

**What Proposal 2 does NOT require from Proposal 1:**
Proposal 1 (Intelligent Index) introduces `UniversalIndex<Axis>` typed objects. The
proposals doc §3.3 sketch shows `IndexTuple` as a tuple of `UniversalIndex<...>` values.
That is the long-term form. However, for v0.7 Proposal 2 can function with a
lighter-weight `IndexTuple` that wraps the current string-enum axis values
(`PhysicalScale`, `Force`, `Symmetry`, etc. from `src/core/types.ts`). The `TupleKey`
canonicalization logic does not change between the string-enum form and the
branded-ID form that Proposal 1 would add. Proposal 2 should therefore define
`IndexTuple` as a typed record over the existing axis enums and include a migration
note in code that the `UniversalIndex<Axis>` substitution is the v0.8 upgrade path.

**Honest-clause:** The proposals doc §3.3 sketch presents `IndexTuple` and `Cell` as
if they are already defined. They are not present anywhere in `src/` as of v0.6.1.
Both types must be introduced from scratch — either in this proposal (Proposal 2) or
in Proposal 3. The recommended split: Proposal 3 introduces `Cell`; Proposal 2
introduces `IndexTuple` and `TupleKey`, and wires `UniversalTensor` to use both.

### Decision #2 — `BRIDGE_EQUATIONS` array is not replaced; it is read by a migration helper

`src/bridges/index.ts` is a 1,793-line array-of-objects catalog (`BRIDGE_EQUATIONS:
BridgeEquationEntry[]`). The catalog is `@public` and is re-exported from `src/index.ts`.
It is consumed by:

- `tests/bridges-index.test.ts` (17+ direct `BRIDGE_EQUATIONS` references)
- `tests/bridges/dimensional-signature-catalog.test.ts` (round-trip invariant)
- 42+ per-bridge encoding tests that import from `src/bridges/equations/be-NN-*.ts`
  and cross-reference `BRIDGE_EQUATIONS.find(e => e.id === NN)`

None of these consumers are touched by this proposal. `BRIDGE_EQUATIONS` stays as-is.
The migration path is a new module — `src/bridges/catalog-adapter.ts` — that reads
`BRIDGE_EQUATIONS` and emits typed `Cell` objects for insertion into `UniversalTensor`.
The adapter is separate from the catalog, keeping the catalog's file-edit footprint at
zero.

### Decision #3 — Flux rule violations: warning vs. error tier

The proposals doc §3.3 lists three rules. Their violation tiers for v0.7 are:

| Rule | v0.7 violation tier | v0.8 plan |
|------|---------------------|-----------|
| Dimensional consistency | **warning** | promote to error after full catalog audit |
| L/B/E type-coordinate matching | **error** | stays error |
| Causality direction | **warning** | promote to error after catalog audit |

Rationale for keeping two rules at warning level in v0.7:

- **Dimensional consistency**: 1 of the 42 bridge entries has a `null`
  `dimensional_signature` in `BRIDGE_EQUATIONS` (BE-15 per grep as of v0.6.1).
  Approximately 4 entries use non-standard regime strings (`'unknown'`, `'microscale'`,
  `'field-A'`, `'field-B'`, `'consciousness'`, `'holography'` — present in the
  `bridges` field across 30+ entries). Until a systematic encoding pass addresses these,
  a hard error on dimensional consistency would block catalog ingestion.
- **Causality direction**: the current `bridges` field is a `[string, string]` pair
  with freeform strings, not typed axis values. Causality direction requires
  interpreting `['quantum', 'classical']` as a specific ordering. This is ambiguous
  until Proposal 1's axis identity layer or at least an explicit ordering convention
  is established.

The L/B/E type-coordinate matching rule can be an error immediately because it
dispatches on `cell.kind` (a v0.7 typed field from Proposal 3), not on existing
freeform string content.

### Decision #4 — `unpopulatedNeighborhoods()` is informational, not blocking

The proposals doc §3.4 describes `unpopulatedNeighborhoods()` as a research roadmap
tool: "cells that are one-axis-removed from a populated cell are candidate areas for
new bridges." This is appealing but the full 6-axis address space has approximately
4 × 5 × 5 × 4 × N × M entries even at the smallest axis enum sizes, making the
neighborhood enumeration potentially large. For v0.7:

- `unpopulatedNeighborhoods()` returns only cells where exactly one axis differs from
  a populated cell.
- The `dimension` and `topology` axes are treated as integer wildcards — neighborhood
  candidates use the same integer value as the populated cell on those axes.
- The return type is `IndexTuple[]`, not a priority-ranked list. Ranking by
  dimensional-signature proximity is deferred to v0.8 or later.

### Decision #5 — `fluxDiagnostics()` returns a structured report, not console output

The proposals doc §3.3 sketch does not include `fluxDiagnostics()`, but the acceptance
criteria (§3.5) lists it. It must return a typed result, not a side-effecting logger,
so that callers can inspect violations programmatically. Return type:

```typescript
interface FluxDiagnostic {
  rule: string;           // rule name, e.g. 'dimensional-consistency'
  cell: Cell;             // the offending cell
  reason: string;         // human-readable explanation
  severity: 'warning' | 'error';
}

interface FluxReport {
  diagnostics: FluxDiagnostic[];
  errorCount: number;
  warningCount: number;
}
```

`UniversalTensor.fluxDiagnostics()` re-runs all rules over the current catalog and
returns a `FluxReport`. It is non-mutating. The `add()` method calls rules at
insertion time and throws on errors; `fluxDiagnostics()` is for post-hoc auditing.

### Decision #6 — No dense-tensor semantics; `Map` remains the storage primitive

The proposals doc §3.2 explicitly states: "UPT's sparse catalog is a TypeScript `Map`,
not anything MathTS ships." This is correct and confirmed by grep: as of v0.6.1,
`UniversalTensor` already uses `private readonly tensorData: Map<string, Set<string>>`
in `src/core/tensor.ts`. The proposal refines the key type and value type; the storage
primitive stays `Map`.

**Honest gap from the proposals doc:** §3.3 shows `UniversalTensor` with a
`private fluxRules: FluxRule[] = []` field and an `add(cell: Cell)` method. Neither
`FluxRule` nor the unified `add` method exist in the current `src/core/tensor.ts`. The
proposals doc sketch is aspirational, not a description of existing code. This design
treats it as the target state to implement.

### Decision #7 — Canonical `TupleKey` is a deterministic string serialization

The current `serializeIndices` private method in `src/core/tensor.ts` produces
`scale:quantum|force:gravitational|...` strings. The new `canonicalize(tuple: IndexTuple)`
function must produce a deterministic key regardless of insertion order. The existing
pipe-separated format is adequate; the function should sort parts alphabetically by
axis name before joining to ensure canonicalization. This is a rename-and-extract of
the existing method with a sort step added.

### Decision #8 — Adam+Eve adversarial review uses Opus subagents

Per v0.6.1 precedent (Decision #9): two parallel Opus subagents. Adam steel-mans;
Eve red-teams. Every Eve finding requires grep-verification. Findings go in
`docs/planning/v0.7-Proposal-2-Review-Findings.md`.

## Phase 1 — `IndexTuple`, `TupleKey`, and `canonicalize`

### Motivation

The current `serializeIndices` private method in `src/core/tensor.ts` collapses
`TensorIndices` (a partial record with optional fields) into a pipe-joined string.
There is no explicit `IndexTuple` type — the full 6-axis coordinate is implicit.
This phase introduces the typed 6-axis tuple and a pure-function canonicalizer
that all later phases and all flux rules depend on.

### Components

- **Task 1.1 — `src/core/index-tuple.ts`** (new module). Define:

  ```typescript
  // v0.7 IndexTuple — typed over existing axis enums.
  // Migration note: when Proposal 1 (Intelligent Index) lands in v0.8,
  // this record's value types will become UniversalIndex<Axis> objects.
  // The TupleKey serialization format is stable across both forms.
  export interface IndexTuple {
    readonly scale: PhysicalScale;
    readonly force: Force;
    readonly symmetry: Symmetry;
    readonly information: InformationMeasure;
    readonly dimension: number;
    readonly topology: number;
  }

  export type TupleKey = string & { readonly __brand: 'TupleKey' };

  export function canonicalize(tuple: IndexTuple): TupleKey {
    // Axes sorted alphabetically to guarantee key stability.
    return [
      `dim:${tuple.dimension}`,
      `force:${tuple.force}`,
      `info:${tuple.information}`,
      `scale:${tuple.scale}`,
      `sym:${tuple.symmetry}`,
      `topo:${tuple.topology}`,
    ].join('|') as TupleKey;
  }
  ```

  Note: `IndexTuple` requires all six axes to be populated (no optional fields).
  The existing `TensorIndices` (partial) is preserved as the external query type.
  Cells must carry a fully-specified coordinate; queries may be partial.

- **Task 1.2 — `extractTuple(cell: Cell): IndexTuple`** helper. Each `Cell` kind
  carries enough axis information to produce a full tuple. The extraction rules
  are specified in the Proposal 3 design and must be cross-checked there.
  **Honest gap:** the proposals doc does not specify the full extraction mapping.
  This is a design risk (see Risks §1).

- **Task 1.3 — Unit tests.** `tests/core/index-tuple.test.ts`: `canonicalize`
  is order-independent; round-trip recovers the original tuple; two tuples differing
  in one axis produce distinct keys; omitting any field is a TypeScript compile error.

### Deliverable

- 1 commit: `src/core/index-tuple.ts` + `tests/core/index-tuple.test.ts`.
- 1 commit: `extractTuple` helper (collocated with `Cell` in Proposal 3's module or
  in `src/core/index-tuple.ts`).

## Phase 2 — `FluxRule` interface and three v0.7 flux rules

### Motivation

This is the core of Proposal 2. Three `FluxRule` implementations enforce semantic
consistency at insertion time. Two emit warnings (collected in `fluxDiagnostics()`
only); one emits an error (thrown from `add()`).

### `FluxRule` interface

```typescript
// src/core/flux-rule.ts
export interface FluxRuleResult {
  ok: true;
} | {
  ok: false;
  reason: string;
  severity: 'warning' | 'error';
}

export interface FluxRule {
  readonly name: string;
  check(tuple: IndexTuple, cell: Cell): FluxRuleResult;
}
```

### Rule 1 — Dimensional consistency (warning)

**Name:** `'dimensional-consistency'`

**Logic:** If `cell.dimensional_signature` is non-null, verify that the signature
is consistent with the cell's `dimension` axis coordinate (the spatial/spacetime
dimension integer). Concretely: if the cell is at `dimension: 4` (4D spacetime),
the dimensional signature must not imply a 3D-only quantity (e.g., a pure 3-volume
[L³] in a 4D context would be flagged). In v0.7 the check is minimal: if
`dimensional_signature` is `null`, the rule emits a warning ("signature not yet
encoded for BE-NN"). If `dimensional_signature` is non-null, the check passes
(the full analytic consistency check — comparing the `Dimension` shape from
`src/dimensional/algebra.ts` against the axis integer — is deferred to v0.8 when
Proposal 3's typed cell AST is available for structured introspection).

**Violation tier:** warning.

**Honest-clause:** The proposals doc §3.3 states "A cell at coordinates including
`Axes.dimension.<d>` must have its `dimensional_signature` consistent with `d`." This
is the long-term form. As of v0.6.1, the `dimension` slot in `TensorIndices` is an
`integer` (not a named axis like `'spacetime-4d'`). The full check described in the
proposals doc cannot be implemented until axis identity (Proposal 1) maps integers to
named dimensional categories. The v0.7 implementation is therefore a narrower check:
non-null signature present → pass; null signature → warning with the bridge ID.

**v0.7 implementation:**

```typescript
// src/core/flux-rules/dimensional-consistency.ts
export const dimensionalConsistencyRule: FluxRule = {
  name: 'dimensional-consistency',
  check(tuple, cell) {
    if (cell.dimensional_signature === null) {
      return {
        ok: false,
        reason: `Cell ${cell.id} has no dimensional_signature; encoding pending.`,
        severity: 'warning',
      };
    }
    return { ok: true };
  },
};
```

### Rule 2 — L/B/E type-coordinate matching (error)

**Name:** `'lbe-coordinate-matching'`

**Logic:** Enforces the structural interpretation of the `Π = L + B + E`
decomposition at the key level:

- A `LawEntry` (kind `'law'`) must be *diagonal*: `from` and `to` scale slots are
  identical (or the entry has only a single scale regime, meaning it does not
  span two distinct scales). A `LawEntry` with `from !== to` is a structural
  error — laws are within-regime; cross-regime relations are bridges.
- A `BridgeEntry` (kind `'bridge'`) must be *off-diagonal*: `from` and `to` scale
  slots must differ. A `BridgeEntry` with `from === to` is a structural error.
- An `EmergenceEntry` (kind `'emergence'`) must span ≥2 substrate scales. An
  `EmergenceEntry` with only one substrate scale is a structural error (it would
  be a law, not an emergent phenomenon).

**Violation tier:** error (thrown from `add()`, not just collected in diagnostics).

**Cross-check against proposals doc:** §3.3 states "A `LawEntry` is diagonal in
regime ... A `BridgeEntry` is off-diagonal. An `EmergenceEntry` spans multiple
scale slots." This matches the logic above. The proposals doc does not specify what
"diagonal" means for the non-scale axes. This design treats *scale* as the primary
diagonality axis, consistent with `Π ∈ H_scale ⊗ ...` framing, and defers
multi-axis diagonality enforcement to v0.8.

### Rule 3 — Causality direction (warning)

**Name:** `'causality-direction'`

**Logic:** For `BridgeEntry` cells, the `from → to` scale ordering should be
physically plausible in a causal sense. The scale hierarchy is:
`quantum < mesoscopic < classical < cosmological`. A bridge flowing from a larger
scale to a smaller scale (e.g., `cosmological → quantum`) without an explicit
time-reversal or UV-complete annotation is unusual enough to warrant a warning.

**v0.7 implementation:**

```typescript
const SCALE_RANK: Record<PhysicalScale, number> = {
  quantum: 0, mesoscopic: 1, classical: 2, cosmological: 3,
};

export const causalityDirectionRule: FluxRule = {
  name: 'causality-direction',
  check(tuple, cell) {
    if (cell.kind !== 'bridge') return { ok: true };
    const fromRank = SCALE_RANK[cell.from.scale];
    const toRank   = SCALE_RANK[cell.to.scale];
    if (fromRank === undefined || toRank === undefined) return { ok: true };
    if (fromRank > toRank) {
      return {
        ok: false,
        reason: `Bridge ${cell.id}: from=${cell.from.scale} (rank ${fromRank}) > ` +
                `to=${cell.to.scale} (rank ${toRank}). If intentional, add ` +
                `timeReversalAnnotation: true to the BridgeEntry.`,
        severity: 'warning',
      };
    }
    return { ok: true };
  },
};
```

**Honest-clause:** 30 of the 42 entries in `BRIDGE_EQUATIONS` currently have
`bridges: ['unknown', 'unknown']`, meaning the causality rule would emit 0 warnings
on them — they lack enough axis information to evaluate. The rule is therefore mostly
inert for the current catalog. It becomes useful once Proposal 1 fills in typed axis
coordinates. This is not a defect in the rule; it reflects the catalog's current
state, and the warning output of the rule is itself diagnostic about encoding debt.

### Wiring into `UniversalTensor.add()`

```typescript
public add(cell: Cell): void {
  const tuple = extractTuple(cell);
  const violations: FluxDiagnostic[] = [];
  for (const rule of this.fluxRules) {
    const result = rule.check(tuple, cell);
    if (!result.ok) {
      const diag: FluxDiagnostic = {
        rule: rule.name, cell, reason: result.reason, severity: result.severity,
      };
      if (result.severity === 'error') {
        throw new FluxViolationError(rule.name, result.reason, cell.id);
      }
      violations.push(diag);
    }
  }
  this.pendingDiagnostics.push(...violations);
  this.cells.set(canonicalize(tuple), cell);
}
```

`pendingDiagnostics` is a private `FluxDiagnostic[]` accumulator cleared on each
`fluxDiagnostics()` call (or kept persistent — decision deferred to implementation).

### Components

- **Task 2.1** — `src/core/flux-rules/` directory with three rule files.
- **Task 2.2** — `FluxViolationError` class (extends `Error`) with `ruleName`, `cellId`.
- **Task 2.3** — Wire rules into `UniversalTensor` private `fluxRules` array.
- **Task 2.4** — Tests: `tests/core/flux-rules.test.ts`. Each rule tested with:
  - A passing cell (returns `{ ok: true }`).
  - A warning-level violation (warning rule, cell with null signature or reversed
    scale ordering).
  - An error-level violation (LBE rule, bridge with from === to).
  - Confirm `add()` throws on error; confirm warning goes into `fluxDiagnostics()`.

### Deliverable

- 1 commit: `src/core/flux-rules/` (three rules + `FluxViolationError`).
- 1 commit: `UniversalTensor.add()` implementation with rule wiring.
- 1 commit: `tests/core/flux-rules.test.ts`.

## Phase 3 — Query surface: `populatedCells`, `populatedCount`, `unpopulatedNeighborhoods`, `fluxDiagnostics`

### Motivation

The proposals doc §3.5 acceptance criteria require all four query methods. They are
straightforward to implement once the `Map<TupleKey, Cell>` storage is in place.

### Components

- **Task 3.1 — `populatedCells(): Cell[]`** Returns `Array.from(this.cells.values())`.
  O(n) in populated count.

- **Task 3.2 — `populatedCount(): number`** Returns `this.cells.size`. O(1).

- **Task 3.3 — `unpopulatedNeighborhoods(): IndexTuple[]`**
  For each populated cell, enumerate all tuples that differ in exactly one axis.
  Axis enumeration: scale (4 values), force (5 values), symmetry (5 values),
  information (4 values). The `dimension` and `topology` axes are integer-valued
  with no finite enumeration — for those axes, generate a ± 1 neighbor only if
  the integer falls in the range declared in the tensor's config. Return the set
  of tuples that are NOT already in `this.cells`. Deduplicate via a `Set<TupleKey>`.

- **Task 3.4 — `fluxDiagnostics(): FluxReport`** Re-runs all three rules over
  `populatedCells()` and returns a `FluxReport` (Decision #5 type). Non-mutating.
  Useful for a post-hoc audit after loading a catalog from `catalog-adapter.ts`.

- **Task 3.5 — Tests.** `tests/core/universal-tensor-v2.test.ts`: empty tensor has
  `populatedCount() === 0`; `populatedCells()` returns all added cells;
  `unpopulatedNeighborhoods()` excludes already-populated coordinates;
  `fluxDiagnostics()` returns correct warning count for null-signature cells;
  O(1) key lookup smoke (10,000 inserts, single retrieval).

### Deliverable

- 1 commit: four query methods + `FluxReport` type.
- 1 commit: `tests/core/universal-tensor-v2.test.ts`.

## Phase 4 — Migration adapter + deprecation shims

### Motivation

The 42-entry `BRIDGE_EQUATIONS` array is the existing catalog. Existing consumers
must continue to work. The migration path is:

1. A new `src/bridges/catalog-adapter.ts` that reads `BRIDGE_EQUATIONS` and emits
   `Cell[]` for insertion into `UniversalTensor`.
2. Deprecation shims: `addLaw`, `addBridge`, `addEmergence` stay callable but emit
   a `@deprecated` JSDoc tag and a console warning in dev mode.

### Components

- **Task 4.1 — `src/bridges/catalog-adapter.ts`** (new module, not public API).
  Exports `bridgeEntriesToCells(entries: BridgeEquationEntry[]): Cell[]`.
  Logic: for each entry, construct a `BridgeEntry` (kind `'bridge'`) using:
  - `id`: `String(entry.id)` (or `"BE-" + entry.id` — naming TBD, document in code).
  - `equation`: the existing `formula_latex` string (wrapping strategy — plain string
    vs. an AST stub — determined by Proposal 3's `Cell.equation` field type; if it
    is an `AstNode`, the adapter wraps in a `SymbolNode` stub with the LaTeX string
    as the symbol name, documenting the lossy encoding honestly).
  - `from` and `to`: parsed from `entry.bridges[0]` and `entry.bridges[1]`. For the
    30 entries with `'unknown'`, the adapter sets a sentinel `IndexCoordinate` with
    `scale: 'classical'` and an `encodingDebt: true` flag. The sentinel is intentional
    and documented — it's the axis encoding debt surfaced by the adapter.
  - `dimensional_signature`: `entry.dimensional_signature` (null passes through).
  - `confidence`: mapped from `entry.status` via:
    `established → 'established' | speculative → 'speculative' | highly-speculative → 'highly-speculative'`.

  **Design risk:** `'unknown'` bridges as sentinels will not satisfy the
  `causalityDirectionRule` (they use the same sentinel scale for from and to) and
  may not satisfy the `lbe-coordinate-matching` rule (from === to sentinel values).
  The adapter must mark these cells with a bypass flag recognized by the rules,
  or the rules must check for a sentinel before evaluating. Preferred approach:
  add an optional `encodingDebt: true` field to `BridgeEntry` that causes all flux
  rules to emit warnings (not errors) for that cell. This is the honest solution:
  the catalog has encoding debt, and the system surfaces it rather than hiding it.

- **Task 4.2 — Deprecation shims for `addLaw`, `addBridge`, `addEmergence`.**
  Each gets a `@deprecated — use add(cell: Cell) instead` JSDoc tag and a guarded
  `console.warn(...)` in dev builds. Shims internally call `add()` with a typed cell
  construction. Callers do not break; they just see the deprecation signal.

- **Task 4.3 — Migration smoke test.** `tests/bridges/catalog-adapter.test.ts`:
  `bridgeEntriesToCells(BRIDGE_EQUATIONS)` returns 42 cells, all with
  `kind === 'bridge'`; inserting all 42 does not throw; `fluxDiagnostics().warningCount`
  is pinned as a snapshot to detect catalog drift.

### Deliverable

- 1 commit: `src/bridges/catalog-adapter.ts` + `tests/bridges/catalog-adapter.test.ts`.
- 1 commit: deprecation shims on `addLaw`, `addBridge`, `addEmergence`.
- 1 commit: snapshot of `fluxDiagnostics()` warning count against the v0.6.1 catalog.

**Adam review targets:**

## Risks

1. **`extractTuple(cell: Cell)` extraction mapping is underspecified.** The proposals
   doc does not define how each `Cell` kind maps to a full 6-field `IndexTuple`. A
   `BridgeEntry` has explicit `from` and `to` coordinates; which one becomes the
   tuple? This design proposes using `from` as the primary coordinate (the "source"
   cell) — but that means a bridge between quantum and classical occupies a
   *quantum*-keyed cell, not a combined cell. This is a design choice with
   consequences for `getBridgeCellContents()` semantics. **Mitigation:** Pin the
   mapping explicitly in `src/core/index-tuple.ts` with a comment, and add a test
   that verifies a bridge is findable by its `from` coordinate.

2. **Multi-scale `LawEntry` breaks the diagonal constraint.** The current `addLaw`
   method accepts `law.scales: PhysicalScale[]` — a law can be declared at multiple
   scales simultaneously (`scales: ['quantum', 'classical']`). The `lbe-coordinate-matching`
   rule as designed requires a `LawEntry` to have a single scale regime. A multi-scale
   law would fail the rule. **Mitigation:** The rule should allow multi-scale laws
   with a warning, not an error. This modifies Decision #3's "error" classification
   for that rule. Or, multi-scale laws are represented as N separate `LawEntry`
   cells (one per scale), which is the cleaner semantic model. Decide in Phase 2's
   TDD and document the choice.

3. **`BRIDGE_EQUATIONS.bridges` freeform strings don't map cleanly to `PhysicalScale`
   enum values.** Of the 42 entries, only a handful use `PhysicalScale`-recognizable
   values (`'quantum'`, `'classical'`, `'cosmological'`). The rest use freeform strings
   like `'microscale'`, `'information'`, `'physical'`, `'consciousness'`,
   `'holography'`, `'field-A'`, `'field-B'`, `'gravity'`, `'dark-sector'`, and 30
   `'unknown'`. The catalog-adapter must handle all of these without throwing.
   **Mitigation:** Map unrecognized strings to a sentinel `'classical'` with an
   `encodingDebt` flag, and document the mapping table in the adapter module's header.

4. **Proposals doc code sketches use `UniversalIndex<Axis>` objects in `IndexTuple`
   but those don't exist yet.** The proposals doc §3.3 sketch shows `IndexTuple` as
   a tuple of `UniversalIndex<'scale'>` etc. That type is introduced by Proposal 1,
   which may or may not land in v0.7 before this proposal. This design uses the
   string-enum form instead and documents the upgrade path. **UNVERIFIED:** whether
   Proposal 1 will land before or after Proposal 2 in v0.7 is not yet decided. If
   Proposal 1 lands first, the `IndexTuple` definition here should be revised to
   use `UniversalIndex<Axis>` fields.

5. **`fluxDiagnostics()` vs. `pendingDiagnostics` mismatch.** If `add()` accumulates
   warnings in `pendingDiagnostics` and `fluxDiagnostics()` re-runs rules from
   scratch, the two sources may diverge (e.g., if a cell is removed between `add()`
   and `fluxDiagnostics()` calls). **Mitigation:** Use `fluxDiagnostics()` as the
   single source of truth (re-run always); discard the `pendingDiagnostics`
   accumulator idea. The only cost is O(n × rules) re-evaluation, which is
   negligible at catalog sizes ≤ 10,000.

## Non-goals

Explicitly NOT in scope for this proposal:

- **Any change to `BRIDGE_EQUATIONS`** or `src/bridges/index.ts`. The catalog is
  read-only from this proposal's perspective.
- **Any change to per-bridge encoding tests** (`tests/bridges/be-NN-*.test.ts`) or
  the dimensional-signature catalog test. Those tests pin the existing `BRIDGE_EQUATIONS`
  array; they are unaffected by this proposal.
- **Implementing Proposal 1's `UniversalIndex<Axis>` type.** This proposal uses
  string enums. Proposal 1 is a separate design track.
- **Promoting warning rules to errors.** That is explicitly a v0.8 milestone, gated
  on a catalog audit pass.
- **`unpopulatedNeighborhoods()` priority ranking.** Informational list only in v0.7.
- **Any bridge physics re-encoding or status changes.** Same constraint as v0.6.1
  Decision #7.
- **Publishing to npm.** The publish is still blocked on `NPM_TOKEN` rotation
  (carried from v0.6.0/v0.6.1).
- **MathTS upstream changes.** This proposal is UPT-only; no MathTS PRs are needed
  or planned.
