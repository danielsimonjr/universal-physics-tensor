## 1. Context

UPT v0.1.0 ([commit `b1eeff6`, tag `v0.1.0`, 2026-05-12](https://github.com/danielsimonjr/universal-physics-tensor/releases/tag/v0.1.0)) closed the Wave A → Wave Z arc with **40 / 40 AST encodings**, 1,161 tests, status distribution 6/31/3/0 (established / speculative / highly-speculative / invalid). The scalar-AST scope is exhausted; further encoding rigor requires extending the AST grammar.

The validator's source (`src/dimensional/validator.ts:5-6`) explicitly notes the v0.1.0 gap:

> "This MVP does NOT track tensor index structure (rank, contractions). Bridge Eq 17's index-rank mismatch from the spec cannot be caught here. Tier 4.5 follow-up — see README."

Bridges with tensor structure are currently encoded via the **typed-stub idiom**: a single symbol named `T_torsion_squared` whose `dim` is the hand-computed dimension of the contracted scalar `T_λμν T^λμν`. Honest about the limitation (every typed-stub is flagged in `notes`), but loses the index structure entirely. The validator cannot verify that the contraction is well-formed; it can only verify that the hand-computed dimension matches the expected result.

v0.2.0 adds the **algebra layer of Riemannian geometry**: variance-typed index labels and the Einstein summation contraction rule. Metric, raise/lower, covariant derivative, and curvature are explicitly deferred to v0.3.0+.

## 2. Scope

### In scope

1. **Spec module**: `docs/specification/Part-VII-Tensor-Algebra.md`. Defines the grammar, contraction rules, dimensional bookkeeping rules, and v0.2.0 limitations. Drift-tested against the implementation.
2. **AST extension**: two new node types — `tensor-symbol` (a tensor with named, variance-typed indices) and `tensor-product` (the Einstein-summation product, contracting all matching upper/lower pairs across operands).
3. **Validator extension**: enriched `ValidationResult` with a `freeIndices` map; recursive walker for the new nodes; strict-boundary rules for how `op` interacts with tensor operands; new error types (`IndexLabelCollisionError`, `VarianceMismatchError`, `RepeatedDummyLabelError`, `TensorInScalarOpError`).
4. **Drift guard**: `tests/dimensional/tensor-spec-vs-impl.test.ts`, analog to existing `spec-vs-index.test.ts`. Every TENSOR-RULE marker in the spec has a matching implementation test; both directions enforced.
5. **Per-bridge structural rewrites**: BE-17 (remove `T_torsion_squared` stub), plus structural encoding for BE-33 (TeVeS tensor invariants), BE-36 (Bekenstein-Hawking on ER bridge), and BE-43 (Wheeler-Feynman EM tensor). Daniel may keep one or two as stubs if literature gaps make structural encoding premature — honest-claude posture preserved.
6. **R4 polish**: 16 bridges with prose-only concerns in `notes` get structured `KnownIssue[]` arrays.
7. **Doc refresh**: `Bridge-Remediation-Plan.md`, `Development-Plan.md`, `Implementation-Plan.md` updated to reflect the post-Wave-Z state (no claims of "2 invalid"; "40 / 40 encoded" everywhere relevant).

### Explicitly out of scope (deferred to v0.3.0+)

- **Metric tensor** `g_μν`, `g^μν` — deferred to v0.3.0 (the "metric layer")
- **Raise/lower** `T^μ_ν = g_νλ T^μλ` — deferred to v0.3.0
- **Covariant derivative** `∇_μ` — deferred to v0.3.0 or v0.4.0 (the "connection layer")
- **Curvature tensors** Riemann, Ricci, scalar, Bianchi identities — deferred to v0.4.0+ (the "curvature layer")
- **Tensor-with-component-dependent-dimensions** (e.g., Faraday `F_μν` mixing electric and magnetic components with different SI dimensions). v0.2.0 assumes uniform component dimension per tensor-symbol; the spec documents this as a known limitation revisited with the metric.
- **Tensor-valued integrals/derivatives** — `integral` and `derivative` AST nodes remain scalar-only
- **Tensor exponentiation** `T^2` (ambiguous in physics literature; explicit contraction required)
- **Property-based testing** as a new paradigm (existing 1,161 deterministic tests are sufficient; revisit for v0.3.0 metric layer)
- **npm publish prep**, examples directory, contributor guide — deferred to a later release once API stabilizes through use

## 3. Approach: spec-first, minimal runtime

**Both reasoning models converged on the same verdict with high confidence:** spec-first methodology (matching UPT's existing pattern in Part-I through Part-VI) with the minimal-AST implementation. Specifically:

1. Write `Part-VII-Tensor-Algebra.md` first. Define the grammar formally. Define the contraction rules. Document the v0.2.0 limitations (uniform component dimension, no metric, etc.).
2. Implement the minimal runtime AST extension matching the spec.
3. Add a drift guard that enforces non-divergence in both directions.

**Rejected alternative**: type-level encoding via TypeScript conditional types and template literal types (`TensorExpr<['μ','ν'], ['α','β']>`). Both reasoners called this "a siren song" for a single-developer library — significant complexity, slow compile times, marginal benefit given the existing test coverage. The structural rigor lives in the runtime validator; TypeScript types stay simple.

**Gemini's clarifying principle, adopted:** *"The primary consumer of the raw AST is the system itself, not the end-user."* The AST stays minimal and structurally precise; user-facing ergonomics (e.g., `scale(scalar, tensor)`) live in a thin API helper layer that constructs the underlying nodes.

## 4. AST extension

### Existing node types (v0.1.0, unchanged)

```typescript
| { kind: 'symbol'; name: string; dim: Dimension }
| { kind: 'op'; op: '+'|'-'|'*'|'/'|'^'; args: ExprNode[] }
| { kind: 'integral'; over: ExprNode; integrand: ExprNode }
| { kind: 'derivative'; of: ExprNode; wrt: ExprNode }
```

### New node types (v0.2.0)

```typescript
| { kind: 'tensor-symbol';
    name: string;
    indices: ReadonlyArray<{ label: string; variance: 'upper' | 'lower' }>;
    dim: Dimension }
| { kind: 'tensor-product'; args: ExprNode[] }
```

**`tensor-symbol`** represents a named tensor with explicit indices. The `dim` field is the **per-component dimension** — every component is assumed to share this dimension (v0.2.0 limitation; see § Non-goals). Indices appear in declaration order; the validator does not reorder them. Repeated labels within a single `tensor-symbol`'s indices array are rejected at validation time.

**`tensor-product`** represents the generalized Einstein-summation product. The validator:

1. Recursively validates each `args[i]`, obtaining `{ dim_i, freeIndices_i }`.
2. Multiplies the dimensions: `dim = multiply(multiply(... dim_0, dim_1) ...)`.
3. Unions the `freeIndices` maps (summing the `upper` and `lower` counts per label across all args).
4. For each label where both `upper > 0` and `lower > 0`, performs Einstein contraction: decrements both counts by `min(upper, lower)`.
5. Rejects any label whose total post-contraction count exceeds 2 (label collision; the user must rename one of the indices).

The result of `tensor-product` is a `{ dim, freeIndices }` pair. If `freeIndices` ends up empty (all indices contracted away), the result is a scalar and can slot directly into `op '+'`, `op '*'`, etc.

## 5. Validator architecture

### Enriched `ValidationResult`

```typescript
export interface ValidationResult {
  ok: boolean;
  inferredDimension: Dimension | null;
  freeIndices: Map<string, { upper: number; lower: number }>;  // NEW
  violations: Violation[];
}
```

**`freeIndices` invariants:**
- For a scalar expression: empty map (or absent entries).
- For a tensor expression with k free indices: each label has exactly one non-zero count (either `upper: 1, lower: 0` or `upper: 0, lower: 1`). Total non-zero entries = k.
- An invalid construct like `T^μ_μ_μ` (label used three times in one tensor-symbol) is rejected with `RepeatedDummyLabelError` before contraction.

### Per-node validation rules

| Node kind | Free-indices rule | Dim rule | Errors raised |
|---|---|---|---|
| `symbol` | Always empty | `node.dim` | — |
| `tensor-symbol` | Built from `node.indices`; reject if any label repeats | `node.dim` | `RepeatedDummyLabelError` |
| `op '+' / '-'` | All args must share same map | All args must share same dim | `DimensionMismatchError`, `FreeIndexMismatchError` |
| `op '*' / '/'` | All args MUST have empty map | Multiply / divide | `TensorInScalarOpError` |
| `op '^'` | Base must have empty map; exponent must be DIMENSIONLESS scalar | `power(base.dim, exponent.value)` | `TensorInScalarOpError`, `NonScalarExponentError` |
| `integral` | Integrand must have empty map (scalar-only in v0.2.0) | `multiply(integrand.dim, over.dim)` | `TensorIntegralError` (deferred feature) |
| `derivative` | Both sides must have empty map (scalar-only) | `divide(of.dim, wrt.dim)` | `TensorDerivativeError` (deferred feature) |
| `tensor-product` | Union args' maps; contract matching pairs; reject label collisions (count > 2) | Multiply args' dims | `IndexLabelCollisionError`, `VarianceMismatchError` |

### Strict-boundary rationale

The boundary `op` is strictly scalar / `tensor-product` is the only multiplicative path for tensors was confirmed by both reasoners. Auto-promoting `op '*'` to tensor-aware behavior would introduce semantic ambiguity at the core of the AST. The cost — slightly more verbose AST construction for scalar-times-tensor expressions — is absorbed by helper functions in the user-facing API layer.

## 6. User-facing API

```typescript
// src/dimensional/tensor.ts

/** Construct a tensor symbol. */
export function tsym(
  name: string,
  indices: ReadonlyArray<{ label: string; variance: 'upper' | 'lower' }>,
  dim: Dimension
): ExprNode;

/** Scale a tensor by a scalar coefficient. Returns a tensor-product. */
export function scale(scalar: ExprNode, tensor: ExprNode): ExprNode;

/** Contract any number of tensors. Returns a tensor-product. */
export function contract(...tensors: ExprNode[]): ExprNode;

/** Construct a tensor sum (uses op '+' with strict free-index matching). */
export function tsum(...tensors: ExprNode[]): ExprNode;
```

These are sugar for AST construction; the validator sees only the underlying nodes. The helpers exist in `src/dimensional/tensor.ts` so bridge encoders can import them alongside the scalar helpers (`sym`, `op`) from the existing modules.

## 7. Worked example: BE-17 before / after

### Before (v0.1.0 typed-stub)

```typescript
// S²_spin = (c⁴/(8πG))² · T_torsion_squared
const T_torsion_squared = sym('T_torsion_squared',
  { L: -4, M: 0, T: 2, I: 0, Theta: 0, N: 0, J: 0 }); // hand-computed

const BE17_RHS = {
  kind: 'op', op: '*',
  args: [coupling_prefactor_squared, T_torsion_squared],
};
```

The validator infers dim `[M²·L⁻²·T⁻²]` but never sees that the stub represents `T_λμν T^λμν` — the rank, contraction pairs, and variance structure are all opaque.

### After (v0.2.0 structural)

```typescript
const T_lower = tsym('T_torsion',
  [{ label: 'λ', variance: 'lower' },
   { label: 'μ', variance: 'lower' },
   { label: 'ν', variance: 'lower' }],
  { L: -2, M: 0, T: 1, I: 0, Theta: 0, N: 0, J: 0 }); // component dim

const T_upper = tsym('T_torsion',
  [{ label: 'λ', variance: 'upper' },
   { label: 'μ', variance: 'upper' },
   { label: 'ν', variance: 'upper' }],
  { L: -2, M: 0, T: 1, I: 0, Theta: 0, N: 0, J: 0 });

const T_contracted = contract(T_lower, T_upper);
// validator: dim=[T²·L⁻⁴], freeIndices=empty (λ, μ, ν all contracted)

const BE17_RHS = contract(coupling_prefactor_squared, T_contracted);
// validator: dim=[M²·L⁻²·T⁻²], freeIndices=empty
```

The validator now **structurally verifies**:
- Three matching upper/lower pairs (λ, μ, ν all dummy)
- Final expression has empty `freeIndices` (true scalar)
- Component dimension composes to `[T²·L⁻⁴]` for the contraction
- Multiplying by `[M²·L²·T⁻⁴]` coupling yields `[M²·L⁻²·T⁻²]` ✓

The `T_torsion_squared` typed-stub disappears. The encoding matches the literature's tensor structure directly. If a future spec edit mis-pairs the indices (say, accidentally puts μ as upper in both factors), the validator catches it; the v0.1.0 stub couldn't.

| `tests/dimensional/tensor-spec-vs-impl.test.ts` | **Drift guard** — every TENSOR-RULE marker in Part-VII has a matching test, and vice versa |
| `tests/bridges/be-17-structural.test.ts` | BE-17 round-trips through structural form; existing be-17-encoding.test.ts continues to pass |
| `tests/bridges/be-33-structural.test.ts`, `be-36-structural.test.ts`, `be-43-structural.test.ts` | One per newly-structurally-encoded bridge |

**Total suite size post-v0.2.0: ~1,250 tests across ~75 files.**

### Drift guard mechanism

Part-VII embeds structured markers:

```markdown
<!-- TENSOR-RULE: op-star-rejects-tensors -->
The validator rejects `op '*'` with any argument whose freeIndices map is non-empty,
emitting `TensorInScalarOpError`.
```

The test parses Part-VII, extracts every `<!-- TENSOR-RULE: <id> -->` marker, and asserts:
- Every rule marker has a matching test (test name or test-id metadata references the rule).
- Every test that claims a rule reference points to a real rule marker.
- The test for each rule actually exercises the documented behavior (positive + negative cases).

A rule added to the spec without a test → fail. A test referencing a non-existent rule → fail.

### Performance

Validator recursion is O(N · F²) for tensor expressions, where N is node count and F is free-index count per subtree (≤ 4 in physics, usually 1-2). With pessimistic constants this stays well under the 23.6 s wall-clock budget the existing 1,161 tests consume. Re-benchmark at end of v0.2.0; flag any single test exceeding 100 ms.

## 12. Future direction (v0.3.0+)

This design preserves forward-compatibility with the next horizons:

- **v0.3.0: Metric layer.** Add `g_μν` and `g^μν` as named tensor-symbols. Add a `raise` / `lower` helper (or new AST node) that applies the metric. The Faraday tensor `F_μν` (mixed E/B components) is revisited; v0.2.0's uniform-component-dim assumption may need extension to "per-component-pair dim" via a more nuanced tensor-symbol shape.
- **v0.3.0 numerical evaluation: pair with mathjs.** Add a numerical-contraction backend that maps `tensor-symbol` to mathjs `Matrix` / `Tensor` types and executes the Einstein summation numerically. This is where v0.2.0's structural rigor pays off: the AST already encodes which indices contract, so the mathjs backend can mechanically lower to `math.multiply` + `math.trace` + `math.einstein` (the latter via custom helper if mathjs doesn't expose a direct `einsum`). The v0.2.0 API helpers (`tsym`, `scale`, `contract`) should compose cleanly with mathjs types — verify forward-compat during v0.2.0 design reviews.
- **v0.3.0 or v0.4.0: Connection layer.** Add Christoffel symbols `Γ^λ_μν` and covariant derivative `∇_μ`. Likely a new AST node `covariant-derivative` paralleling the existing `derivative`.
- **v0.4.0: Curvature layer.** Riemann tensor `R^μ_νρσ`, Ricci tensor, Ricci scalar, Bianchi identities.
- **v0.4.0+: Visualization via threejs.** A separate repo per the Future-Production-Hardening parking lot. Consumes UPT's structured tensor encoding as a JSON / typed-API export. Renders 6D tensor slices, projections, equation browser, interactive parameter adjustment. The v0.2.0 structural encoding (free-indices, variance, rank) gives threejs concrete geometric structure to visualize — vs the v0.1.0 typed-stubs which are opaque scalars.

**The v0.2.0 design choice that most affects v0.3.0+ readiness:** keeping the AST minimal (no type-level encoding) means future extensions can add new node kinds without refactoring TypeScript types. Adding `metric`, `covariant-derivative`, or `riemann-tensor` is a discriminated-union addition, not a type-system refactor.

## 13. Risks and open questions

### Risks both reasoners flagged

- **Index label namespace ambiguity in nested expressions.** `(A^μ_ν B^ν_α) + C^μ_α` requires the validator to scope `ν` to within the parenthesis (it's a dummy local to the product). The recursive walker handles this naturally if implemented correctly, but it's a class of bug to watch for in week 4 of implementation.
- **The "uniform component dimension" assumption is leaky.** Faraday tensor `F_μν` has electric-field components and magnetic-field components with different SI dimensions in `[V/m]` vs `[T]`. v0.2.0 documents this as a known limitation; v0.3.0 may need a `per-pair-dim` extension to `tensor-symbol`.
- **Multi-pair contraction edge cases.** Expressions like `R^α_β R_α^β` (full self-contraction) need careful walker implementation to handle both pairs simultaneously. Gemini specifically flagged this when reviewing the `{ contract, t1, t2 }` shape; the chosen `{ tensor-product, args: [...] }` shape sidesteps it.

### Open questions for review

1. **Should `tensor-product` enforce a canonical ordering of free indices in its output `freeIndices` map?** (Pro: deterministic test comparison. Con: arbitrary convention.) Suggest deferring decision until first concrete bug emerges.
2. **Should `tensor-symbol` allow zero indices** (a rank-0 tensor, i.e., a scalar via the tensor API)? Lets the API treat scalars and tensors uniformly. Suggest **yes** for v0.2.0; the validator's freeIndices map handles the empty case correctly already.
3. **Should `contract(...)` and `scale(...)` API helpers verify argument shape at call time** (TypeScript type guard) or defer to the validator? Suggest defer-to-validator for v0.2.0; reconsider after first ergonomic complaint.
