## Goal

A physicist authoring or reviewing a bridge equation today must read a
TypeScript AST module (`src/bridges/equations/be-NN-*.ts`) — a format that
requires knowing UPT's internal node types, dimensional algebra, and
`ExprNode` union. The goal of this proposal is to lower that barrier by
re-expressing each bridge as a `.mtsw` reactive workbook: a YAML text file
with prose context, metadata, build code, and test cells that a physicist
can read, edit, and validate without understanding UPT's TypeScript internals.

The sprint succeeds if:

1. All 42 bridges have a corresponding `.mtsw` workbook that builds and
   validates end-to-end via `mtsw run`.
2. The existing round-trip invariant — every bridge's encoded AST round-trips
   through the dimensional analyzer back to its registered
   `dimensional_signature` — continues to be pinned by
   `tests/bridges/dimensional-signature-catalog.test.ts` with no test
   changes required.
3. The existing per-bridge encoding tests (74 files in `tests/bridges/`) remain
   green against the TypeScript modules, which remain the source-of-truth for
   the runtime catalog.
4. CI adds a `workbooks:validate` step that runs `mtsw validate` on every
   `.mtsw` file; the step must pass on every commit.
5. A "Authoring a bridge: workbook walkthrough" tutorial ships in
   `docs/guides/workbook-authoring.md`.

## Dependency Precondition — Honest Audit

**`@danielsimonjr/mathts-workbook` is NOT in `package.json` as of v0.6.1.**

Inspection of `package.json` confirmed: `optionalDependencies` lists only
`@danielsimonjr/mathts-tensor` and `@danielsimonjr/mathts-autograd`.
`mathts-workbook` appears neither in `optionalDependencies`, `devDependencies`,
nor `peerDependencies`. It is not installed in `node_modules/@danielsimonjr/`.

This is the same precondition that bit v0.6.1: `mathts-tensor` was not
installed in the build environment and required an ambient `.d.ts` shim before
the optional-import path would compile. Workbook adds the same class of risk.

**Resolution before any code work begins:**

- Add `@danielsimonjr/mathts-workbook` to `devDependencies` in `package.json`.
  It is an authoring and CI tool, not a runtime dependency shipped to UPT
  consumers — see §Dependency Contract below.
- Verify `npm install` resolves the package from the npm registry.
- Confirm `mtsw` CLI is available as `npx mtsw` after install.
- If the package is not yet published to the public npm registry (it is a
  sister-repo package), the precondition blocks this entire proposal until it
  is published or a local `file:` path is used. **Document the resolution in
  the implementation plan's Task 0.**

Any plan that skips this verification gate and proceeds to workbook authoring
will hit the same ambient-shim debt v0.6.1 hit on `mathts-tensor`.

## Architectural Decisions (locked)

### Decision #1 — TypeScript modules remain the source-of-truth for the runtime catalog

`.mtsw` workbooks are the **authoring and documentation format**; they are NOT
the runtime source-of-truth. The data flow is:

```
.mtsw workbook
  └─ code cell (hand-maintained TypeScript-compatible DSL)
       └─ references / mirrors the TS module in src/bridges/equations/be-NN-*.ts
              └─ imported by src/bridges/index.ts (BRIDGE_EQUATIONS registry)
                     └─ consumed by UPT public API at runtime
```

This keeps the existing test suite intact with zero changes:
- `tests/bridges/dimensional-signature-catalog.test.ts` continues to import
  from `src/bridges/equations/*.ts` directly.
- `tests/bridges/be-NN-*.test.ts` (74 files) continue to import from the
  same TS modules.
- No test file needs to know workbooks exist.

The alternative — making `.mtsw` workbooks the source-of-truth and generating
the TS modules from them — would require a code-generation pipeline, break the
test import graph, and introduce a build-order dependency that doesn't exist
today. That scope is v1.0+ at the earliest, if ever.

### Decision #2 — Workbooks live in `docs/bridges/workbooks/`

Three candidate locations were considered:

| Location | Pro | Con |
|---|---|---|
| `src/bridges/equations/` (next to TS) | Colocation | Pollutes the source tree; confuses the dep-graph generator |
| `docs/bridges/workbooks/` | Clearly doc-layer; not in `files` publish manifest | One level removed from the TS modules |
| `bridges/` (new top-level dir) | Peer to `src/` and `docs/` | Yet another top-level dir; doesn't signal "docs" |

**Decision: `docs/bridges/workbooks/`**. Rationale:

- Workbooks are documentation artifacts (physics prose + validation tests
  for human readers), not runtime sources. They belong in `docs/`.
- Not in the `files` array in `package.json`, so they don't inflate the
  published npm package.
- The `docs:deps` generator's `--include-tests` flag already walks `tests/`;
  adding a `--include-docs` flag or a YAML-aware exception can exclude
  `docs/bridges/workbooks/*.mtsw` from unused-file analysis without
  touching the dep-graph logic.
- Path is stable across refactors — moving a TS module doesn't invalidate
  the workbook path convention.

Naming convention: `docs/bridges/workbooks/be-NN-<slug>.mtsw`, mirroring the
TS module slug (e.g., `be-37-shapiro-delay.mtsw` for
`src/bridges/equations/be-37-shapiro-delay.ts`).

### Decision #3 — `mathts-workbook` is a devDependency only

UPT consumers (`npm install universal-physics-tensor`) get no exposure to
`mathts-workbook`. The package is only needed for:

- Bridge authoring (local workbook editing with live dimensional feedback).
- CI validation (`mtsw validate` in the `workbooks:validate` npm script).
- The SymPy export tool (runs `mtsw run` as a preprocessing step).

Add to `devDependencies`, not `optionalDependencies`. Rationale: unlike
`mathts-tensor` and `mathts-autograd` (which are optional runtime backends
that UPT consumers might want to activate), workbook tooling is purely a
maintainer concern. There is no user story in which a downstream application
needs `@danielsimonjr/mathts-workbook` at runtime to consume the UPT API.

The `"files"` array in `package.json` already excludes `docs/` from the
published package. No change needed there.

### Decision #4 — The `.mtsw` skeleton for a bridge has exactly four cells in fixed order

Every bridge workbook uses the same cell ordering:

1. `markdown` — prose physics context, references, honest-claude scope notes.
2. `data` — structured metadata (coordinates, parameters, dimensional signature, confidence).
3. `code` — imports and re-exports the bridge's existing exports from the TS module.
4. `test` — dimensional self-check and at least one numerical or limit check.

This ordering is mandatory, not advisory. Rationale: the `mtsw graph` CLI
produces a dependency graph using `depends_on` annotations; a fixed ordering
makes the graph layout predictable across all 42 workbooks.

### Decision #5 — Migration strategy: hand-authored from existing TS modules

All 42 bridges are migrated by **hand-authoring** the workbook from the
existing TS module, not by an automated transformer. Rationale:

- Each bridge module's docstring already contains prose physics context,
  dimensional analysis commentary, references, and honest-claude scope notes.
  That prose must be curated into the `markdown` cell, not mechanically
  extracted — the docstrings contain embedded code comments, formatting
  artifacts, and internal cross-references that would require per-bridge
  human judgment to clean up anyway.
- The `data` cell's YAML metadata cannot be auto-generated reliably: the
  `dimensional_signature` string, `confidence` level, and `bridges` field
  (from/to coordinates) must be cross-checked against `BRIDGE_EQUATIONS` in
  `src/bridges/index.ts` and the BRIDGE-PHYSICS-AUDIT findings. Several
  entries have contested metadata (9 `unknown <-> unknown` bridge fields;
  status miscalibrations per the audit §5).
- An automated transformer would need to parse TypeScript AST and
  re-emit YAML — a non-trivial tool that would itself need tests. For 42
  bridges at ~30-60 minutes per workbook, the total hand-authoring effort is
  roughly one sprint (≈ 2 weeks), which matches the Proposals doc §7 estimate.

**Batch order:** start with the 8 `established` bridges first
(BE-11, BE-14, BE-16, BE-19, BE-20, BE-29, BE-51, BE-52), then proceed
through the 31 `speculative` and 3 `highly-speculative` entries. Rationale:
the established bridges have the cleanest physics, the most complete TS
modules, and the best numerical evaluators — they are the right set to
validate the workbook skeleton convention before applying it at scale.

### Decision #6 — Code cells reference TS module exports; they do not re-implement ASTs

The `code` cell in each workbook does not reproduce the bridge's `ExprNode`
AST. It imports and re-exports the named exports from the corresponding TS
module:

```yaml
- id: build
  kind: code
  content: |
    // Re-export from the canonical TS module.
    // The AST and evaluator live in src/bridges/equations/be-37-shapiro-delay.ts.
    import {
      BE37_SHAPIRO_DELAY_RHS,
      BE37_SHAPIRO_DELAY_LHS,
      evaluateShapiroDelay,
      validateBE37Dimensions,
    } from 'universal-physics-tensor/bridges/equations/be-37-shapiro-delay';

    export { BE37_SHAPIRO_DELAY_RHS, BE37_SHAPIRO_DELAY_LHS,
             evaluateShapiroDelay, validateBE37Dimensions };
```

This approach:
- Prevents duplication of the AST (single source of truth in the TS module).
- Lets the `test` cell call the real evaluators and validators, not stubs.
- Keeps the workbook thin: a prose + metadata + thin import layer + test layer.
- Avoids the risk of workbook ASTs drifting from TS module ASTs.

The alternative — embedding the full AST in YAML — would create a parallel
definition that would immediately begin drifting from the TS source of truth.
That path is explicitly rejected.

### Decision #7 — The `test` cell is mandatory and must include dimensional validation

Every bridge workbook's `test` cell must:

1. Call the bridge's dimensional self-check function (e.g.,
   `validateBE37Dimensions()`) and assert `ok: true`.
2. If the bridge has a numerical evaluator (e.g., `evaluateShapiroDelay()`),
   call it with at least one canonical input and assert the result is within
   expected bounds.
3. If the bridge has a known analytic limit (e.g., BE-37's round-trip
   Shapiro delay for the Sun at 1 AU), check the evaluator against the
   published approximate value.

The `test` cell is the workbook's contribution to physics correctness:
it exercises the bridge with a physicist-readable scenario, annotated with
the reference it's checked against.

Bridges that currently lack a numerical evaluator (many of the 31 speculative
entries have only AST encoding, no `evaluateXxx()` function) are an exception:
their `test` cell must at minimum call the dimensional self-check.

### Decision #8 — CI adds `workbooks:validate` and `workbooks:run` npm scripts

Two new npm scripts:

```json
"workbooks:validate": "mtsw validate docs/bridges/workbooks/*.mtsw",
"workbooks:run": "mtsw run docs/bridges/workbooks/*.mtsw"
```

`workbooks:validate` runs in CI on every commit via the existing CI pipeline
(the implementation plan must specify where in the pipeline — it should run
after `npm run build` so the TS modules are compiled to `dist/` before the
code cells import them).

`workbooks:run` is heavier (executes all `test` cells) and is NOT part of the
default commit CI. It runs as a pre-release gate, alongside `npm test`, before
tagging a release. This mirrors the existing `npm run smoke` pattern.

### Decision #9 — No `.uptf.json` export format in this proposal

The Proposals doc §8.5 mentions a `.uptf.json` serialization. That is deferred
to v1.0+. Workbook-to-JSON export is a separate concern; v0.9 ships the
workbook format and CI validation only. The SymPy export tool (`tools/export-sympy/`)
mentioned in §8.6 is similarly deferred — it requires Proposal 4 (Bridge DSL)
to be in place first so there is a compiled bridge object to walk.

## The `.mtsw` Skeleton

This is the canonical four-cell skeleton. Every bridge workbook must conform
to this structure exactly. BE-37 (Shapiro delay) is used as the worked example.

```yaml
# docs/bridges/workbooks/be-37-shapiro-delay.mtsw
version: '1.0'
metadata:
  title: 'Bridge Equation 37 — Shapiro Gravitational Time Delay'
  bridge_id: 37
  slug: 'be-37-shapiro-delay'
  ts_module: 'src/bridges/equations/be-37-shapiro-delay.ts'

cells:

  - id: prose
    kind: markdown
    content: |
      # Bridge Equation 37 — Shapiro Gravitational Time Delay

      **Reformulated from:** Variable Speed of Light Cosmology (VSL) —
      the original `c(t,x) ≠ const` ansatz is operationally meaningless
      per Ellis & Uzan 2005 (*Am. J. Phys.* 73:240). Light always travels
      at _c_ locally; any "varying c" in vacuum is a rescaling of other
      constants with no observable consequence independent of those constants.

      **Encoded as:** Shapiro gravitational time-delay — the coordinate-time
      delay of light passing near a massive body in a Schwarzschild
      gravitational field:

        Δt = (2 G M / c³) · ln(R_far / R_near)

      This is the operationally-meaningful gravitational "effective-c"
      phenomenon that survives the Ellis-Uzan critique. Shapiro 1964
      predicted the effect; Cassini 2003 (Bertotti-Iess-Tortora, _Nature_
      425:374) measured it to ~10⁻⁵ precision.

      **Bridge framing:** `speculative` — the bridge label "VSL cosmology" is
      contested; the Shapiro delay formula itself is canonical GR.

      **Dimensional check:**
      - G: [L³ M⁻¹ T⁻²], M: [M] → 2GM: [L³ T⁻²]
      - c³: [L³ T⁻³] → 2GM/c³: [T] ✓
      - ln(R_far/R_near): dimensionless (ratio of lengths) ✓
      - Δt: [T] ✓

      **References:**
      - Shapiro 1964, _Phys. Rev. Lett._ 13:789
      - Bertotti, Iess & Tortora 2003, _Nature_ 425:374 (Cassini measurement)
      - Ellis & Uzan 2005, _Am. J. Phys._ 73:240 (motivation for reformulation)
      - Will 1981/2014, _Theory and Experiment in Gravitational Physics_

  - id: meta
    kind: data
    content: |
      bridge_id: 37
      status: speculative
      confidence: speculative
      from: { axis: scale, name: cosmological }
      to:   { axis: scale, name: classical }
      dimensional_signature: '[time]'
      parameters:
        - { name: G, dim: '[L³ M⁻¹ T⁻²]', physical: 'Newton gravitational constant' }
        - { name: M, dim: '[M]',            physical: 'gravitating body mass' }
        - { name: c, dim: '[L T⁻¹]',        physical: 'speed of light' }
        - { name: R_far,  dim: '[L]', physical: 'outer radial distance' }
        - { name: R_near, dim: '[L]', physical: 'inner radial distance' }
      encoding_note: >
        The canonical Shapiro delay scalar (one-way, γ=1).
        Also encodes the eikonal structural form g^μν (∂_μ S)(∂_ν S) = 0
        (v0.3.0 tensor layer) via BE37_EIKONAL_LHS; the scalar above is its
        weak-field integrated solution.
      references:
        - { cite: 'Shapiro 1964', doi: '10.1103/PhysRevLett.13.789' }
        - { cite: 'Bertotti et al. 2003', doi: '10.1038/nature01997' }

  - id: build
    kind: code
    content: |
      // Thin re-export: the canonical AST and evaluators live in the TS module.
      // This cell exposes them to the test cell below without reimplementing them.
      import {
        BE37_SHAPIRO_DELAY_LHS,
        BE37_SHAPIRO_DELAY_RHS,
        BE37_EIKONAL_LHS,
        BE37_EIKONAL_RHS_ZERO,
        evaluateShapiroDelay,
        validateBE37Dimensions,
        validateBE37EikonalDimensions,
      } from 'universal-physics-tensor/bridges/equations/be-37-shapiro-delay';

      export {
        BE37_SHAPIRO_DELAY_LHS,
        BE37_SHAPIRO_DELAY_RHS,
        BE37_EIKONAL_LHS,
        BE37_EIKONAL_RHS_ZERO,
        evaluateShapiroDelay,
        validateBE37Dimensions,
        validateBE37EikonalDimensions,
      };

  - id: verify
    kind: test
    depends_on: [build]
    content: |
      import { assert } from '@danielsimonjr/mathts-workbook/test';
      import {
        validateBE37Dimensions,
        validateBE37EikonalDimensions,
        evaluateShapiroDelay,
      } from '#build';

      // 1. Dimensional self-check: both LHS and RHS must be [time].
      const dimReport = validateBE37Dimensions();
      assert(dimReport.ok, `Dimensional check failed: ${JSON.stringify(dimReport)}`);

      // 2. Eikonal structural form: both sides must be dimensionless.
      const eikonalReport = validateBE37EikonalDimensions();
      assert(eikonalReport.ok, `Eikonal dimensional check failed: ${JSON.stringify(eikonalReport)}`);

      // 3. Numerical bracket check: Sun, light from 1 AU to grazing R_sun.
      //    Published one-way Shapiro delay ~ 50-60 μs (Shapiro 1964, textbook value).
      const dt = evaluateShapiroDelay({
        M_kg: 1.989e30,    // solar mass
        R_far_m: 1.496e11, // 1 AU
        R_near_m: 6.957e8, // solar radius
      });
      assert(dt > 40e-6 && dt < 70e-6,
        `Expected ~50-60 μs one-way Shapiro delay for Sun, got ${(dt * 1e6).toFixed(1)} μs`);
```

### Cell-type matrix across the 42 bridges

| Bridge set | `markdown` | `data` | `code` | `test` (dim only) | `test` (dim + numerical) |
|---|---|---|---|---|---|
| 8 established | all | all | all | — | all 8 |
| 31 speculative | all | all | all | ~20 (no evaluator) | ~11 |
| 3 highly-speculative | all | all | all | all 3 | — |

The `code` cell is always present. The `test` cell's depth depends on whether
the TS module exports a numerical evaluator. Adding evaluators to bridges that
currently lack them is a follow-up item, not in this proposal's scope.

## How the Existing Test Suite Is Preserved

The round-trip invariant pinned by `tests/bridges/dimensional-signature-catalog.test.ts`
is **not affected by this proposal**. That test imports directly from
`src/bridges/equations/*.ts`. The `.mtsw` workbooks are a parallel artifact;
they import from the same TS modules but do not replace them.

The chain of invariants:

```
TS module (source of truth)
  ├─ imported by: tests/bridges/dimensional-signature-catalog.test.ts
  │     → asserts dimensional_signature round-trips through validator
  ├─ imported by: tests/bridges/be-NN-*.test.ts (74 per-bridge tests)
  │     → asserts encoding correctness, evaluator behavior, edge cases
  └─ imported by: docs/bridges/workbooks/be-NN-*.mtsw (code cell)
        → exposes exports to test cell
        → test cell runs dim check + numerical bracket check (new)
```

The workbook `test` cells ADD coverage; they do not replace the existing
vitest tests. In particular: the per-bridge `tests/bridges/` files test
TypeScript-level contracts (types, guard conditions, edge cases, null
inputs). The workbook `test` cells test physics-level scenarios (canonical
inputs from the literature, limit checks).

The BRIDGE-PHYSICS-AUDIT.md finding about `formula_latex`/encoding transparency
(§1 real finding: "add an `encoded_form` field to entries whose AST encodes a
reduction") is addressed partially by the `data` cell's `encoding_note` field.
Every bridge workbook that encodes a reduction must include an `encoding_note`
explaining what `dimensional_signature` actually describes.

## Source-of-Truth Question — Resolved

`src/bridges/index.ts` (`BRIDGE_EQUATIONS`) remains the sole source-of-truth
for the runtime catalog. Workbooks consume it; they do not replace it. A
future code-generation pipeline (workbook YAML → TS catalog entry) is v1.0+
scope, explicitly not in this proposal.

## Dependency Contract

| Dependency | Type | Rationale |
|---|---|---|
| `@danielsimonjr/mathts-workbook` | `devDependencies` | Authoring and CI tool; not shipped to UPT consumers |
| `mtsw` CLI | available via `npx mtsw` | Provided by `mathts-workbook` package |

UPT's published package (`npm install universal-physics-tensor`) does not
acquire `mathts-workbook` transitively. The `"files"` field in `package.json`
already excludes `docs/`; workbooks at `docs/bridges/workbooks/` are excluded
from the npm artifact.

Downstream consumers who want to use `.mtsw` authoring for their own
bridge additions would need to install `@danielsimonjr/mathts-workbook`
themselves. That is by design — the workbook runtime is an authoring-layer
optional, not a runtime core.

- **Task 0.3 — CI script stub.** Add `"workbooks:validate"` and

  workbooks:validate` passes with BE-37 as the only workbook.

two new scripts. 2 commits (dep + scripts; BE-37 skeleton).

## Phase 1 — Established Bridges (8 workbooks)

Start with the 8 `established` bridges (BE-11, 14, 16, 19, 20, 29, 51, 52):
they have the most complete TS modules, the cleanest physics, and the strongest
`tests/bridges/` coverage. Working these first validates the skeleton before
replicating it across the contested speculative entries.

Note: BE-51 and BE-52's evaluators live at `src/bridges/gravitational-lensing.ts`
and `src/bridges/perihelion-precession.ts` (v0.4.0 level), not in
`src/bridges/equations/`. The workbook `code` cell imports from the correct path.

Per-workbook protocol: (1) read TS module docstring; (2) draft `markdown` from
prose; (3) draft `data` from `BRIDGE_EQUATIONS` in `src/bridges/index.ts`;
(4) draft `code` re-export list; (5) draft `test` with dimensional check +
numerical bracket from docstring; (6) run `mtsw run`; commit.

Full `npm test` runs once at phase end, not per-workbook (CLAUDE.md: "don't
re-run the full suite per task").

**Deliverable:** 8 `.mtsw` files; `npm run workbooks:validate` passes on all 8.

## Phase 2 — Speculative Batch A (bridges 11-32, ~22 workbooks)

Bridges that currently lack a numerical evaluator get a `test` cell with
dimensional check only, plus an explicit `TODO` comment:

```yaml
      # TODO: add numerical bracket check when evaluateBE23() is implemented.
```

Bridges with `unknown <-> unknown` bridge metadata (audit §3, ~9 entries):
the `data` cell corrects clearly fixable cases (missing regime name where
the physics is unambiguous). Contested metadata (BE-18 dark sector,
BE-42 Hawking mis-filed) gets an `audit_note` field rather than a correction:

```yaml
      audit_note: >
        BRIDGE-PHYSICS-AUDIT §3: flagged bridge-incoherent. Metadata reflects
        current catalog state; see the audit for recommended correction.
```

The `BRIDGE_EQUATIONS` TS entries are NOT changed in this proposal.

**Deliverable:** ~22 `.mtsw` files; `npm run workbooks:validate` passes.

## Phase 3 — Speculative Batch B (bridges 33-52, ~12 workbooks)

Completes the catalog. Includes the three `highly-speculative` entries and
bridges with open physics questions (BE-33 exponent candidate error, BE-34
Kibble-Zurek Boltzmann extension, BE-28 Onsager MEPP critical warning).

These get a `physics_question` field in the `data` cell:

```yaml
      physics_question: >
        AUDIT §2: two-model convergence suggests exponent should be −1/z,
        not −ν/z. Pending Millis 1993 / Sachdev Ch. 11 verification.
        Do not change the TS module until verified.
```

And a corresponding note in the `test` cell that documents without asserting
a resolution.

**Deliverable:** ~12 `.mtsw` files; all 42 bridges covered; `workbooks:validate`
passes on all 42.

## Risks

1. **`mathts-workbook` not published to npm.** `mathts-tensor` and
   `mathts-autograd` are in `optionalDependencies` but not installed in the
   current environment. If `mathts-workbook` is similarly absent from the
   public registry, the proposal blocks entirely. Task 0.1 is the gate.

2. **`code` cell import semantics.** If `mtsw`'s sandboxed `evaluate()` cannot
   resolve ESM `import` statements, the skeleton's `code` cell design is wrong
   and needs a fundamentally different approach. Mitigation: Adam+Eve review
   + Task 0.2 live validation before committing the skeleton convention.

3. **Workbook drift from TS modules.** When a TS module gains or changes
   exports, the workbook's `code` cell re-export list goes stale. Mitigation:
   the `test` cell calls the evaluator — signature changes cause `mtsw run`
   failures, surfacing drift. The CI `workbooks:validate` step gates structure
   but does not run `test` cells.

4. **Audit TODOs become permanently embedded markers.** The `physics_question`
   and `audit_note` fields are tracking markers, not action items. Mitigation:
   Task 4.3 surfaces them as `todo.md` items with a v1.0 resolution target.

5. **Ordering dependency on v0.8 (Proposals 3 + 5).** The `data` cell's
   `from`/`to` fields use plain strings if `UniversalIndex` (Proposal 3)
   isn't in place. That is acceptable — the workbook is documentation, not
   runtime. Document in the skeleton that `from`/`to` will gain typed
   references once Proposal 3 ships.

## Non-Goals

- Any change to the TS modules in `src/bridges/equations/`.
- Any change to `src/bridges/index.ts` (`BRIDGE_EQUATIONS`).
- Any change to `tests/bridges/` (existing tests are untouched).
- Code-generation from `.mtsw` to TypeScript (v1.0+ scope).
- `.uptf.json` export format (Decision #9; v1.0+ scope).
- SymPy/Mathematica export tool (deferred; requires Proposal 4).
- Adding numerical evaluators to bridges that currently lack them.
- Resolving open BRIDGE-PHYSICS-AUDIT physics-content questions (BE-33 exponent,
  BE-34 Boltzmann extension) — those are physics work requiring literature
  verification, incompatible with workbook-authoring tempo.
- Any new public API exported from `src/index.ts`.
