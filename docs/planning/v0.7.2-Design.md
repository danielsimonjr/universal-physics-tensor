## 3. Decisions

### Decision #1 — Migrate to `Float64Array` with row-major flat indexing, NOT `Float32Array` or nested-array fallback

Per the v0.6.0 BR-2 precedent (`christoffelFn` → `Float64Array(64)`,
5-6× speedup measured). `Float64Array` preserves the full SI numerical
precision (Schwarzschild calculations need ≥e-9 relative tolerance on
GL4 Mercury runs — `Float32Array` would risk floor-level catastrophic
cancellation in `c²·g_tt` terms).

**Index convention** (mirror BR-2 exactly):
- `gInv` (4×4): `flat[mu*4 + nu] = g^{μν}` — row-major.
- `dgInv` (4×4×4): `flat[lambda*16 + mu*4 + nu] = ∂_λ g^{μν}` — row-major
  in the outer index, then row-major in the (μ,ν) pair.

These conventions match `christoffelFn` (`flat[i*16 + j*4 + k] = Γ^i_{jk}`)
so a future flat-Riemann migration would slot cleanly.

### Decision #2 — Two BREAKING fixture-surface changes, communicated up-front

`tests/fixtures/schwarzschild.ts` and `src/numerical/painleve-gullstrand-metric.ts`
are NOT in `src/index.ts`'s public re-export surface. The fixture lives
under `tests/`; the PG metric is exported but consumers reading the
README + spec would mostly know to use it through the FD pipeline (which
auto-adapts via `flattenNA`).

BUT: any consumer code that directly indexed `result[mu][nu]` will break
at runtime. The CHANGELOG + commit messages must call this out
explicitly. PG is `@public` in `src/index.ts`; the BREAKING-on-signature
nature of the change argues for a minor version bump (0.7 → 0.8) BUT we
defer that escalation to the user (per the v0.7-series tag-strategy
deferral pattern). For now, ship under `v0.7.2` with a BREAKING-CHANGE
prefix on the relevant commit.

### Decision #3 — `flattenNA` widening covers most consumer-side TS surface

The Phase 5 agent's recon (v0.7.1) noted that `flattenNA` at runtime
already handles `Float64Array` correctly via `for-of` iteration on
typed arrays. The migration's TypeScript-side surface is therefore:
1. The fixture's return type changes (`number[][]` → `Float64Array`).
2. Consumer function signatures that DECLARE `gInverseFn:
   (x: ...) => number[][]` must widen to `Float64Array | number[][]`
   OR accept a `MetricFnFlat` type alias.
3. Tests that do direct `gInv[mu][nu]` must rewrite to `gInv[mu*4 + nu]`.

Phase 1 produces a small `MetricFnFlat` type alias in `src/numerical/types.ts`
(or wherever the existing `MetricFn` alias lives) that captures the new
shape. All consumers reference the alias.

### Decision #4 — Pre-flight `git merge-base` check is MANDATORY in every agent brief

Per the v0.7 + v0.7.1 worktree-fork-point lesson (worktrees sometimes fork
from `master` instead of the working branch). Every agent brief in the
implementation plan MUST include:

```
git fetch origin claude/changelog-todo-sync-9PdMg
test "$(git rev-parse HEAD)" = "$(git rev-parse origin/claude/changelog-todo-sync-9PdMg)" \
  || git reset --hard origin/claude/changelog-todo-sync-9PdMg
```

The v0.7.1 Phase 3 agent's fork-point catch was correct; we generalize
the fix into the standard preamble. Otherwise the agent improvises
against a stale baseline.

### Decision #5 — Phase 1 + Phase 2 do NOT run in parallel

They share the FD-lowering pipeline contract (both write `Float64Array`-
returning closures that the same downstream code consumes). If they
land in parallel and one widens a type signature one way while the
other widens it differently, the cherry-pick merge becomes hostile.

Phase 1 lands FIRST (Schwarzschild — the canonical case, 20+ callsites).
Phase 2 follows (PG — fewer callsites, but exercises the SAME type-
alias widening Phase 1 just established). Both serial.

Phase 4 (S-9 simplify) IS parallel-safe with Phase 1 + 2 — it touches
`src/numerical/lowering.ts` only, which is downstream of the fixture
migrations and independent of their type contracts.

### Decision #6 — Bench gate IS the verdict for Phase 1 (not just suite-green)

v0.7.1's Phase 5 lesson: O-2 alone got 1.27× speedup on PO-1. The
brainstorm's "2-5×" prediction was for O-1+O-2 combined. Phase 5 (this
sprint) re-measures `bench/gl4-picard-alloc.bench.ts` after Phase 1 +
Phase 2 + Phase 4 all land. Expected: ≥ 2.0× speedup vs v0.7.1
post-O-2 baseline (3,490 hz single stage → ≥ 6,980 hz post-O-1).

If the bench shows <1.5× after Phase 1 lands, the migration may have
introduced a subtle memory-locality or cache-line issue invisible to
the suite. STOP and diagnose before continuing — do NOT commit Phase 5
finalization until the bench gate is met or the deviation explained.

### Decision #7 — S-9 brainstorm count is STALE; Phase 4 task brief MUST re-grep

Per the v0.7.1 S-14 lesson (brainstorm claimed 5×, actual was 8×). S-9's
"5 deferred-evaluator arms" claim is from the v0.7.1 simplify brainstorm.
Phase 4 Task brief: `grep -n "// TODO.*lower\|return.*notImplemented\|throw new.*notimplemented" src/numerical/lowering.ts` to count actual arms at HEAD. If the count differs from 5, adjust scope; document honestly.

## 8. What this design is NOT

- NOT a public API change. `MetricFnFlat` is the only new exported type;
  all existing `@public` symbols remain exported with widened types.
- NOT a behaviour change. Every test assertion that passed at HEAD
  `b9d720f` must pass at the v0.7.2 release HEAD. The migration is
  representational, not semantic.
- NOT a new bridge or new physics. The catalog stays at 44 entries.
- NOT a version bump that hits npm. Per ongoing user directive, the
  version stays at `0.6.0` in `package.json` until the publish-token
  rotation unblocks the release pipeline.
