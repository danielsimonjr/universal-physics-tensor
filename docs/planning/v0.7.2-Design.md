## 3. Decisions

### Decision #1 — Migrate to `Float64Array` with row-major flat indexing, NOT `Float32Array` or nested-array fallback

Per the v0.6.0 BR-2 precedent (`christoffelFn` → `Float64Array(64)`,
5-6× speedup measured). `Float64Array` preserves the full SI numerical
precision (Schwarzschild calculations need ≥e-9 relative tolerance on
GL4 Mercury runs — `Float32Array` would risk floor-level catastrophic
cancellation in `c²·g_tt` terms).

**Index convention** (mirror BR-2 exactly):
- `gInv` (4×4): `flat[mu*4 + nu] = g^{μν}` — row-major.
- `dgInv` (4×4×4): `flat[lambda*16 + mu*4 + nu] = ∂_λ g^{μν}` — row-major
  in the outer (partial-derivative) index, then row-major in the (μ,ν)
  pair. Verified by Adam A-11 against the existing `dg[lambda][mu][nu]`
  nested-array convention at `tests/fixtures/schwarzschild.ts:204`.

These conventions match `christoffelFn` (`flat[i*16 + j*4 + k] = Γ^i_{jk}`)
so a future flat-Riemann migration would slot cleanly.

### Decision #3 — Three consumer categories for `Float64Array` migration (revised per Adam A-3)

The r1 design's "runtime adapts via `flattenNA`" framing was incomplete.
The reality is three distinct consumer categories with different
migration shapes:

1. **`flattenNA`-mediated consumers** (curvature-lowering FD pipeline:
   `curvature-lowering-helpers.ts:147,148,156` etc.):
   - Runtime: `for (const c of Float64Array)` yields numbers correctly,
     so `flattenNA` works post-widening at runtime.
   - Type-level: `NestedArray = number | NestedArray[]` at
     `src/numerical/types.ts:11` EXCLUDES typed arrays. Widening
     required: `NestedArray = number | NestedArray[] | Float64Array`
     OR introduce `FlatOrNested = NestedArray | Float64Array` and
     retype `flattenNA`'s parameter. Task 1.1 / 3.1 lands this widening.

2. **Direct-indexed in `src/`** — the HOT-PATH category that v0.7.1's
   Phase 5 agent flagged + Adam A-1 enumerates:
   - `src/numerical/gl4-integrator.ts:227,236,303,341` (`gInvAtXj[mu][nu]`,
     `dgInvAtXj[mu][nu][rho]` — the Picard solver hot path)
   - `src/numerical/weyl-lowering.ts:79`
   - `src/numerical/perihelion-finder.ts:88,417`
   - `src/numerical/killing.ts:212`
   - `src/numerical/null-ic.ts` (2 hits per Eve E1.1)
   - `src/numerical/be37-covariant-eikonal.ts` (10 hits per Eve E1.1)
   - These MUST rewrite `[μ][ν]` → `[μ*4+ν]` and `[λ][μ][ν]` →
     `[λ*16+μ*4+ν]` at every callsite. They bypass `flattenNA` entirely.
   - Phase 3 Task 3.3 (split per A-3): explicit "rewrite the 6 hot-path
     `src/` consumers" task, separate from the type-alias widening.

3. **Direct-indexed in `tests/` + `bench/`**:
   - Per Adam A-12 actual file split (re-greppable in Phase 0):
     `tests/fixtures/` 5 files (schwarzschild, schwarzschild.test,
     de-sitter, flrw, minkowski — per Decision #8, the latter 3 stay
     nested-array), `tests/numerical/` 7 files, `tests/dimensional/`
     3 files, `tests/bridges/` 0 files, `bench/` 0 files.
   - Phase 3 Task 3.4 / 3.5 — batched mechanical rewrite (Schwarzschild
     fixture + downstream tests).

Each category gets its own task; Phase 0 verifies the file enumeration
empirically before Phase 1/3 brief opens.

### Decision #8 — Sibling fixtures (de-sitter, flrw, minkowski) STAY nested-array; `MetricFn` union-widens — NEW per Adam A-2 + Eve E1.1

Sibling fixtures at `tests/fixtures/de-sitter.ts`, `flrw.ts`, `minkowski.ts`
declare their own `xGFn` / `xGInverseFn` / `xDgInverseFn` closures with
the identical `number[][]` / `number[][][]` return-type pattern. Direct-
index callsite counts at HEAD per Adam A-2: de-sitter 17, flrw 8,
minkowski 1.

**Decision**: keep sibling fixtures on the legacy nested-array path for
v0.7.2. The `MetricFn` / `MetricFnFlat` type alias gains a UNION member
so consumers can accept both shapes:

```ts
// In src/numerical/types.ts (or lowering-utils.ts where MetricFn lives)
export type MetricFnFlat = (x: ReadonlyArray<number>) => Float64Array;
export type MetricFnNested = (x: ReadonlyArray<number>) => number[][];
export type MetricFn = MetricFnFlat | MetricFnNested;
```

Consumers that direct-index (`gInv[mu][nu]`) must narrow via a runtime
check or an exhaustive type-guard helper. The hot-path `src/` consumers
(Decision #3 category 2) are migrated to the FLAT layout in Phase 3 — so
they REQUIRE `MetricFnFlat`, not the union, in their parameter types.

**Out-of-scope deferral**: sibling-fixture migration to `Float64Array`
is a v0.7.3 / v0.8 task. The divergence is acknowledged honestly in §1
out-of-scope and tracked in `todo.md`.

### Decision #9 — Adam+Eve vets dispatched SERIALLY (per Eve E9)

The v0.7.1 parallel-agent infrastructure friction (Phase 5 agent
reporting reverts; O-1 attempt failing) argues that **parallel agent
dispatch is the EXCEPTION case**, not the default. For Phase 2 mid-cycle
vet:

- Dispatch Adam first; wait for completion; cherry-pick + push Adam's
  vet doc commit.
- Dispatch Eve on the post-Adam HEAD; wait for completion; cherry-pick
  + push Eve's vet doc commit.

This adds ~15-30 min wall-time vs parallel dispatch but eliminates the
class of "Eve reviews a HEAD that's already drifted from what Adam
reviewed" failure modes that contributed to v0.7.1 design vet noise.

If a future sprint reaches a phase that's genuinely independent (e.g.,
two file-disjoint phases dispatched in parallel during execution, NOT
review), parallel is OK there — but the vet pair specifically is serial
by default.
