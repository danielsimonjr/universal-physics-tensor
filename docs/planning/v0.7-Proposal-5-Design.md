> the `RegimeType` extension system. Per the proposals doc's own
> sequencing (§11), this proposal lands in **v0.8**, not v0.7. It
> depends structurally on at least Proposals 1 and 3 from the v0.7
> "Foundation Consolidation" wave. This design doc commits to that

## Honest framing up front

Proposal 5 is **the most under-specified of the eight proposals** in
the source doc. §6.2 of the proposals doc shows a worked example
(`defineRegime({ axis: 'scale', name: 'quantum-biological', … })`)
but **never closes the taxonomy of built-in regimes**, never pins
the exact union the extension API extends, and skirts the question
of whether a regime is a value (`'quantum'`) or a structured object
(with `tags`, `limits`, `participatesIn`). The acceptance criteria
in §6.3 read more like an API sketch than a design.

This doc commits to a specific decision at every fork, even where
the source proposals doc is silent. Where the commitment is
debatable, it is flagged with a "Decision rationale" or "Honest-flag"
block. The single most consequential decision is **§Decision #1
(below) — ship the *extension-point mechanism* in v0.8, defer the
closed taxonomy of built-in regimes to a follow-up research task.**
The taxonomy is a physics-classification problem (which 42 bridges
sit in which regime?), not an engineering problem, and bundling it
into the engineering deliverable risks rushing the physics.

---

## Goal

Introduce a typed, extensible categorical axis for bridges — the
"regime" axis — that:

1. Replaces the **free-text `category` / `category_name`** columns
   on `BridgeEquationEntry` (currently 15 distinct
   `category_name` strings across the 42-bridge catalog, verified
   by `grep -h "category_name:" src/bridges/index.ts | sort -u`)
   with a typed enum-like value.
2. Replaces the **closed-union `Symmetry`** and
   **closed-union `InformationMeasure`** types in
   `src/core/types.ts` with extensible analogues, **without**
   breaking the v0.7 public-API contract.
3. Permits **third-party packages** to register new regime values
   (`defineRegime({...})`) and have them flow through the bridge
   catalog, validator-registry, and Π-tensor flux rules just as
   the built-ins do — the "factory-tier idiom" from §6 of the
   proposals doc.
4. Records **provenance** on every regime value (which package /
   version registered it) so cross-package catalogs are auditable.
5. Surfaces a **migration story** for the 42 existing bridges:
   each gets back-tagged with one or more regime values (a bridge
   may legitimately sit at the boundary of two regimes — e.g.
   BE-11 Decoherence bridges quantum ↔ classical, BE-13 Einstein
   Trace bridges information-thermodynamic ↔ GR).

The sprint succeeds if:

- The extension-point API (`defineRegime`, `defineSymmetry`,
  `defineInformationMeasure`, lookup helpers) is operational,
  type-safe end-to-end, and exercised by an in-tree example
  (`examples/extending-uptf/`).
- The five built-in axes (scale, force, symmetry, information,
  dimension, topology — per Proposal 1's `AxisName` union) are
  re-implemented through the extension API itself, so the
  built-in registration code is the **same code path** third-party
  consumers use ("eating one's own dog food"; eliminates the
  drift class where built-ins drift away from extensions).
- The 42 bridges in `src/bridges/index.ts` are NOT yet re-tagged
  (deferred to a follow-up). The v0.8 deliverable ships the
  **mechanism + a re-tagging audit document** that enumerates
  candidate regime assignments per bridge for physics review,
  with no commitment yet to any specific multi-regime mapping.

## Why this proposal is v0.8, not v0.7

§11 of the proposals doc explicitly sequences `RegimeType` under
v0.8 ("Extension Surface Expansion"), with v0.7 reserved for
foundation work (Proposals 1, 2, 3, 4). This design respects that
sequencing for three structural reasons:

1. **Proposal 3 (Typed L+B+E discriminated union) must land first.**
   Proposal 5's regime values live as fields on `LawEntry`,
   `BridgeEntry`, `EmergenceEntry`. Before those Cell types
   exist as a discriminated union, Proposal 5 has no shape to
   attach to.
2. **Proposal 1 (UniversalIndex layer) introduces `AxisName`.**
   The five built-in axes Proposal 5 extends — scale, force,
   symmetry, information, dimension, topology — are first named
   in Proposal 1. Without it, Proposal 5 has six independent
   axis definitions to wire up, which is duplicative.
3. **Proposal 2 (Sparse semantic catalog) introduces flux rules.**
   The v0.6 example in §6.2 includes a `fluxRules` field on
   `defineRegime`. That field only makes sense once the
   `UniversalTensor` from Proposal 2 has the flux-rule plumbing
   to consume it.

Practical consequence: this design assumes Proposals 1, 2, 3 have
shipped in v0.7. Proposal 4 (Bridge DSL) is **not** a structural
dependency — Proposal 5 can ship before or after it.

## Architectural Decisions (locked)

### Decision #1 — Ship the extension-point mechanism only; defer the closed taxonomy of built-in regimes

The proposals doc §6 lists candidate regimes (classical mechanics,
GR, QFT, cosmology, condensed matter) but does **not** close the
taxonomy. The honest options are:

- **(a)** Commit to a specific built-in taxonomy in this design
  (e.g., "the eight regimes are: classical-mechanics,
  quantum-mechanics, QFT, GR, cosmology, condensed-matter,
  statistical-mechanics, information-theoretic"), and back-tag
  the 42 bridges accordingly as part of v0.8.
- **(b)** Ship only the extension-point mechanism in v0.8 — the
  `defineRegime` API plus the registry plumbing — and treat the
  closed taxonomy of built-ins as a separate v0.8.x or v0.9
  research deliverable that requires per-bridge physics review.

**This design commits to option (b).** Three reasons:

1. **The bridge categorization is itself a research task.** The
   42-bridge catalog spans contested boundaries (BE-13
   Jacobson-style information-thermodynamic Einstein equations is
   GR? information-theoretic? both?). A "ship the taxonomy as
   part of the engineering release" plan would either rush the
   physics or pad the sprint past the 2–3 week budget the
   proposals doc allocates.
2. **The extension mechanism is the load-bearing engineering
   work.** Designing the registry, the type-safety story, the
   provenance recording, and the cross-package collision rules is
   what costs the 2–3 weeks. Adding eight built-in `defineRegime`
   calls on top costs hours.
3. **The v0.6.1 hygiene precedent: don't bundle physics work into
   refactor work.** v0.6.1's Decision #7 explicitly carves out
   bridge re-encoding from the hygiene sprint for the same
   reason — physics review and engineering tempo are incompatible.

**Honest-flag:** option (a) is defensible — it would give v0.8 a
crisper "user-visible improvement" story (categorized 42 bridges
through a typed regime axis), where option (b) ships an API hook
that has no immediately-visible payoff for read-only consumers of
the catalog. The trade is **engineering rigor vs. release
narrative**; this design picks rigor. The follow-up regime-tagging
work is explicit in the §Deliverable list, not silently dropped.

**What ships in v0.8 under option (b):**
- The `defineRegime` / `defineSymmetry` / etc. API.
- The closed registry of *axis names* (scale, force, symmetry,
  information, dimension, topology — pinned from Proposal 1).
- The eight v0.6 closed-union values from `core/types.ts`
  re-registered through `defineRegime`. These eight ARE the
  v0.8 built-ins — but they were inherited from v0.6, not
  designed in v0.8. The taxonomy-as-physics-decision is
  explicitly *not* re-opened in v0.8.
- An audit document `docs/architecture/v0.8-regime-tagging-audit.md`
  that proposes a regime assignment for each of the 42 bridges
  for physics review (not for landing as code).

### Decision #2 — Registry pattern: closed-base + open extension point, with a string-tag escape hatch

TypeScript enum / union types are closed by design. The "factory-
tier idiom" of allowing third-party variants requires a runtime
extension mechanism. The two existing in-tree precedents
(`CURVATURE_KIND_REGISTRY`, `VALIDATOR_REGISTRY`) are both **closed**
record-keyed-by-union-type registries. Proposal 5's registry must
be **open** — entries added after module-load by downstream callers.

The exact mechanism is:

```ts
// Conceptual sketch — do NOT treat as binding implementation.
// The actual API will be re-specced in the v0.8 Implementation Plan.

export type RegimeAxisName =
  | 'scale' | 'force' | 'symmetry'
  | 'information' | 'dimension' | 'topology';

export interface RegimeValueBase {
  readonly axis: RegimeAxisName;
  /** Tag string — globally unique within (axis, package). */
  readonly tag: string;
  /** Human-readable display name. */
  readonly displayName: string;
  /** Free-form descriptive tags (NOT the discriminant). */
  readonly tags?: ReadonlySet<string>;
  /** Limit procedure (e.g. 'ℏ → 0', 'T → 0') if applicable. */
  readonly limits?: string;
  /** Provenance record. */
  readonly provenance: RegimeProvenance;
}

export interface RegimeProvenance {
  /** npm package name of the registering caller. */
  readonly registeredBy: string;
  /** Package version at registration time. */
  readonly version: string;
  /** Timestamp of the registration call. */
  readonly registeredAt: number;
}

// Internal registry — Map<axis, Map<tag, RegimeValueBase>>.
const REGIME_REGISTRY: Map<RegimeAxisName, Map<string, RegimeValueBase>>
  = new Map();

export function defineRegime(spec: Omit<RegimeValueBase, 'provenance'> & {
  registeredBy: string;
  version: string;
}): RegimeValueBase {
  // collision check, register, return frozen value
}

export function lookupRegime(
  axis: RegimeAxisName, tag: string
): RegimeValueBase | undefined {
  return REGIME_REGISTRY.get(axis)?.get(tag);
}

export function listRegimesByAxis(
  axis: RegimeAxisName
): readonly RegimeValueBase[] {
  return Array.from(REGIME_REGISTRY.get(axis)?.values() ?? []);
}
```

**Three structural commitments:**

1. **The `tag` field is a `string`, not a literal-typed union.**
   This is the string-tag escape hatch. TypeScript's type system
   cannot constrain third-party tag values at compile time
   without consuming the third-party module. The tradeoff is
   accepted explicitly: cross-package consumers get **runtime
   lookup with `undefined` failure**, not compile-time tag
   validity. Within a single package (including UPT's own
   built-ins), a literal-typed alias can narrow further:
   ```ts
   export type BuiltinScaleTag =
     | 'quantum' | 'mesoscopic' | 'classical' | 'cosmological';
   export const ScaleRegimes: Record<BuiltinScaleTag, RegimeValueBase>
     = { /* … */ };
   ```
   This dual-surface (string-keyed registry + literal-typed alias
   for built-ins) gives both the open-extension story and the
   compile-time safety story.

2. **The `axis` axis itself is closed.** New axes
   (e.g. a hypothetical "computational-class" axis) require a
   SemVer-minor UPT release, not a third-party registration.
   This is the "closed-base" half of "closed-base + open
   extension point". The trade is intentional: an open axis
   namespace would make cross-package catalog merging
   intractable.

3. **Provenance is mandatory, not optional.** The `registeredBy`
   and `version` fields are required parameters of `defineRegime`,
   not best-effort. This is the audit trail when two packages
   register colliding tags or when a downstream consumer asks
   "where did this regime come from?". Failing to provide
   provenance is a TypeScript compile error, not a runtime
   warning.

**Why not a sealed class hierarchy?** Classes-as-discriminants
work in Java/C#, less well in TypeScript ESM. UPT's existing AST
nodes are plain readonly-object literals with a `kind` discriminant
(see `CurvatureCompositeNode<K, S>` at
`src/dimensional/curvature-composite.ts:139`). Proposal 5 follows
that idiom.

**Why not just allow `string` everywhere?** Because the migration
from `PhysicalScale = 'quantum' | ...` (compile-time-checked) to
`string` (no checks) is a strict regression for built-in callers.
The dual-surface approach preserves the compile-time check for
built-ins while opening the extension point for third parties.

### Decision #3 — Cross-package collision: namespaced-tag + first-write-wins, with a diagnostic

Two third-party packages both calling
`defineRegime({ axis: 'scale', tag: 'mesoscopic-bio', ... })`
present a collision. The honest options are:

- **(a)** First-write-wins with a warning (silently the second
  call's payload is dropped, second caller gets the first
  registration's object back).
- **(b)** Last-write-wins (second caller overwrites the first;
  any extant references to the first become stale).
- **(c)** Throw on collision; require the caller to scope-prefix
  their tags (`'@user/qbio.mesoscopic-bio'`).
- **(d)** Namespaced-tag with mandatory prefix (a la npm scopes):
  the tag's first segment must equal `registeredBy`, enforced at
  registration time. UPT's own built-ins use a reserved bare-tag
  namespace (`'quantum'`, not `'universal-physics-tensor/quantum'`).

**This design picks (d), with a runtime error if a third-party
package registers a bare tag.** Rationale:

- (a) and (b) hide collisions, which is the v0.6.0 doc-integrity
  review's "drift class" pattern — bugs that grow silently.
- (c) is essentially (d) without the enforcement; (d) makes
  the convention machine-checkable.
- The cost of (d) — slightly verbose third-party tags like
  `'@user/qbio.quantum-biological'` — is bounded and predictable.
  The bare-tag reservation for built-ins keeps the v0.6
  inheritance compact.

**Diagnostic:** when a registration is rejected for namespace
violation, the error message names the offending tag, the
expected prefix (derived from `registeredBy`), and points at
`docs/extending-uptf.md`. Following the v0.6.1 Decision #3
principle ("the goal is for the tool to be *correct*, not for it
to ignore inconvenient findings").

### Decision #4 — Multi-regime bridges are first-class via a `RegimeSet`

The proposals doc §6 worked example assumes a regime is a single
value attached to a bridge. The 42-bridge audit (referenced in
v0.6.0-doc-integrity-review.md, §H batch) makes clear that a
significant fraction of bridges sit at the boundary of two
regimes — that's *what makes them bridges*. BE-13 (Jacobson
Einstein-from-thermodynamics) is GR ∩ information-theoretic;
BE-25 (IIT Φ_max) is information-theoretic ∩ neuroscience-of-
consciousness; BE-37 (Shapiro delay) is GR ∩ observational-
astrophysics. Forcing a single regime tag would either falsify
the bridge's positioning or force the taxonomy to invent
hyphenated joint regimes (an explosion in tag count).

**Decision:** the regime field on `BridgeEntry` (introduced in
Proposal 3) is `ReadonlySet<RegimeValueBase>`, not
`RegimeValueBase`. A `BridgeEntry`'s primary regimes can include
2 or more values; the order is irrelevant; the set is canonicalized
for serialization. `LawEntry` (which is per-construction
diagonal in regime, per Proposal 2's flux rule #2) retains a
single-valued regime field.

**Consequence:** the per-axis `RegimeSet` analogue means a bridge
is positioned in the 6-axis tensor by *six sets of regime values*,
not six scalars. This is consistent with v0.6's
`BridgeEquationEntry.bridges: [string, string]` two-element
tuple (a bridge always names two regimes already, just as free
text). The v0.8 work formalizes what v0.6 already encoded
informally.

### Decision #5 — The five v0.6 closed-union types are migrated, not deleted

`PhysicalScale`, `Force`, `Symmetry`, `InformationMeasure` (and
the implicit dimension / topology axes that exist as fields with
no enum yet) are migrated to the regime registry, not deleted.
The v0.7 / v0.8 public-API contract requires:

- The string literal values (`'quantum'`, `'electromagnetic'`,
  `'poincare'`, `'vonNeumann'`, etc.) remain stable. They are
  the `tag` fields of registered built-ins.
- The closed-union *types* remain exported from `src/core/types.ts`
  as the literal-typed aliases described in Decision #2. They
  narrow `string` to the built-in tag set for compile-time
  ergonomics.
- A new `Regime` (or `RegimeValueBase`) type is also exported for
  callers who need the full object form (with provenance, limits,
  tags).

**v0.8 explicitly does NOT:**

- Rename `Symmetry` to `SymmetryRegime` (gratuitous churn).
- Remove `Force = 'gravitational' | ...` (would break every
  v0.6 consumer).
- Re-shape `TensorIndices` (let Proposal 1's `UniversalIndex<Axis>`
  do that work).

The v0.6 closed-union types become **type aliases over the
registry's literal-typed-alias surface**. Same string values,
same compile-time check, plus a new object-form lookup path.

### Decision #6 — Module-load ordering: built-ins register at import time

The MathTS factory-tier system runs at module load and freezes
the scope. Proposal 5's registry runs at module load for the
built-ins (the eight v0.6 closed-union values), then stays open
to runtime additions for third-party callers.

**Concrete ordering:**

1. `src/core/regimes.ts` is the registry module. Its
   side-effecting import registers nothing on its own.
2. `src/core/regimes-builtins.ts` (a sibling module) registers
   the eight v0.6 values via `defineRegime` calls at module
   load. Importing `regimes-builtins` is what makes the
   built-ins available.
3. `src/index.ts` imports `regimes-builtins` for its side
   effects. This guarantees that any consumer of the public
   API sees the built-ins.
4. Third-party packages (`@user/qbio-uptf-regimes`,
   `examples/extending-uptf/`) call `defineRegime` at their own
   module load time. Their tags become visible to subsequent
   `lookupRegime` calls.

**Honest-flag:** module-load ordering is fragile in TypeScript
ESM. A consumer that calls `lookupRegime('scale', 'quantum')`
*before* `src/index.ts`'s side effects have run will get
`undefined`. The mitigation: every public function that consumes
the registry imports `regimes-builtins` explicitly, not transitively.
This is the same defensive style as v0.4.0's connection-layer
imports.

### Decision #7 — Acceptance criteria, restated and tightened

The proposals doc §6.3 acceptance criteria are kept verbatim
where they're testable; tightened where they're under-specified:

| §6.3 criterion | This design's interpretation |
|---|---|
| `defineRegime`, `defineSymmetry`, etc. operational | API exists; types compile; collision/provenance enforced |
| Example downstream package in `examples/extending-uptf/` | In-tree example that *exercises* the public API (not just imports the types); registers ≥1 new regime per axis; passes its own vitest suite |
| v0.6 placeholders (`galilean`, `susy`) re-expressed via the same API as third-party extensions | Each built-in goes through `defineRegime` in `regimes-builtins.ts`; no privileged "internal" registration path exists |
| Provenance recorded and surfaced | Every `RegimeValueBase` has a `provenance` field; `BridgeEntry.regimes` consumers can introspect it; a query helper `provenanceFor(regime)` exists |

**Adversarial-review note:** the v0.8 Implementation Plan must
**not** inherit these acceptance criteria implicitly from this
doc. Each must be re-stated in the plan with a TDD-RED test
spec.

  with the expected provenance, for each of the ~18 v0.6
  built-ins. Plus a meta-test that `listRegimesByAxis` returns
  exactly the v0.6 set (no more, no fewer).

### Tests

- `tests/core/regimes-builtins.test.ts` — new file.
- Existing tests over `PhysicalScale` / `Force` / `Symmetry` /
  `InformationMeasure` consumption must continue to pass without
  modification.

### Deliverable

2 commits: the registration module + literal-typed aliases (one

## Phase 3 — Per-axis convenience APIs

### Motivation

§6.2 of the proposals doc shows `defineSymmetry`,
`defineInformationMeasure` as sibling APIs alongside
`defineRegime`. They're sugar over `defineRegime({ axis: 'symmetry',
… })`, but the per-axis convenience matters for downstream
ergonomics — and the per-axis spec types (e.g. `defineSymmetry`
might accept `generators` and `irreps` fields that don't apply
to other axes).

### Components

- **Task 3.1 — `defineScale`, `defineForce`, `defineSymmetry`,
  `defineInformationMeasure`, `defineDimensionalCategory`,
  `defineTopologicalClass`.** Each is a thin wrapper over
  `defineRegime` that binds the `axis` field and adds axis-
  specific optional fields.
- **Task 3.2 — Per-axis lookup helpers.** `lookupScale(tag)`,
  `lookupForce(tag)`, etc. Each is `lookupRegime(axis, tag)`
  cast to the axis-specific subtype. The return type narrows to
  the axis-specific spec, not the generic `RegimeValueBase`.
- **Task 3.3 — Tests.** Per-axis registration round-trips; per-
  axis lookup returns the axis-specific subtype.
- **Task 3.4 — Migration of `src/core/types.ts`.** Update the
  doc comments on `Symmetry` and `InformationMeasure` to reference
  the registry as the canonical surface. The type aliases stay;
  the doc explains why.

### Tests

- `tests/core/regimes-per-axis.test.ts` — new file.
- `tests/api/public-surface.test.ts` — snapshot regen.

### Deliverable

3 commits across the 4 tasks.

## Phase 4 — Integration with `BridgeEntry`, flux rules

### Motivation

The registry is decorative unless `BridgeEntry` actually carries a
regime field. Per Decision #4, that field is a
`ReadonlySet<RegimeValueBase>`. This phase also wires the regime
axis into Proposal 2's flux rules.

### Components

- **Task 4.1 — Extend `BridgeEntry` (defined in Proposal 3) with
  a `regimes: ReadonlySet<RegimeValueBase>` field.** The field
  is optional in v0.8 (i.e. typed as
  `regimes?: ReadonlySet<RegimeValueBase>`) to preserve the v0.7
  public-API contract. Becomes mandatory in v1.0 or v0.9 (a
  SemVer-major decision).
- **Task 4.2 — Flux-rule integration.** Add a fourth v0.8 flux
  rule to Proposal 2's `UniversalTensor`:
  *RegimeConsistency* — a bridge's `regimes` set must be a
  subset of `{ from.regime, to.regime }`'s closure. Warning only
  in v0.8; promote to error in v0.9 after the catalog audit
  (parallel to Proposal 2's own causality-warning approach).
- **Task 4.3 — Catalog adapter.** A non-breaking helper that
  reads the existing `BridgeEquationEntry.category` /
  `category_name` strings and emits a candidate
  `ReadonlySet<RegimeValueBase>` for physics review. This is
  the **audit-document generator**, not a code transform.
- **Task 4.4 — `LawEntry.regime: RegimeValueBase` (single-valued
  per Decision #4).** Same optionality treatment.
- **Task 4.5 — Tests.** End-to-end test: create a `BridgeEntry`
  via the v0.7 Bridge DSL (Proposal 4) with a `regimes` field;
  add to a `UniversalTensor`; assert the flux rule fires when
  the regime set is inconsistent.

### Tests

- `tests/core/bridge-regimes.test.ts`, `tests/core/flux-regime-
  consistency.test.ts` — new files.
- Existing bridge-catalog tests continue to pass (the new field
  is optional and the existing catalog doesn't set it yet).

### Deliverable

4–5 commits across the 5 tasks.

## Risks

1. **Module-load-ordering fragility.** Per Decision #6, the
   built-ins depend on a side-effecting import. Tree-shaking
   bundlers may elide it. Mitigation: explicit
   `import './regimes-builtins.js'` in every consumer module,
   not just `src/index.ts`; add a runtime guard that throws if
   `listRegimesByAxis('scale')` is empty when the first public
   API is called.
2. **Cross-package collision in the wild.** Two third-party
   packages register the same tag. Namespace-prefix enforcement
   (Decision #3) mitigates within the rules, but a malicious or
   misconfigured caller could still cause confusion. Mitigation:
   provenance + clear error messages; explicit anti-pattern
   section in `docs/extending-uptf.md`.
3. **The closed-base axes don't cover an emerging need.** A
   future proposal needs a seventh axis (e.g.,
   "computational-class") and the closed `RegimeAxisName` union
   blocks it. Mitigation: adding a new axis is a SemVer-minor
   step, the same shape as adding a new symbol to the public
   surface — expected, not pathological.
4. **Set-valued regime fields create combinatorial test
   complexity.** Decision #4 makes
   `BridgeEntry.regimes: ReadonlySet<RegimeValueBase>`, which
   widens the test matrix. Mitigation: keep the v0.8 audit-doc
   per-bridge tagging *paper-only* until physics review converges;
   v0.8 ships the mechanism with empty / single-element sets in
   the catalog itself.
5. **`RegimeType` extension is a power tool with a small
   audience.** Few third parties will actually call
   `defineRegime`. The risk is shipping API surface that nobody
   uses. Mitigation: the
   `examples/extending-uptf/` worked example serves both as
   acceptance criterion and as adoption seed; the
   `docs/architecture/v0.8-regime-tagging-audit.md` deliverable
   directly serves UPT's own internal taxonomy work, so the
   payoff isn't conditional on third-party adoption.

---

## Non-goals

Explicitly NOT in scope for v0.8 Proposal 5:

- **Closed taxonomy of regimes per Decision #1.** The eight v0.6
  closed-union values get registered as built-ins; that's all the
  taxonomy v0.8 commits to. No new built-in regimes (e.g. no
  built-in `'qft'` or `'gr'` regime is added in v0.8) — that's
  v0.9 work once the audit doc lands.
- **Per-bridge regime back-tagging in code.** The
  `BridgeEquationEntry.category` / `category_name` columns stay
  intact; the regime field on `BridgeEntry` is optional and
  unpopulated in v0.8.
- **Removal of `PhysicalScale` / `Force` / `Symmetry` /
  `InformationMeasure` closed-union types.** They become aliases
  over the registry's literal-typed-alias surface, per Decision
  #5. A SemVer-major release could remove them; v0.8 doesn't.
- **A new "computational-class" axis** (or any seventh axis).
  The six axes from Proposal 1 (scale, force, symmetry,
  information, dimension, topology) are the v0.8 closed-base.
- **Cross-axis dependency constraints** (e.g. "a regime on the
  symmetry axis can only be used with these scale-axis regimes").
  Possible future work; out of scope here.
- **Runtime deregistration.** `defineRegime` is monotone; there's
  no `undefineRegime`. Test environments that need to reset state
  can mock the registry module.
- **A "compatibility mode" that auto-derives `BridgeEntry.regimes`
  from `BridgeEquationEntry.category_name`.** Phase 5 Task 4.3
  proposes an *audit-doc generator* that emits **candidates** for
  physics review. There is **no automatic conversion** in v0.8.
- **The v0.7 foundation proposals (1, 2, 3, 4) themselves.** This
  design assumes they have shipped; their own design docs are
  separate artifacts.
- **Promoting the `RegimeConsistency` flux rule from warning to
  error.** Decision #4 / Phase 4 ships the rule as
  warning-only, per the precedent set by Proposal 2's
  causality-warning. Promotion is v0.9 work.

## Open questions to escalate before the Implementation Plan

These don't block this design from landing, but the
Implementation Plan must answer them:

1. **Should `defineRegime` be idempotent for identical
   re-registrations?** Two `defineRegime` calls with byte-
   identical specs (same axis, same tag, same provenance) — is
   that a collision error or a no-op? This design leans
   "collision error" (Decision #3) for clarity, but a no-op
   policy would be more forgiving of accidental double-import.
2. **What's the serialization story?** A `RegimeValueBase`
   round-tripped through JSON loses its registry identity (it's
   a plain object after `JSON.parse`). Consumers that
   re-hydrate via `lookupRegime(axis, tag)` get the canonical
   value back, but the equality check `===` won't hold across
   the round-trip. Document this in `docs/extending-uptf.md`.
3. **Should the audit-doc generator (Phase 5 Task 4.3) be a CLI
   tool or just a TypeScript script?** Other UPT tools live in
   `tools/`; this could too. Or it could be a one-off
   committed-output document. Lean: TypeScript script in
   `tools/regime-tagging-audit/`, output committed as the audit
   markdown file.
4. **Are per-axis specs (e.g., `defineSymmetry` accepting
   `generators` and `irreps` fields) v0.8 scope or v0.9 scope?**
   This design's Phase 3 ships per-axis convenience APIs but
   keeps the spec shape identical to `RegimeValueBase`. Axis-
   specific extra fields (lifted from the proposals doc §6.2's
   `defineSymmetry` example) are a v0.9 add — they're not on
   the v0.8 critical path.
