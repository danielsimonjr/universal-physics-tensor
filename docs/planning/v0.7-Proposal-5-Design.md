# UPT v0.7 — Proposal 5 (`RegimeType` Extension System) — Design

> **Scope:** Design doc for one of eight v0.7+ proposals — Proposal 5,
> the `RegimeType` extension system. Per the proposals doc's own
> sequencing (§11), this proposal lands in **v0.8**, not v0.7. It
> depends structurally on Proposals 1 and 3 from the v0.7 "Foundation
> Consolidation" wave. This design commits to that sequencing and is
> explicit about which v0.7 surfaces it consumes.
>
> **No code changes in this artifact.** Design-only; the
> Implementation Plan is a separate follow-up.
>
> **Inspiration & precedent:** The factory-tier idiom is borrowed
> from MathTS's tiered factory activation (242/273 mathjs factories
> across 18 tiers, per the MathTS 0.1.2 CHANGELOG). The in-tree
> registry pattern is precedented in UPT v0.6.0
> (`CURVATURE_KIND_REGISTRY` in `src/dimensional/curvature-composite.ts:71-110`)
> and v0.6.1 (`VALIDATOR_REGISTRY` in
> `src/dimensional/validator-registry.ts`). Both are *closed-record*
> registries; Proposal 5 extends the pattern to *open* registration.
> The shape difference is load-bearing — Decision #2 below.
>
> **Source for findings:**
> - `docs/planning/UPT v0.70 - Proposals.md` §6, §0, §11.
> - `src/core/types.ts` — the current `PhysicalScale`, `Force`,
>   `Symmetry`, `InformationMeasure` closed unions this proposal
>   replaces with extensible analogues.
> - `src/bridges/index.ts` — `BridgeEquationEntry`, including the
>   `category` / `category_name` free-text columns and the
>   `tractability_class` discriminated union (precedent for adding
>   a typed regime axis alongside the existing free-text column).
> - `src/dimensional/curvature-composite.ts`, `src/dimensional/validator-registry.ts`
>   — closed-record and discriminated-dispatch precedents.

## Honest framing up front

Proposal 5 is **the most under-specified of the eight proposals** in
the source doc. §6.2 shows a worked example but **never closes the
taxonomy of built-in regimes**, never pins the exact union the
extension API extends, and skirts the question of whether a regime is
a string (`'quantum'`) or a structured object. The §6.3 acceptance
criteria read like an API sketch.

This doc commits at every fork; debatable commitments are flagged.
The most consequential is **Decision #1: ship the extension-point
mechanism in v0.8; defer the closed taxonomy of built-ins to a
follow-up.** The taxonomy is a physics-classification problem (which
of 42 bridges sit in which regime?), not engineering; bundling it
risks rushing the physics.

---

## Goal

Introduce a typed, extensible categorical axis for bridges — the
"regime" axis — that:

1. Replaces the **free-text `category` / `category_name`** columns
   on `BridgeEquationEntry` (currently 15 distinct `category_name`
   strings across the 42-bridge catalog, verified by
   `grep -h "category_name:" src/bridges/index.ts | sort -u`)
   with a typed enum-like value.
2. Replaces the closed-union `Symmetry` and `InformationMeasure`
   in `src/core/types.ts` with extensible analogues, **without
   breaking the v0.7 public-API contract**.
3. Permits **third-party packages** to register new regime values
   (`defineRegime({...})`) and have them flow through the bridge
   catalog, validator-registry, and Π-tensor flux rules just as
   the built-ins do — the "factory-tier idiom" of §6.
4. Records **provenance** on every regime value (registering
   package + version) so cross-package catalogs are auditable.
5. Surfaces a **migration story** for the 42 existing bridges:
   each candidate-tagged with one or more regime values (a
   bridge may legitimately sit at the boundary of two regimes —
   e.g. BE-11 Decoherence bridges quantum ↔ classical, BE-13
   Einstein Trace bridges information-thermodynamic ↔ GR).

Sprint succeeds if:

- The extension-point API (`defineRegime` plus per-axis
  convenience APIs, lookup helpers) is operational, type-safe
  end-to-end, and exercised by `examples/extending-uptf/`.
- The five built-in axes (per Proposal 1's `AxisName` union) are
  re-implemented through the extension API itself — same code path
  third parties use ("eat one's own dog food"; eliminates the
  drift class where built-ins drift away from extensions).
- The 42 bridges in `src/bridges/index.ts` are **not** yet re-tagged
  in code. The v0.8 deliverable ships the **mechanism plus an
  audit document** enumerating candidate regime assignments for
  physics review, with no commitment yet to any specific mapping.

## Why this proposal is v0.8, not v0.7

§11 sequences `RegimeType` under v0.8 ("Extension Surface Expansion").
v0.7 is the "Foundation Consolidation" wave (Proposals 1–4). Three
structural reasons:

1. **Proposal 3 (Typed L+B+E discriminated union) must land first.**
   Proposal 5's regime values live as fields on `LawEntry`,
   `BridgeEntry`, `EmergenceEntry`. Without those Cell types as a
   discriminated union, Proposal 5 has no shape to attach to.
2. **Proposal 1 (UniversalIndex layer) introduces `AxisName`.** The
   five built-in axes Proposal 5 extends — scale, force, symmetry,
   information, dimension, topology — are first named in Proposal 1.
3. **Proposal 2 (Sparse semantic catalog) introduces flux rules.**
   The §6.2 example includes a `fluxRules` field on `defineRegime`;
   that field only makes sense once `UniversalTensor` has the
   flux-rule plumbing to consume it.

Proposal 4 (Bridge DSL) is **not** a structural dependency.

## Architectural Decisions (locked)

### Decision #1 — Ship the extension-point mechanism; defer the closed taxonomy of built-ins

§6 lists candidate regimes (classical mechanics, GR, QFT, cosmology,
condensed matter) but does **not** close the taxonomy. Two honest
options:

- **(a)** Commit to a specific built-in taxonomy in v0.8 (e.g., eight
  regimes: classical-mechanics, quantum-mechanics, QFT, GR,
  cosmology, condensed-matter, statistical-mechanics,
  information-theoretic) and back-tag the 42 bridges.
- **(b)** Ship only the extension-point mechanism — the `defineRegime`
  API plus registry plumbing — and treat the closed taxonomy as a
  v0.8.x / v0.9 deliverable requiring per-bridge physics review.

**This design picks (b).** Three reasons:

1. **Bridge categorization is itself a research task.** The 42
   catalog spans contested boundaries (BE-13 Jacobson is GR?
   information-theoretic? both?). Bundling per-bridge tagging would
   rush the physics or pad the sprint past 2–3 weeks.
2. **The extension mechanism is the load-bearing engineering
   work.** Registry design + type-safety + provenance + collision
   rules costs the 2–3 weeks. Adding eight `defineRegime` calls on
   top costs hours.
3. **v0.6.1 precedent.** Decision #7 in v0.6.1 explicitly carves
   bridge re-encoding out of the hygiene sprint for the same reason.

**Honest-flag:** (a) is defensible — crisper "user-visible
improvement" narrative. (b) ships an API hook with no
immediately-visible payoff for read-only catalog consumers. Trade is
**engineering rigor vs. release narrative**; this design picks rigor.
Follow-up regime-tagging work is explicit in the §Deliverable list.

**What ships in v0.8 under (b):**

- `defineRegime` / `defineSymmetry` / etc. API.
- Closed registry of *axis names* (scale, force, symmetry,
  information, dimension, topology — pinned from Proposal 1).
- The eight v0.6 closed-union values re-registered through
  `defineRegime`. These ARE the v0.8 built-ins — inherited from
  v0.6, not re-designed in v0.8.
- `docs/architecture/v0.8-regime-tagging-audit.md` proposing
  regime assignments for each of the 42 bridges, for physics
  review (not for landing).

### Decision #2 — Closed-base axes + open-registration tags, with a string-tag escape hatch

TypeScript enum / union types are closed by design; the factory-tier
idiom requires a runtime extension mechanism. The two in-tree
precedents (`CURVATURE_KIND_REGISTRY`, `VALIDATOR_REGISTRY`) are
**closed** record-keyed-by-union-type registries. Proposal 5's
registry must be **open** — entries added after module-load by
downstream callers.

Conceptual sketch (the v0.8 Implementation Plan re-specs this):

```ts
export type RegimeAxisName =
  | 'scale' | 'force' | 'symmetry'
  | 'information' | 'dimension' | 'topology';

export interface RegimeValueBase {
  readonly axis: RegimeAxisName;
  /** Tag string — globally unique within (axis, package). */
  readonly tag: string;
  readonly displayName: string;
  readonly tags?: ReadonlySet<string>;       // descriptive
  readonly limits?: string;                  // 'ℏ → 0', 'T → 0'
  readonly provenance: RegimeProvenance;
}

export interface RegimeProvenance {
  readonly registeredBy: string;   // npm package name
  readonly version: string;
  readonly registeredAt: number;
}

const REGIME_REGISTRY:
  Map<RegimeAxisName, Map<string, RegimeValueBase>> = new Map();

export function defineRegime(spec: Omit<RegimeValueBase, 'provenance'>
  & { registeredBy: string; version: string }): RegimeValueBase;

export function lookupRegime(
  axis: RegimeAxisName, tag: string,
): RegimeValueBase | undefined;

export function listRegimesByAxis(
  axis: RegimeAxisName,
): readonly RegimeValueBase[];
```

**Three structural commitments:**

1. **The `tag` field is `string`, not a literal-typed union.**
   This is the string-tag escape hatch. TypeScript's type system
   cannot constrain third-party tag values at compile time without
   consuming the third-party module. Cross-package consumers get
   **runtime lookup with `undefined` failure**, not compile-time
   tag validity. Within a single package (including UPT's
   built-ins), a literal-typed alias narrows further:
   ```ts
   export type BuiltinScaleTag =
     | 'quantum' | 'mesoscopic' | 'classical' | 'cosmological';
   export const ScaleRegimes: Record<BuiltinScaleTag, RegimeValueBase>
     = { /* … */ };
   ```
   Dual surface (string-keyed registry + literal-typed alias for
   built-ins) gives both open-extension and compile-time safety.
2. **The `axis` axis is closed.** New axes (e.g. a hypothetical
   "computational-class") require a SemVer-minor UPT release, not
   a third-party registration. This is the "closed-base" half. An
   open axis namespace would make cross-package catalog merging
   intractable.
3. **Provenance is mandatory, not optional.** The `registeredBy`
   and `version` fields are required parameters of `defineRegime`,
   not best-effort. The audit trail matters when two packages
   collide or when a downstream asks "where did this regime come
   from?". Missing provenance is a TypeScript compile error.

**Why not a sealed class hierarchy?** Classes-as-discriminants work
in Java/C#, less well in TypeScript ESM. UPT's existing AST nodes
are plain readonly-object literals with a `kind` discriminant (see
`CurvatureCompositeNode<K, S>` at
`src/dimensional/curvature-composite.ts:139`). Proposal 5 follows that
idiom.

**Why not just `string` everywhere?** Migration from `PhysicalScale =
'quantum' | ...` (compile-checked) to `string` (no checks) is a strict
regression for built-in callers. The dual-surface preserves the
compile-time check for built-ins while opening the runtime extension
point for third parties.

### Decision #3 — Namespaced-tag + first-write-wins, with a runtime error on bare-tag misuse

Two third-party packages both calling `defineRegime({ axis: 'scale',
tag: 'mesoscopic-bio', ... })` present a collision. Honest options:

- (a) First-write-wins with a warning (second call silently dropped).
- (b) Last-write-wins (second call overwrites; extant refs become
  stale).
- (c) Throw on collision; require scope-prefixed tags
  (`'@user/qbio.mesoscopic-bio'`).
- (d) Namespaced-tag with **mandatory prefix** enforced at
  registration time (the tag's first segment must equal
  `registeredBy`). UPT's own built-ins use a reserved bare-tag
  namespace (`'quantum'`, not
  `'universal-physics-tensor/quantum'`).

**Pick (d), with a runtime error if a third-party registers a bare
tag.** Rationale:

- (a) and (b) hide collisions — the v0.6.0 doc-integrity review's
  "drift class" pattern; bugs that grow silently.
- (c) is essentially (d) without the enforcement.
- (d)'s cost — verbose third-party tags like
  `'@user/qbio.quantum-biological'` — is bounded and predictable.

**Diagnostic:** when a registration is rejected for namespace
violation, the error names the offending tag, the expected prefix
(derived from `registeredBy`), and points at `docs/extending-uptf.md`.
Following v0.6.1 Decision #3: "the goal is for the tool to be
*correct*, not for it to ignore inconvenient findings."

### Decision #4 — Multi-regime bridges are first-class via a `RegimeSet`

The §6.2 example assumes a regime is a single value. The 42-bridge
audit (referenced in v0.6.0-doc-integrity-review.md, batch H) makes
clear that a significant fraction of bridges sit at the boundary of
two regimes — *that's what makes them bridges*. BE-13 (Jacobson) is
GR ∩ information-theoretic; BE-25 (IIT Φ_max) is information-theoretic
∩ neuroscience-of-consciousness; BE-37 (Shapiro) is GR ∩
observational-astrophysics. Forcing a single regime tag would either
falsify the bridge's positioning or force the taxonomy to invent
hyphenated joint regimes (a combinatorial explosion in tag count).

**Decision:** the regime field on `BridgeEntry` (introduced by Proposal
3) is `ReadonlySet<RegimeValueBase>`, not `RegimeValueBase`. A bridge's
primary regimes can include 2+ values; order irrelevant; the set is
canonicalized for serialization. `LawEntry` (which is per-construction
diagonal in regime, per Proposal 2's flux rule #2) retains a
single-valued regime field.

**Consequence:** the per-axis `RegimeSet` analogue means a bridge is
positioned in the 6-axis tensor by *six sets of regime values*, not
six scalars. This is consistent with v0.6's
`BridgeEquationEntry.bridges: [string, string]` two-element tuple
(a bridge already names two regimes, just as free text). v0.8
formalizes what v0.6 already encoded informally.

### Decision #5 — The five v0.6 closed-union types are migrated, not deleted

`PhysicalScale`, `Force`, `Symmetry`, `InformationMeasure` (plus the
implicit dimension / topology axes that exist as fields with no enum
yet) are migrated to the registry, not deleted. The v0.7 / v0.8
public-API contract requires:

- The string-literal values (`'quantum'`, `'electromagnetic'`,
  `'poincare'`, `'vonNeumann'`, etc.) remain stable. They are the
  `tag` fields of registered built-ins.
- The closed-union *types* remain exported from `src/core/types.ts`
  as literal-typed aliases (per Decision #2) that narrow `string` to
  the built-in tag set.
- A new `Regime` (or `RegimeValueBase`) type is also exported for
  callers who need the full object form (with provenance, limits).

**v0.8 explicitly does NOT:**

- Rename `Symmetry` → `SymmetryRegime` (gratuitous churn).
- Remove `Force = 'gravitational' | ...` (would break every v0.6
  consumer).
- Re-shape `TensorIndices` (let Proposal 1's `UniversalIndex<Axis>`
  do that).

The v0.6 closed-union types become **type aliases over the registry's
literal-typed-alias surface**. Same string values, same compile-time
check, plus a new object-form lookup path.

### Decision #6 — Module-load ordering: built-ins register at import time

MathTS's factory-tier system runs at module load and freezes scope.
Proposal 5's registry runs at module load for built-ins, then stays
open to runtime additions for third-party callers.

Ordering:

1. `src/core/regimes.ts` — registry module; its import alone
   registers nothing.
2. `src/core/regimes-builtins.ts` — sibling module that calls
   `defineRegime` for the eight v0.6 values at module load.
3. `src/index.ts` does `import './core/regimes-builtins.js'` for
   side effects (the `.js` extension is required per CLAUDE.md's
   ESM rule).
4. Third-party packages call `defineRegime` at their own module
   load time.

**Honest-flag:** module-load ordering is fragile in TypeScript ESM. A
consumer calling `lookupRegime('scale', 'quantum')` *before*
`src/index.ts`'s side effects have run will get `undefined`.
Mitigation: every public function that consumes the registry imports
`regimes-builtins` explicitly, not transitively (the same defensive
style as v0.4.0's connection-layer imports). Also add a runtime guard
that throws if `listRegimesByAxis('scale')` is empty at first
public-API call.

### Decision #7 — Acceptance criteria, restated and tightened

The §6.3 criteria are kept where testable; tightened where
under-specified:

| §6.3 criterion | This design's interpretation |
|---|---|
| `defineRegime`, `defineSymmetry`, etc. operational | API exists; types compile; collision/provenance enforced |
| Example downstream package in `examples/extending-uptf/` | In-tree example that *exercises* the public API (not just imports the types); registers ≥1 new regime per axis; passes its own vitest suite |
| v0.6 placeholders (`galilean`, `susy`) re-expressed through the same API as third-party extensions | Every built-in goes through `defineRegime` in `regimes-builtins.ts`; no privileged "internal" registration path |
| Provenance recorded and surfaced | Every `RegimeValueBase` has a `provenance` field; consumers can introspect it via a `provenanceFor(regime)` helper |

**Adversarial-review note (v0.5.0 carry-forward):** the Implementation
Plan must **not** inherit these criteria implicitly from this doc.
Each must be re-stated in the plan with a TDD-RED test spec.

## Phase 4 — Integration with `BridgeEntry`, flux rules

### Motivation

The registry is decorative unless `BridgeEntry` carries a regime
field. Per Decision #4 it's a `ReadonlySet<RegimeValueBase>`. This
phase also wires the regime axis into Proposal 2's flux rules.

### Components

- **Task 4.1 — Extend `BridgeEntry`** (Proposal 3) with
  `regimes?: ReadonlySet<RegimeValueBase>`. Optional in v0.8;
  becomes mandatory in v0.9 / v1.0 (SemVer-major).
- **Task 4.2 — Flux rule.** *RegimeConsistency* — a bridge's
  `regimes` set must be a subset of `{ from.regime, to.regime }`'s
  closure. Warning-only in v0.8; promote to error in v0.9 after
  the audit (parallel to Proposal 2's causality-warning).
- **Task 4.3 — Catalog adapter.** Non-breaking helper that reads
  `BridgeEquationEntry.category` / `category_name` and emits
  *candidate* `ReadonlySet<RegimeValueBase>` for physics review.
  **Audit-document generator, not a code transform.**
- **Task 4.4 — `LawEntry.regime: RegimeValueBase`** (single-valued
  per Decision #4). Same optional treatment.
- **Task 4.5 — Tests.** End-to-end: build a `BridgeEntry` via the
  Bridge DSL (Proposal 4) with `regimes`; add to a
  `UniversalTensor`; flux rule fires on inconsistency.

### Tests

- `tests/core/bridge-regimes.test.ts`,
  `tests/core/flux-regime-consistency.test.ts` (new).
- Existing bridge-catalog tests pass unchanged.

### Deliverable

4–5 commits.

## Risks

1. **Module-load-ordering fragility.** Built-ins depend on a
   side-effecting import; tree-shaking bundlers may elide it.
   Mitigation: explicit `import './regimes-builtins.js'` in every
   consumer module; runtime guard throwing if
   `listRegimesByAxis('scale')` is empty at first public-API call.
2. **Cross-package collision in the wild.** Misconfigured callers
   can still cause confusion despite namespace-prefix enforcement.
   Mitigation: provenance + clear error messages; explicit
   anti-pattern section in `docs/extending-uptf.md`.
3. **Closed-base axes don't cover an emerging need.** A future
   proposal needs a seventh axis. Mitigation: adding an axis is a
   SemVer-minor step, same shape as a new public-API symbol.
4. **Set-valued regime fields widen the test matrix** (Decision
   #4). Mitigation: keep v0.8 audit-doc tagging paper-only;
   catalog cells stay empty / single-element in v0.8 itself.
5. **`RegimeType` extension is a power tool with a small audience.**
   Risk of shipping API nobody uses. Mitigation: the in-tree
   example is both acceptance criterion and adoption seed; the
   audit doc directly serves UPT's own internal taxonomy work,
   so the payoff is not conditional on third-party adoption.

## Non-goals

Explicitly NOT in scope for v0.8 Proposal 5:

- **Closed taxonomy of regimes** (Decision #1). The eight v0.6
  closed-union values are the only built-ins v0.8 ships. New
  built-ins (`'qft'`, `'gr'`, etc.) are v0.9 work, post-audit.
- **Per-bridge regime back-tagging in code.** The
  `BridgeEquationEntry.category` / `category_name` columns stay;
  `BridgeEntry.regimes` is optional and unpopulated in v0.8.
- **Removal of `PhysicalScale` / `Force` / `Symmetry` /
  `InformationMeasure`.** They become aliases over the registry's
  literal-typed surface (Decision #5). SemVer-major could remove
  them; v0.8 doesn't.
- **A seventh axis** ("computational-class" etc.). Six axes only.
- **Cross-axis dependency constraints.** Possible future work.
- **Runtime deregistration.** `defineRegime` is monotone.
- **Auto-deriving `BridgeEntry.regimes` from
  `BridgeEquationEntry.category_name`.** Task 4.3 emits
  **candidates** for physics review — no automatic conversion.
- **The v0.7 foundation proposals themselves** (1, 2, 3, 4).
  Separate design docs.
- **Promoting `RegimeConsistency` from warning to error.**
  Warning-only in v0.8; promotion is v0.9.

## Open questions to escalate before the Implementation Plan

These don't block this design but the Implementation Plan must
answer them:

1. **`defineRegime` idempotency.** Two calls with byte-identical
   specs — collision error or no-op? Design leans collision-error
   (Decision #3); no-op would be more forgiving of double-import.
2. **Serialization.** A `RegimeValueBase` round-tripped through
   JSON loses registry identity. `===` won't hold; consumers must
   re-hydrate via `lookupRegime`. Document in
   `docs/extending-uptf.md`.
3. **Audit-doc generator (Task 4.3): CLI tool or one-off script?**
   Lean: TS script in `tools/regime-tagging-audit/`, output
   committed as the audit markdown.
4. **Per-axis spec extras (`defineSymmetry`'s `generators` /
   `irreps`) — v0.8 or v0.9?** Phase 3 keeps spec shape identical
   to `RegimeValueBase`; axis-specific extras are v0.9.
