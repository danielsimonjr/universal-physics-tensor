# v0.14 — `mergeAxes` / `splitAxis` for `LabeledTensor` (Design Note)

> **STATUS: DEFERRED — BLOCKED on a prerequisite (Adam vet, RED 2026-06-16).**
> The Adam adversarial review found this design rests on an assumption the
> codebase already violates: the helpers address axes by label key and rely on
> `canonicalLabelOrder` (sorted keys, `labeled-tensor.ts:151`) tracking the
> engine's positional axis order — but `transpose` (`:297`) returns labels
> UNCHANGED after permuting the engine axes, desyncing canonical-key order from
> engine-axis order (and `contract`'s result labels, `:233-263`, are not in
> sorted order either). So "contiguous in canonical order" is the wrong invariant
> and `engine.reshape` (which fuses STORAGE-adjacent axes, `float64-engine.ts:437`)
> would fuse the wrong data on any post-`transpose`/`contract` tensor — silent
> numerical corruption, no throw. `mergeAxes`/`splitAxis` cannot be made correct
> without first establishing the class-wide invariant "canonicalLabelOrder index
> == engine axis position" (e.g. by storing an explicit key→axis map, or
> reordering the labels record inside `transpose`/`contract`). That is a
> foundation fix to `LabeledTensor`'s internal model with its own blast radius
> (it changes `transpose`/`contract` semantics) and warrants its OWN design +
> Adam+Eve vet. **This feature is therefore blocked pending that prerequisite
> fix; it is not shipped in v0.14.** The body below is retained as the spec to
> resume from ONCE the axis-ordering invariant is fixed — at which point the
> helpers should address axes in ENGINE-AXIS space (Adam's MUST-FIX #1/#2) and
> add a transposed-tensor round-trip test (MUST-FIX #3).


Closes the deferred rank-changing-reshape gap. `LabeledTensor.reshape`
(`src/core/labeled-tensor.ts:310`) is rank-preserving only — it throws
`RankPreservationError` (`:122`) for any rank change, and its docstring + the
error message both promise "a future `mergeAxes` / `splitAxis` helper for rank
changes." This note specifies those two helpers.

## The one design question (and its resolution)

A `LabeledTensor` carries exactly one `UniversalIndex` label per axis (the
constructor enforces `Object.keys(labels).length === tensor.shape.length`,
`:180`). The engine layer (`engine.reshape`) already handles the raw data; the
ONLY new work is **label bookkeeping**. The open question the scoping flagged:
*what `UniversalIndex` does a merged axis carry?* The identity-contraction
machinery (Decision #3, id-equality matching) has no notion of a "product
index", so a merged axis has no canonical identity to synthesize.

**Resolution: the caller supplies it.** `mergeAxes` takes the new merged-axis
label (key + `UniversalIndex`) as an explicit argument; `splitAxis` takes the
full set of replacement labels. No composite-id scheme is invented — the helpers
are pure structural reshape + a label-record rewrite, and the physics-identity
decision stays with the caller (consistent with the existing house rule that the
constructor never fabricates labels). This sidesteps the design gap entirely.

## Axis addressing

Axis position ↔ label is mediated by `canonicalLabelOrder` (sorted label keys,
`:151`), so "axis i" means the i-th key in sorted order. To keep the API
unambiguous and independent of that internal ordering, both helpers address axes
by **label key**, and `mergeAxes` requires the merged keys to be **contiguous in
canonical order** (a non-contiguous merge would require an implicit transpose —
out of scope; the caller can `transpose` first). The helper computes the
canonical order internally and validates contiguity.

## API

```ts
// Fuse a contiguous run of axes (by label key) into ONE axis carrying a
// caller-supplied label. Rank R → R − (keys.length − 1).
mergeAxes(
  keys: readonly string[],              // ≥2 existing label keys, contiguous in canonical order
  merged: { key: string; index: UniversalIndex<AxisName> },
): LabeledTensor

// Split ONE axis (by label key) into several, with caller-supplied sub-labels
// whose sizes multiply to the original axis size. Rank R → R + (parts.length − 1).
splitAxis(
  key: string,                          // existing label key
  parts: readonly { key: string; index: UniversalIndex<AxisName>; size: number }[], // ≥2
): LabeledTensor
```

Both return a NEW `LabeledTensor` (immutable, like `reshape`/`transpose`).

## Semantics

**`mergeAxes`:**
1. Validate: `keys.length ≥ 2`; every key exists in `this.labels`; the keys form
   a contiguous block in `canonicalLabelOrder(this.labels)`; `merged.key` does
   not collide with a surviving label key.
2. New shape: the merged axis size = product of the merged axes' sizes; the
   surviving axes keep their sizes. Built in canonical order so it matches what
   `engine.reshape` expects.
3. `engine.reshape(this.tensor, newShape)`.
4. New labels record: drop the merged keys, insert `merged.key → merged.index`.
5. `new LabeledTensor(reshaped, engine, newLabels)`.

**`splitAxis`:**
1. Validate: `key` exists; `parts.length ≥ 2`; every `parts[i].size` is a
   positive integer; `∏ parts[i].size === ` the original axis size; no
   `parts[i].key` collides with a surviving label key or another part key.
2. New shape: replace the split axis's size with the part sizes (in `parts`
   order), at the split axis's canonical position.
3. `engine.reshape`, then build new labels (drop `key`, insert each part), and
   wrap.

## Errors

Reuse `UPTError` subclasses where possible; add minimal new ones only as needed:
- `AxisMergeError extends UPTError` — non-contiguous keys, <2 keys, unknown key,
  or merged-key collision (one class, message states which).
- `AxisSplitError extends UPTError` — size product mismatch, <2 parts, unknown
  key, non-positive/non-integer size, or part-key collision.

Both set `.name` + `Object.setPrototypeOf` per the repo error convention
(`IdentityConflictError`/`RankPreservationError` precedent, `:100`/`:122`). These
are NOT `@public` unless `LabeledTensor` itself is surfaced (it is `@public` at
`:169`, so the new methods are `@public`; the error classes follow the
`RankPreservationError` precedent which IS `@public`).

## Public surface

`LabeledTensor` is already `@public`. Adding two methods does NOT change the
runtime export snapshot (methods are not separate exports). The two new error
classes, IF `@public` (mirroring `RankPreservationError`), must be added to
`src/index.ts` + `ALL_TYPE_EXPORTS` + the runtime list IF they are currently
re-exported the way `RankPreservationError` is — verify whether
`RankPreservationError` is on the public manifest first; match its treatment
exactly (a new error sibling should be surfaced the same way its sibling is, or
not at all — no half-exported error).

## Test plan

- `mergeAxes`: a 2×2×2 → merge two adjacent axes → 4×2, value-identity preserved
  (read back via `engine.toNested`); labels record correct; round-trips with
  `splitAxis` back to the original shape + labels. Non-contiguous keys throw;
  <2 keys throw; merged-key collision throws.
- `splitAxis`: 4×2 → split the 4-axis into 2×2 → 2×2×2; size-product mismatch
  throws; part-key collision throws; non-integer size throws.
- Round-trip: `merge` then `split` (and vice-versa) recovers the original data
  (the engine reshape is its own inverse for matching shapes) and a labels record
  equal to the original when the caller supplies the original labels back.
- Regression: existing `reshape` rank-preservation tests
  (`tests/core/labeled-tensor.test.ts:210`) unchanged; full suite green.

## Open questions for the Adam+Eve vet

1. Address axes by label KEY (this note) vs by integer position? (Lean: key —
   the class is label-first; positions are an internal detail via
   `canonicalLabelOrder`.)
2. Require contiguity, or auto-transpose non-contiguous merges? (Lean: require
   contiguity + throw; auto-transpose hides a cost and a label-order change.)
3. Error-class treatment vs `RankPreservationError`: surface the two new error
   classes exactly as `RankPreservationError` is surfaced (verify its manifest
   status first), or keep them internal? (Lean: match the sibling precedent.)
