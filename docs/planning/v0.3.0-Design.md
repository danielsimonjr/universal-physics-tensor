## 1. Context

UPT v0.2.1 ([commit `87f437b`, tag `v0.2.1`, 2026-05-13](https://github.com/danielsimonjr/universal-physics-tensor/releases/tag/v0.2.1)) closed the v0.2.x line with the tensor algebra layer plus one post-release correctness fix. The catalog stands at 40/40 AST encodings, 1,208 tests + 3 todo, 0 invalid bridges. v0.2.x supports variance-typed indices and Einstein contraction but lacks the metric tensor — same-variance label pairs (`A^μ B^μ`) are rejected with `VarianceMismatchError` because there's no machinery to raise/lower.

v0.3.0 adds the **metric layer**: first-class `metric-tensor` nodes, the Kronecker delta as identity primitive, partial-derivative AST nodes for spacetime derivatives, and explicit `raise()` / `lower()` helpers. Per the TensorJS roadmap (§12 of v0.2.0-Design.md), v0.3.5 then adds the mathjs numerical-contraction backend; v0.4.0 adds Christoffel symbols + covariant derivative.

## 2. Scope

### In scope

1. **Part-VIII spec module**: `docs/specification/Part-VIII-Metric-Layer.md` with TENSOR-RULE markers + bidirectional drift guard (analog to Part-VII). Documents metric-tensor semantics, raise/lower rules, Kronecker delta, partial-derivative invariants.
2. **Three new AST node kinds**:
   - `metric-tensor` (Decision 1b): rank-2 tensor with same-variance indices, signature, per-encoding dimension
   - `tensor-partial-derivative` (Decision 5 Adam-shape): `∂_μ T^ν` with explicit `wrt` coordinate operand
   - `kronecker-delta` (Decision 7a): identity tensor for inverse-metric consistency checks and future v0.4.0 contractions
3. **User-facing helpers**:
   - `metric(name, indices, dim, signature)` constructs a `metric-tensor`
   - `raise(operand, gInverse, label)` / `lower(operand, g, label)` with **internal alpha-conversion** (Decision 8a) — helper renames operand-mismatched labels in the metric so labels align at call site
   - `pderiv(of, wrt, wrtIndex)` constructs a `tensor-partial-derivative`
   - `kronecker(upperLabel, lowerLabel, dimension)` constructs a `kronecker-delta`
4. **Validator extension**: new `MetricTensorValidationResult`, `PartialDerivativeValidationResult`, `KroneckerDeltaValidationResult` shapes following the v0.2 `{dim, freeIndices}` carrier pattern; per-kind validation rules; new error types (`InvalidMetricRankError`, `MetricSignatureError`); updated error messages on `VarianceMismatchError` AND `IndexLabelCollisionError` to suggest `raise()` / `lower()` when triggered by tensor-product structure.
5. **`InverseMetricInconsistencyWarning` (optional check)**: when both `g_μν` and `g^μν` are present in scope as `metric-tensor` nodes, the validator may attempt the contraction `g^μν · g_νλ` and warn if the result doesn't equal `kronecker(μ, λ)`. Decision 6+7 made this implementable.
6. **Worked example — GR-flavored bridge structural rewrite**: encode at least one existing bridge using new primitives. Candidate: a gravitational-lensing or geodesic-related bridge (chosen during execution; both reasoners suggested Schwarzschild-shape or post-Newtonian as cleanest).
7. **R-tier polish**: any bridges that picked up new `known_issues` entries since v0.2.1 get normalized (lightweight, follows Task 13 pattern from v0.2.0).

### Explicitly out of scope (deferred to later versions)

- **Faraday tensor `F_μν` mixed-component dimensions** (Decision 3): deferred to **v0.5.0+** with explicit BREAKING-change flag. The single `dim: Dimension` field on `metric-tensor` and `tensor-symbol` bakes in the uniform-dimension assumption that v0.5.0 will need to refactor. Both reasoners flagged this as the riskiest forward-compat liability of v0.3.0. See §14.
- **Christoffel symbols `Γ^λ_μν`**: v0.4.0 ("connection layer"). The v0.3.0 design intentionally provides `∂_μ g_νλ` as a building block — verified composable by Adam's trace.
- **Covariant derivative `∇_μ`**: v0.4.0.
- **Riemann curvature tensor `R^μ_νρσ`, Ricci, Bianchi**: v0.4.0+.
- **mathjs numerical-contraction backend**: v0.3.5 ("numerical-backend release").
- **Symbolic inverse-metric derivation** (Decision 6 (b)/(c)): v0.3.0 ships with two separate `metric-tensor` declarations; symbolic inversion is deferred.
- **Static-vs-dynamic metric distinction**: v0.4.0 work. v0.3.0 treats every `metric-tensor` as a potentially-varying field; `∂_μ g_νλ` always produces a non-trivial result. Future work may add a `varying: boolean` or `derivative-zero: boolean` field for optimization; v0.3.0 doesn't preclude this addition.
- **Tensor-with-mixed-component-dimensions** (broader than Faraday): same v0.5.0+ deferral.

## 3. Approach: spec-first, minimal AST extension, helper-mediated ergonomics

Both reasoning models reached **Approve-with-concerns / high confidence** on the consolidated design after two rounds of review. The pattern adopted from v0.2.0 holds: write Part-VIII first; implement minimal runtime to match; bidirectional drift guard.

Key architectural insight: **`computeContraction` barely changes in v0.3.0**. The metric naturally composes as a `tensor-product` arg. `lower(A^μ, g_μν, 'μ')` constructs `tensor-product([g_μν, A^μ])`; existing v0.2 contraction sees `g`'s `(μ:lower, ν:lower)` and `A`'s `μ:upper`; the μ pair contracts; result has free `ν:lower`. The raise/lower API is sugar around `tensor-product` construction; the contraction algebra is unchanged.

What IS genuinely new validator-side work:
- New AST kinds and their `validateMetricTensor`, `validatePartialDerivative`, `validateKroneckerDelta` functions
- Helper alpha-conversion logic (the metric's labels get renamed to align with operand's labels before construction)
- Error message updates with raise/lower suggestions
- Optional `InverseMetricInconsistencyWarning` machinery

## 4. AST extension

### Existing node types (v0.2.1, unchanged)

```typescript
| { kind: 'symbol'; name: string; dim: Dimension }
| { kind: 'op'; op: '+'|'-'|'*'|'/'|'^'; args: ExprNode[] }
| { kind: 'integral'; over: ExprNode; integrand: ExprNode }
| { kind: 'derivative'; of: ExprNode; wrt: ExprNode }
| { kind: 'tensor-symbol'; ... role?: Role }
| { kind: 'tensor-product'; args: ReadonlyArray<ExprNode> }
```

### New node types (v0.3.0)

```typescript
| { kind: 'metric-tensor';
    name: string;                  // 'g', 'eta', 'g_inverse', etc.
    indices: ReadonlyArray<{label: string; variance: 'upper'|'lower'}>;
                                   // exactly 2 indices, SAME variance
    signature: string;             // '+,-,-,-' or '+,+,+,-' or '+,+,+'
    dim: Dimension;                // per-encoding (Decision 4)
  }

| { kind: 'tensor-partial-derivative';
    of: ExprNode;
    wrt: ExprNode;                 // coordinate tensor; typically tensor-symbol with role: 'coordinate'
    wrtIndex: { label: string; variance: 'lower' };
                                   // the operator's covariant index (always lower)
  }

| { kind: 'kronecker-delta';
    indices: ReadonlyArray<{label: string; variance: 'upper'|'lower'}>;
                                   // exactly 2 indices, MIXED variance (one upper, one lower)
    dim: Dimension;                // typically DIMENSIONLESS for the canonical δ^μ_ν
  }
```

### Type-level constraints (enforced by validator)

| Node | Rank | Variance constraint | Other invariants |
|---|---|---|---|
| `metric-tensor` | exactly 2 | both same (upper/upper or lower/lower) | `signature` is a valid string per spec; `dim` is user-specified |
| `tensor-partial-derivative` | rank = of's rank + 1 | `wrtIndex.variance === 'lower'` always | `wrt` MUST be tensor-like (tensor-symbol, ideally with `role: 'coordinate'`) |
| `kronecker-delta` | exactly 2 | one upper + one lower | typically `dim = DIMENSIONLESS` (the canonical δ^μ_ν) |

## 5. Validator architecture

### New return-carrier interfaces

Following the v0.2 `{dim, freeIndices}` pattern from `TensorSymbolValidationResult`:

```typescript
export interface MetricTensorValidationResult {
  readonly dim: Dimension;
  readonly freeIndices: Map<string, { upper: number; lower: number }>;
}

export interface PartialDerivativeValidationResult {
  readonly dim: Dimension;
  readonly freeIndices: Map<string, { upper: number; lower: number }>;
  readonly role?: Role;  // inherited from `of` per Adam-confirmed semantics
}

export interface KroneckerDeltaValidationResult {
  readonly dim: Dimension;       // typically DIMENSIONLESS
  readonly freeIndices: Map<string, { upper: number; lower: number }>;
}
```

### Per-kind validation rules

**`metric-tensor`** (validator.ts `infer()` switch case):
- Reject if `indices.length !== 2` with `InvalidMetricRankError`
- Reject if the two indices have different variance (forbidden for v0.3.0; raise/lower deals with cross-variance via the inverse metric) with new `MetricSignatureError`
- freeIndices = both indices (each contributing `{upper: 1}` or `{lower: 1}` to its label)
- Output dim = `node.dim`

**`tensor-partial-derivative`** (validator.ts `infer()` switch case):
- Recursively validate `of`; collect `of`'s `{dim_of, freeIndices_of}` via `inferArgLocal` (the v0.2 local-Map pattern)
- Recursively validate `wrt`; collect `wrt.dim`; **discard wrt's freeIndices** (the operator's index is `wrtIndex`, not `wrt`'s own indices)
- Reject if `wrtIndex.variance !== 'lower'` with new `PartialDerivativeIndexVarianceError`
- Output dim = `divide(dim_of, wrt.dim)`
- Output freeIndices = `freeIndices_of ∪ {wrtIndex.label: lower}`. Reject if `wrtIndex.label` collides with an existing free index from `of` (use `IndexLabelCollisionError` with a partial-derivative-aware message)
- Output `role` inherits from `of` (∂_μ field = field; ∂_μ constant = field-ish, see §13 open question on this)

**`kronecker-delta`** (validator.ts `infer()` switch case):
- Reject if `indices.length !== 2` with `InvalidKroneckerRankError`
- Reject if the two indices have the SAME variance with `KroneckerVarianceError` (must be one upper, one lower)
- freeIndices = both indices contribute appropriately
- Output dim = `node.dim` (typically DIMENSIONLESS)

### Updated error messages (existing types, refreshed for raise/lower discoverability)

- `VarianceMismatchError`: append `"Hint: if you intended to contract these via the metric, use raise(operand, gInverse, label) or lower(operand, g, label)."` to the existing message text.
- `IndexLabelCollisionError`: when the colliding label appears in a `tensor-product` whose call site was a raise/lower helper, the error includes the helper context and suggests using a DIFFERENT inverse metric (not the same metric with mismatched variance). Adam's specific catch.

### `wrt` argument semantics — spec comment

Both reasoners agreed this needs explicit explanation:

> **The `tensor-partial-derivative` node ignores `wrt`'s own free indices.** This is deliberate: `∂/∂x^μ` is an operator whose index `μ` is *covariant* (lower), regardless of the variance of the coordinate's index. The `wrt` argument is used for its dimension only (for the `divide(of.dim, wrt.dim)` rule). The operator's index is supplied separately via `wrtIndex`. This distinguishes the differentiation operator `∂_μ` from the coordinate differential `dx^μ`.

This comment lives in both Part-VIII (spec) and the JSDoc of `validatePartialDerivative` (implementation).

## 6. User-facing API helpers

```typescript
// src/dimensional/metric.ts (new file)

export function metric(
  name: string,
  indices: ReadonlyArray<{label: string; variance: 'upper'|'lower'}>,
  dim: Dimension,
  signature: string,
): MetricTensorNode;

export function kronecker(
  upperLabel: string,
  lowerLabel: string,
  dim?: Dimension,  // defaults to DIMENSIONLESS
): KroneckerDeltaNode;

/** Raise an index of `operand` via the inverse metric `gInverse`. The helper
 *  performs INTERNAL ALPHA-CONVERSION (Decision 8a) on `gInverse`'s labels
 *  so that one matches `label` and the other is a fresh non-colliding label.
 *  The output is a tensor-product validator can contract through the standard
 *  Einstein rule. */
export function raise(
  operand: ExprNode,
  gInverse: MetricTensorNode,
  label: string,
): TensorProductNode;

export function lower(
  operand: ExprNode,
  g: MetricTensorNode,
  label: string,
): TensorProductNode;

export function pderiv(
  of: ExprNode,
  wrt: ExprNode,
  wrtIndex: { label: string; variance: 'lower' },
): TensorPartialDerivativeNode;
```

### Helper alpha-conversion (Decision 8a) — detail

`raise(A_μ, g_inverse_αβ, 'μ')` semantics:

1. Helper inspects `gInverse.indices` and `operand`'s free indices.
2. Picks one of `gInverse`'s labels (say α) to rename to `μ` (so it'll contract with operand's μ).
3. Picks the OTHER `gInverse` label (β) and renames to a fresh label NOT in `operand`'s free-indices map (e.g., `β'` or `ν_fresh`). This becomes the FREE index on the output.
4. Returns `{kind: 'tensor-product', args: [renamed-gInverse, operand]}`.

Helper implementation is a pure function. The fresh-label generator uses a deterministic naming scheme (e.g., `<original-label>_<counter>`) to keep error messages debuggable.

## 7. Worked example — gravitational-lensing-shape bridge (preview)

The specific bridge chosen during execution (Task 7 of the implementation plan). Sketch using the new primitives:

```typescript
// Hypothetical: deflection angle = (4GM/c²) · ∫ (∂_μ φ) (g^μν n_ν) dλ
const g_inverse = metric('g_inverse',
  [{label: 'μ', variance: 'upper'}, {label: 'ν', variance: 'upper'}],
  GEOMETRIZED_METRIC_DIM,
  '+,-,-,-');

const phi = tsym('phi',  // gravitational potential (scalar field)
  [],
  POTENTIAL_DIM);

const n = tsym('n',      // unit vector along line of sight
  [{label: 'ν', variance: 'lower'}],
  DIMENSIONLESS);

const x_coord = tsym('x',
  [{label: 'α', variance: 'upper'}],
  LENGTH,
  'coordinate');

const grad_phi = pderiv(phi, x_coord, {label: 'μ', variance: 'lower'});
// grad_phi has free index μ:lower, dim = POTENTIAL_DIM / LENGTH

const raised_grad = raise(grad_phi, g_inverse, 'μ');
// raised_grad: free index μ:upper (the renamed inverse-metric pair), dim composes

const contracted = contract(raised_grad, n);
// μ contracts; result is a scalar
```

Exact bridge selection happens at execution time. Both reasoners suggested gravitational lensing or Schwarzschild post-Newtonian as good candidates because they exercise: metric, inverse metric, partial derivative, raise, contract — i.e., the entire v0.3.0 surface in one bridge.

## 13. Risks and open questions

### Risks both reasoners flagged

- **Faraday-deferral cascade**: `metric-tensor.dim: Dimension` is a single field; bakes in uniform-component-dim assumption. v0.5.0+ Faraday work will require refactoring `metric-tensor.dim` AND `tensor-symbol.dim` together. Both reasoners rate this as v0.3.0's highest forward-compat liability. Documented explicitly in §14.
- **Helper alpha-conversion edge cases**: when `operand` has many free indices and `gInverse` has labels colliding with several of them, the fresh-label generation must avoid ALL such collisions. Test coverage in `tests/dimensional/raise-lower.test.ts` must include the "operand has 4+ free indices that all conflict with metric labels" stress case.
- **Static-vs-dynamic metric**: v0.3.0 treats every metric as potentially-varying; `∂_μ g_νλ` always produces a non-trivial result. v0.4.0 Christoffel work may need an "is-constant" flag for optimization. v0.3.0 design doesn't preclude this addition; future work can append a `varying: boolean` field. Adam's specific catch.

### Open questions for review

1. **Should `tensor-partial-derivative.role` always inherit from `of`?** Adam says yes (∂_μ field = field). Edge case: ∂_μ of a `metric-tensor` — what's the role? The metric-tensor doesn't carry a role field in this design. Suggested: pass through `of`'s role if present; default to `'field'` otherwise. Implementer should confirm during execution.
2. **`InverseMetricInconsistencyWarning` strictness.** Should it FAIL the validation (`ok: false`) or just record a violation with `severity: 'warning'`? Adam suggests warn-not-error; this commits us to a `Violation.severity` field (currently violations are all errors). Either add that field in v0.3.0 OR drop the warning and add it back in v0.3.5 with the severity field.
3. **`kronecker(μ, λ, dim)` parameter order**. Should it be `(upper, lower, dim?)` or `(lower, upper, dim?)`? The canonical δ^μ_ν has upper first; suggested `(upper, lower, dim?)` matching convention.
4. **Bridge candidate for worked example.** Both reasoners suggested gravitational lensing or Schwarzschild post-Newtonian. Pin during execution after reviewing current bridge catalog for cleanest tensor structure.
5. **Should `metric-tensor` carry a `varying` field now** for v0.4.0 readiness? Pro: forward-compat. Con: unused in v0.3.0; may rot. Suggest defer until v0.4.0 Christoffel design.

## 14. Forward-compatibility sanity checks

Building on v0.2.0-Design.md §14:

### 14.1 `metric-tensor` and `kronecker-delta` JSON round-trip
Both new node kinds must JSON-serialize losslessly per the v0.2.0 round-trip test pattern (§14.6 of v0.2.0-Design.md). Add to `tests/dimensional/metric-ast-serialization.test.ts`.

### 14.2 `tensor-partial-derivative` JSON round-trip
Same; with extra care that `wrtIndex` (a nested object) survives the trip.

### 14.3 Faraday-cascade explicit flag
The Part-VIII spec INCLUDES a clearly-marked section titled "v0.5.0+ refactor scope: per-component dimension support." This commits the future-self of v0.5.0 to refactoring `metric-tensor.dim`, `tensor-symbol.dim`, and `kronecker-delta.dim` together. The flag lives in the spec so a v0.5.0 design pass starts with this constraint in view.

### 14.4 v0.4.0 covariant-derivative composition test
A "preview test" (in `it.todo` form) that composes `∂_μ g_νλ` and asserts the resulting AST is well-formed. v0.4.0's Christoffel work would activate this test by building on it. Prevents v0.4.0 from discovering composition failures cold.

### 14.5 SemVer posture for new errors
New error types (`InvalidMetricRankError`, `MetricSignatureError`, `InvalidKroneckerRankError`, `KroneckerVarianceError`, `PartialDerivativeIndexVarianceError`) are additive. Existing error-type imports keep working. No breaking changes. v0.3.0 is a minor-version bump per SemVer.

### 14.6 Static-vs-dynamic metric forward-compat
Per §13 open question 5: v0.3.0 doesn't add a `varying` field on `metric-tensor`, but the AST structure permits adding one in v0.4.0 without breaking existing v0.3.0 consumers (optional fields are backward-compatible additions in TypeScript discriminated unions).

### 14.7 mathjs lowering forward-compat (v0.3.5)
The future mathjs backend will receive `metric-tensor` and `kronecker-delta` nodes as inputs and lower them to `math.Matrix` instances. Both nodes' `dim` field + `indices` array provide sufficient information for this lowering, matching the v0.2.0 `tensor-symbol`-to-mathjs path. No additional v0.3.0 metadata needed.

### 14.8 threejs visualization forward-compat (v0.5.0+)
The future threejs viz repo will need to discriminate "this is a metric / inverse metric / Kronecker delta vs a generic field tensor" — the distinct `kind` tags from Decisions 1+7 make this trivial. The original Decision 1(c) (registry-based) would have required threejs to consult an external registry; the chosen 1(b) (first-class node) is viz-friendly.
