# v0.12.0 — Symbolic Bridge Composition (Observable Contract) · Design Note

Pushes composition from NUMERIC-only (`composeEdges` chains `evaluate`
closures, a black box) to SYMBOLIC: composing two bridges produces a new
`ExprNode` (the substituted AST), which is dimensionally validated and
numerically evaluable. This resolves the Observable-contract deferral the
spec flags as the prerequisite (Part-IX-Composition.md §4).

## Background (grounded 2026-06-15)

- `composeEdges(first, second)` (src/composition/compose.ts) pipes `first`'s
  numeric output into `second`'s evaluator. The composed edge has **no
  symbolic form** — just a chained closure.
- Bridge AST modules (e.g. be-16-landauer.ts, be-42-hawking-temperature.ts)
  export full closed-form RHS `ExprNode` trees, BUT in **physics** symbol
  vocabulary (`'M'`, `'T'`, `'k_B'`), not the graph's **quantity** names
  (`'mass'`, `'temperature'`).
- **Missing, must build**: a scalar `ExprNode` evaluator and an `ExprNode`
  substitution helper. Neither exists (verified: validator.ts only infers
  dims; lowering.ts is tensor-oriented; evalFormulaAst is a different AST).
- Part-IX §4 defers the Observable contract, enumerating options (a) a
  breaking `Observable` interface on every evaluator, (b) per-pair
  `BridgeAdapter`s (combinatorial), (c) a lossy numeric cascade. It does
  **not** enumerate the option below.

## The contract — option (d): optional symbolic ExprNode

A bridge edge MAY expose a symbolic form of its target:

```ts
interface BridgeEdge {
  // ... existing fields ...
  /** OPTIONAL: the target quantity as a symbolic ExprNode whose leaf
   *  symbols are EITHER source-quantity NAMES (graph vocabulary) or
   *  registered constant symbols (hbar, c, G, k_B, 8pi, ln2, ...). */
  readonly symbolic?: ExprNode;
}
```

This is **option (d)**: additive (optional → non-breaking), no per-pair
adapters, and it retains dimensional type-safety (the AST validates). The
vocabulary decision is the crux: **leaves are graph quantity-names + a
constant registry**, so a junction substitution threads by source-quantity
name (e.g. `be16Edge.symbolic` has a leaf named `'temperature'`, the source
quantity, not `'T'`).

`Observable` is the shared RETURN contract the spec said was missing — what
`composeSymbolic` produces:

```ts
interface Observable {
  readonly name: string;          // target quantity name
  readonly symbol: string;
  readonly dim: Dimension;        // dimensionally-validated
  readonly expr: ExprNode;        // the composed (substituted) AST
  readonly leaves: readonly string[];   // free leaf symbols (the inputs)
  evaluate(values: Record<string, number>): number;  // numerically executable
}
```

## Building blocks

1. **`CONSTANTS`** (`src/composition/symbolic-constants.ts`) — a
   `Record<string, { value: number; dim: Dimension }>` for the physical
   constants and numeric literals the symbolic forms use, importing the
   SAME SI values from `core/constants.js` the evaluators use (bit-for-bit:
   `HBAR_SI`, `C_SI`, `G_SI`, `K_B_SI`) plus `ln2 = Math.LN2`, `8pi`, `4pi`,
   `2`, `3`.

2. **`evalExpr(node, values)`** (`src/composition/expr-eval.ts`) — a scalar
   `ExprNode` evaluator. Leaf value = `values[name]` ?? `CONSTANTS[name].value`
   ?? `Number(name)` (numeric-literal symbols). Ops: `+ - * / ^` (`^` reads
   the exponent as `Number(arg[1].name)`). `integral` / `derivative` /
   tensor arms throw a clear `SymbolicEvalError` (out of scope — symbolic
   composition targets scalar closed forms). Unknown free symbol with no
   value throws.

3. **`substitute(expr, name, replacement)`** (`src/composition/expr-subst.ts`)
   — replace every `{kind:'symbol', name}` leaf with `replacement`, recursing
   the scalar arms. Tensor arms are passed through unchanged (no tensor
   junction in the scalar chain) — if one is encountered on the substitution
   path, throw clearly.

4. **`composeSymbolic(first, second, opts)`**
   (`src/composition/compose-symbolic.ts`):
   - Find the junction (reuse `composeEdges`' name/identification matching):
     `first.target.name` matches a `second` source by name or
     `QUANTITY_IDENTIFICATIONS`. The junction's name in `second.symbolic` is
     the source-quantity name (`ident.to` when identified).
   - Require both operands carry `symbolic` (else throw a clear
     `SymbolicCompositionError` — fall back to numeric `composeEdges`).
   - `expr = substitute(second.symbolic, junctionName, first.symbolic)`.
   - **Validate**: `validate(expr).inferredDimension` must equal
     `second.target.dim` (dimensional homogeneity of the composed form). The
     junction dim is already checked by name matching; this is the stronger
     whole-expression check.
   - `leaves` = free symbols of `expr` minus those in `CONSTANTS`.
   - Return an `Observable` whose `evaluate` calls `evalExpr(expr, values)`.

5. **Author symbolic forms** for the CT-1 / CT-1b chain edges (in
   `calibration.ts`), leaves in graph vocabulary:
   - `lawSchwarzschildRadius`: `(2·G·mass)/c²`.
   - `be42ViaRsEdge`: `(hbar·c)/(4pi·k_B·schwarzschild-radius)`.
   - `be16Edge`: `k_B·temperature·ln2`.
   - `be42Edge`: `(hbar·c³)/(8pi·G·mass·k_B)`.

## Worked example — CT-1 symbolic (the marquee)

`composeSymbolic(be42Edge, be16Edge)` (via `hawking-temperature ≡
temperature`):
`substitute(k_B·temperature·ln2, 'temperature', hbar·c³/(8pi·G·mass·k_B))`
→ `k_B · (hbar·c³/(8pi·G·mass·k_B)) · ln2`. UNSIMPLIFIED (we are not a CAS),
but `validate()` confirms it is `[energy]` (k_B cancels dimensionally) and
`evalExpr` on `{mass: M_sun}` reproduces the numeric CT-1 value
`E_min = ℏc³ln2/(8πGM)` — the framework's first derived literature relation,
now carried SYMBOLICALLY, not as a closure.

## Consistency / drift guard (the load-bearing invariant)

For EVERY edge with a `symbolic` form, a test asserts
`evalExpr(edge.symbolic, probeInputs) ≈ edge.evaluate(probeInputs)` over
several probe inputs (tight tolerance). This BINDS the symbolic form to the
numeric evaluator — the symbolic AST cannot silently drift from the physics
the evaluator computes. This is what makes option (d) safe where a separate
registry would rot.

## Scope & honest limits

- Scalar closed forms ONLY. Tensor-valued bridges and transcendental-interior
  bridges (typed-stubs) have no `symbolic` form and fall back to numeric
  `composeEdges` (unchanged). This is the same honesty as the rest of the
  catalog.
- No algebraic simplification — composed ASTs are correct but unsimplified.
  Dimensional validation + numeric cross-check are the correctness gates.
- The Observable contract is OPT-IN per edge; most edges won't carry it
  initially. The contract + the chain edges demonstrate the capability; broad
  authoring is future work.

## Surface policy

`evalExpr`, `substitute`, `composeSymbolic`, `Observable`, the symbolic
errors, and `CONSTANTS` are surfaced thoughtfully: the composition pieces
(`composeSymbolic`, `Observable`, `SymbolicCompositionError`) are candidates
for the PUBLIC surface (they extend the public `composeEdges` story); the
helpers (`evalExpr`, `substitute`, `CONSTANTS`) can stay internal. `symbolic?`
on `BridgeEdge` is an additive optional field (non-breaking). Final
public/internal split decided after the Adam+Eve vet. Public additions get
the snapshot + `@public`-reachability updates.

## Test plan

- `evalExpr`: scalar arithmetic, constants, `^`, missing-symbol throw,
  integral/derivative throw.
- `substitute`: leaf replacement, nested, no-op when absent, multi-occurrence.
- `composeSymbolic`: CT-1 symbolic = energy + numeric match to `composeEdges`;
  CT-1b (lawSchwarzschildRadius ∘ be42ViaRs) chain; junction-by-identification;
  missing-`symbolic` throw; dimensional-mismatch rejection.
- Drift guard across all symbolic-bearing edges.

## Adam vet — r2 revisions applied

Adam verdict: YELLOW. The contract (option (d), optional `symbolic?`, drift
guard, Observable) holds; the following precision fixes are now binding on the
implementation:

- **(A-1) Leaf resolution order, no `NaN` literals.** `evalExpr` resolves a
  leaf as `values[name] ?? CONSTANTS[name]?.value ?? Number(name)` (optional
  chaining — a missing constant must fall through, not throw), and throws if
  the result is non-finite. `8pi`, `4pi`, `ln2` (and any non-base-10 literal)
  MUST be registered in `CONSTANTS` — `Number('8pi')` is `NaN`.
- **(A-2, CRITICAL) Relative tolerance on every numeric cross-check.** The
  drift guard and composed-form checks use a RELATIVE-error assertion
  (`|a−b|/|b| < 1e-9`), NEVER `toBeCloseTo` (absolute — against SI magnitudes
  like `T_H≈6e-8` or `E_min≈3e-21` it falsely "passes" everything as ≈0). The
  `^` arm uses `Math.pow`, so `c^3` ≠ `c*c*c` by ~1 ULP — relative tol absorbs
  this. (A shared `relClose(a,b,tol)` test helper.)
- **(A-3, HIGH) Zero-occurrence guard.** `substitute` returns
  `{ expr, count }`; `composeSymbolic` throws `SymbolicCompositionError` when
  the junction leaf occurs ZERO times in `second.symbolic` (a silent no-op
  substitution would yield a dimensionally-valid but physics-wrong composition
  that ignores `first`). Multi-occurrence substitutes all (documented). Every
  symbolic chain gets a composed-form numeric cross-check vs `composeEdges`,
  not just CT-1/CT-1b.
- **(A-4, HIGH) `equals()` not `===` for the composed-dim check** — value
  equality on the `Dimension` vector, per the `compose.ts:204` precedent.
- **(A-5, HIGH) `values` win over `CONSTANTS`; disjointness guard.** Leaf
  resolution prefers caller `values` over `CONSTANTS` (A-1 order already does
  this). A guard test asserts `CONSTANTS` keys are disjoint from every
  `quantities.ts` canonical quantity name (collision would silently mis-resolve
  a leaf).
- **(A-6, MEDIUM) Explicit leaf dims + leaf-dim↔registry guard.** Every
  literal/constant leaf is `sym(name, dim)` with an explicit `dim` (matching
  the be-42 AST pattern); a guard asserts each leaf's `dim` equals
  `CONSTANTS[name].dim`.
- **(A-7, MEDIUM) Single constant source, guarded end-to-end.** `CONSTANTS`
  imports SI values from `core/constants.js` (the same source the evaluators
  resolve to). The drift guard (`evalExpr(symbolic) ≈ edge.evaluate`)
  transitively catches any triple-source drift end-to-end, so no evaluator
  refactor is needed — the guard IS the binding.
- **(A-8, MEDIUM) Surface bookkeeping.** Publicly-surfaced additions
  (`composeSymbolic`, `Observable`, `SymbolicCompositionError`) get the
  `EXPECTED_RUNTIME_EXPORTS`/`ALL_TYPE_EXPORTS` + snapshot update and a
  `src/index.ts` re-export (for `@public`-reachability). `symbolic?` is an
  additive optional field on the already-`@public` `BridgeEdge` — no new
  symbol, no snapshot impact. Helpers (`evalExpr`, `substitute`, `CONSTANTS`)
  stay `@internal`.
- **(A-9, LOW) Composed-Observable provenance** from `second.target`
  (`name`/`symbol`/`dim`).
- **(A-10, LOW) `substitute` recursion scope.** Recurses all SCALAR arms
  (`symbol`, `op`, `integral`, `derivative`); tensor arms throw a clear error
  if encountered on the path (matching `evalExpr`'s scalar-only scope).

## Eve vet — r3 revisions applied

Eve verdict: YELLOW (no CRITICAL/RED). She VERIFIED the marquee junction
directions, `validate()` non-nullness on the composed AST, and the bit-for-bit
constant agreement — and caught that the recon misnamed the erasure-energy
quantity (it is **`landauer-erasure-energy`**, grep-confirmed at
`quantities.ts:200`, NOT `erasure-energy`). The following additional fixes are
binding:

- **(EVE-1, HIGH) Strict Observable input.** `Observable.evaluate(values)`
  accepts EXACTLY the advertised `leaves` keys: a missing leaf throws naming
  the leaf; an unknown key (including a `CONSTANTS` token like `c`/`8pi`)
  throws. The static disjointness guard (A-5) does not cover runtime caller
  input — this does. (Internal `evalExpr` keeps `values`-first resolution; the
  public `Observable.evaluate` is the strict wrapper.)
- **(EVE-2, MEDIUM) Domain behavior documented.** `Observable.evaluate` is a
  PURE symbolic value evaluator — it does NOT domain-check (unlike
  `composeEdges`, which throws `DomainViolationError`, compose.ts:310-323). So
  `evaluate({mass: -1})` returns a (wrong-signed) number rather than throwing.
  Documented on the contract; callers wanting domain-checked numeric values
  use `composeEdges`. The drift/cross-checks probe in-domain inputs only.
- **(EVE-3, MEDIUM) Power authoring pinned.** Every constant power is authored
  as `^` with an integer exponent symbol `sym('n', DIMENSIONLESS)` (e.g.
  `c³ = c^3`), NOT repeated multiplication. The evaluators use repeated mult
  (`C_SI*C_SI` at calibration.ts:142; `c*c*c` at be-42:115), so
  `Math.pow(c,3)` differs by ~1 ULP — which is exactly why the A-2 RELATIVE
  tolerance (1e-9) is load-bearing, and keeps `^`-arm coverage for exponent>2.
- **(EVE-4, MEDIUM) Junction-name resolution.** The substitution target name is
  `viaIdentification ? identification.to : junction.name` — NOT
  unconditionally `ident.to`. CT-1b (`lawSchwarzschildRadius ∘ be42ViaRsEdge`)
  joins by NAME (`schwarzschild-radius`, grep-confirmed quantities.ts:264),
  `viaIdentification === null`; an always-`ident.to` mis-impl yields
  `undefined` → zero-occurrence → spurious A-3 throw. Pre-execution gate: assert
  CT-1b's junction name resolves to `'schwarzschild-radius'`.
- **(EVE-5, LOW) Leaf-dim guard covers quantity leaves too.** A-6's leaf-dim↔
  registry guard extends to SOURCE-QUANTITY leaves: each such leaf's `dim` must
  equal the matching `Quantity.dim` (e.g. the `mass` leaf is `MASS`), not just
  the constant leaves.

## Open questions for the Adam+Eve vet

1. Should `symbolic?` live on `BridgeEdge` (with the drift guard) or in a
   separate registry? (Drift guard argues for on-edge.)
2. Public vs internal split for `composeSymbolic` / `Observable`.
3. Is the unsimplified composed AST acceptable, or is minimal
   constant-folding (k_B/k_B → 1) worth the complexity? (Lean: no — validate
   + numeric match suffice.)
4. Constant vocabulary collisions: a source quantity named like a constant
   (`'c'`?) — none exist today, but should `evalExpr` prefer `values` over
   `CONSTANTS` (caller wins)? (Lean: yes, `values` first.)
