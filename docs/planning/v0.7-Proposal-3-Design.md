# UPT v0.7 — Proposal 3: Typed L/B/E Discriminated Union — Design

> **Scope note:** This document designs one specific proposal from
> `docs/planning/UPT v0.70 - Proposals.md` §4. It is a design study,
> not a commitment to ship. Greenlight and sequencing decisions rest
> with the maintainer after Adam+Eve adversarial review.
>
> **Inspiration & precedent:** The v0.6.1 minimize sprint demonstrated
> that structural rigor (export-policy buckets, validator-registry
> discriminated-union) can be added to existing code with no public-API
> change and no behavioral diff. Proposal 3 applies the same discipline
> to the cell-storage layer. The ITensor paper (Fishman et al., SciPost
> Phys. Codebases 2022, §6) provides the conceptual reference: ITensor's
> storage-layer design separates the *kind* of a stored object from its
> *value*, enabling exhaustive dispatch over a closed set of cases.
>
> **Source for findings:** `docs/planning/UPT v0.70 - Proposals.md` §4
> (Proposal 3, lines 236–312), §0 Executive Summary, §11 Sequencing,
> §12 Layering Insight. Codebase cross-checks against HEAD of
> `src/core/tensor.ts` (441 LOC), `src/core/types.ts` (195 LOC),
> `src/bridges/index.ts` (first 200 lines), and `src/index.ts`
> (public-API manifest). MathTS CHANGELOG referenced in §1 of the
> proposals doc but not directly relevant to this proposal — Proposal 3
> is UPT-internal with zero MathTS dependency.

---

## Goal

The sprint succeeds if all of the following are true at the tagged
commit:

1. A `Cell` discriminated union exists in `src/core/cell.ts` (new
   module) with three variants — `LawCell`, `BridgeCell`,
   `EmergenceCell` — each carrying a `kind: 'law' | 'bridge' |
   'emergence'` discriminator field. TypeScript can narrow to the
   specific variant at every consumption site.
2. Every switch over `Cell.kind` in the codebase has an exhaustive
   `never` arm, consistent with the existing `_exhaustive: never`
   pattern used at `src/dimensional/validator.ts:636`. New consumption
   sites introduced in this sprint also carry that arm.
3. `UniversalTensor` grows a unified `addCell(cell: Cell): boolean`
   method that replaces the three separate `addLaw` / `addBridge` /
   `addEmergence` call sites in consumers that want kind-agnostic
   ingestion. The existing three methods are kept as typed conveniences
   (no removal of public API).
4. The `confidence` field across all three cell variants is typed as
   `'established' | 'speculative' | 'highly-speculative'` — matching
   the catalog's `BridgeEquationStatus` vocabulary — not as a raw
   `number` in `[0,1]` (the current `PhysicalLaw.confidence` /
   `EmergentPhenomenon.confidence` shape). This resolves the
   type-vocabulary split between `src/core/types.ts` (numeric) and
   `src/bridges/index.ts` (string literal union).
5. The existing test suite passes unmodified or with trivially-updated
   fixture types. No test is deleted; count is net-add only.
6. `README.md`'s footnote "'+' in Π = L + B + E is disjoint union, not
   algebraic" is updated to point at `src/core/cell.ts` as the type
   enforcement.

## Tag Decision

**Ship as `v0.7.0` (minor bump), as part of the v0.7 "Foundation
Consolidation" rollup** described in `docs/planning/UPT v0.70 -
Proposals.md` §11.

The proposals doc sequences Proposals 1, 2, 3, and 4 together under
v0.7 with the theme "every existing capability still works, but the
architecture is now what it should be." That sequencing is correct for
Proposal 3's character: it is purely structural, introduces no new
physics, and adds compile-time guarantees on top of already-correct
runtime behavior.

**Argument for the rollup:** Proposal 3 is the lightest of the four
v0.7 proposals (1 week vs. 2-3 weeks each for Proposals 1 and 4). It
should not ship alone as `v0.7.0` because the version bump would
claim a "Foundation Consolidation" milestone while only delivering the
smallest piece of it. The right posture is: implement Proposal 3 as the
first task of the v0.7 sprint, then proceed to Proposals 2 and 1 (in
that order — see Phase Architecture below), and tag `v0.7.0` when all
four are complete.

**Argument against early standalone release:** A `v0.7.0` that only
adds a discriminated union and no Intelligent Index layer (Proposal 1)
or sparse catalog (Proposal 2) would claim "Foundation Consolidation"
without the foundation. Version discipline matters more than early
shipping cadence.

**`v0.7.0-alpha` option:** if the maintainer wants to checkpoint
Proposal 3 while the larger proposals are in flight, a `v0.7.0-alpha.1`
pre-release tag is appropriate. Do not treat an alpha as the stable
`v0.7.0` milestone.

## Architectural Decisions (locked)

### Decision #1 — Discriminator field is `kind`, not `type` or `role`

The existing `ExprNode` discriminated union in
`src/dimensional/validator.ts` (lines 66-69) uses `kind` as the
discriminator. The v0.6.1 validator-registry excerpt in
`v0.6.1-Design.md` (Phase 2, Proposal 1) also uses `kind` as the
pattern discriminator. Using `type` would conflict with TypeScript's
built-in `typeof` keyword semantics in narrowing and with the prose
use of "type" throughout the codebase. Using `role` would be novel
vocabulary with no precedent here. `kind` matches existing convention
at every consumption site in `src/dimensional/`.

### Decision #2 — New module `src/core/cell.ts`; existing `types.ts` interfaces are not deleted

The three existing interfaces — `PhysicalLaw`, `BridgeEquation`,
`EmergentPhenomenon` — in `src/core/types.ts` remain exported and
unchanged. The new `Cell` union lives in `src/core/cell.ts` as a
net-add. The three cell variants (`LawCell`, `BridgeCell`,
`EmergenceCell`) embed the existing interfaces by reference or carry a
structurally compatible superset.

Rationale: deleting `PhysicalLaw` / `BridgeEquation` / `EmergentPhenomenon`
would be a breaking change to every downstream consumer that imports
them by name. The SemVer commitment (v0.1.0 onward per CLAUDE.md)
requires a major bump for breaking removals. v0.7.0 is a minor release.
Migration is additive: the new `LawCell`, `BridgeCell`, `EmergenceCell`
types are the preferred forward-looking shapes; the old interfaces are
marked `@deprecated` in JSDoc to guide consumers without forcing a
breaking change.

The proposals doc's illustrative TypeScript at §4.2 introduces `LawEntry`,
`BridgeEntry`, `EmergenceEntry` as standalone interfaces with a `CellBase`
abstract base. UNVERIFIED: the doc's `BridgeEntry.from: AxisCoordinate`
and `BridgeEntry.to: AxisCoordinate` assume an `AxisCoordinate` type
that does not exist in HEAD (Proposal 1 creates it). In this sprint,
`BridgeCell.source: TensorIndices` and `BridgeCell.target: TensorIndices`
are used instead — the existing type from `src/core/types.ts:76` —
deferring the `AxisCoordinate` upgrade to Proposal 1.

### Decision #3 — `confidence` field becomes a string literal union, not a number

Current state (verified against HEAD):
- `PhysicalLaw.confidence: number` (0-1 range, `src/core/types.ts:108`)
- `EmergentPhenomenon.confidence: number` (0-1 range, `src/core/types.ts:172`)
- `BridgeEquation.confidence: number` (0-1 range, `src/core/types.ts:143`)
- `BridgeEquationEntry.status: BridgeEquationStatus` ('established' |
  'speculative' | 'highly-speculative' | 'invalid', `src/bridges/index.ts:42-46`)

The catalog (42 entries) uses the `status` vocabulary. The core types
use a numeric float. This is a type-vocabulary split: the string-literal
vocabulary is more expressive (conveys epistemic semantics, not a false
numerical precision).

Decision: `Cell` variants carry `confidence: 'established' | 'speculative' |
'highly-speculative'` (omitting `'invalid'` — cells in the tensor are by
definition active; invalid entries should not be added). The numeric
`confidence` field on the old interfaces is left in place (no breaking
change). A runtime `confidenceToStatus(n: number): BridgeEquationStatus`
adapter is provided for consumers that must migrate gradually.

Risk flagged: the `'invalid'` exclusion from the cell type means an
`addCell` call with a hand-constructed `LawCell` cannot carry `confidence:
'invalid'`. This is intentional — it makes the invariant type-enforced
rather than convention-enforced.

### Decision #4 — `UniversalTensor.addCell(cell: Cell)` dispatches by `kind`

The switch inside `addCell` is exhaustive:

```typescript
switch (cell.kind) {
  case 'law':       return this.addLaw(toLaw(cell));
  case 'bridge':    return this.addBridge(toBridge(cell));
  case 'emergence': return this.addEmergence(toEmergence(cell));
  default: {
    const _exhaustive: never = cell;
    throw new Error(`Unknown cell kind: ${(_exhaustive as Cell).kind}`);
  }
}
```

The three existing `addLaw` / `addBridge` / `addEmergence` methods stay
public (backward-compat), implement the actual storage logic, and remain
the preferred single-cell entry points for typed consumers. `addCell` is
a convenience for kind-agnostic ingestion (e.g., deserializers,
migration code, Proposal 2's `compose()` function).

### Decision #5 — No `add(cell1: Cell, cell2: Cell): Cell` is introduced

The "+" in `Π = L + B + E` is disjoint union, not algebraic addition.
The proposals doc is explicit on this: a `compose(L, B, E)` factory
function populates a `UniversalTensor` by iterating the three arrays, not
by computing a cell-level sum. This decision locks in the type-system
guarantee: there is no public API that takes two `Cell` values and returns
a third. If a future proposal needs composition operations, they operate at
the `UniversalTensor` level (aggregating populated cells), not at the
`Cell` level.

### Decision #6 — Exhaustiveness guard uses the `_exhaustive: never` pattern, not `@typescript-eslint/switch-exhaustiveness-check`

The proposals doc §4.3 references `@typescript-eslint/switch-exhaustiveness-check`.
Cross-check against HEAD: there is no ESLint configuration file at the
repo root (verified: `ls` shows no `.eslintrc.*` or `eslint.config.*`).
The repo uses TypeScript's own `noImplicitReturns` + the manual
`_exhaustive: never` guard pattern (`src/dimensional/validator.ts:636`).

Decision: Proposal 3 continues this existing pattern. Adding an ESLint
config for a single rule would be scope creep and would require a new
dev dependency. The `_exhaustive: never` pattern achieves the same
compile-time guarantee under the existing `tsconfig.json` strict-mode
settings. UNVERIFIED: whether `strict: true` is set — should be
confirmed in Phase 0.

### Decision #7 — The `equation` field in Cell variants is NOT typed to the v0.6 physics AST

The proposals doc §4.2 types the `equation` slot as `AstNode`, described
as "UPT's existing v0.6 AST." Cross-check against HEAD: the v0.6 AST
nodes live in `src/dimensional/validator.ts` (the `ExprNode` union at
lines 66-69) and in `src/dimensional/` sub-modules (`KillingVectorNode`,
`EinsteinFieldEquationNode`, etc. imported at lines 47-84 of validator.ts).
These are dimensional-validation AST nodes, not equation-representation
AST nodes. The `PhysicalLaw.equation`, `BridgeEquation.equation`, and
`EmergentPhenomenon.description` fields in `src/core/types.ts` are all
plain strings (LaTeX).

Decision: `Cell` variants carry `equation: string` (LaTeX, matching the
existing fields) in v0.7. Typing the equation slot to a rich AST type is
Proposal 4's scope. Adding a dependency on the dimensional-validator AST
in the core cell type would create an undesirable coupling between the
storage layer and the validation layer.

### Decision #8 — `src/core/cell.ts` is a new module, NOT a modification of `tensor.ts`

`src/core/tensor.ts` (441 LOC) implements `UniversalTensor` with storage
and query methods. Adding the `Cell` union type to that file would push
it past the 500 LOC hygiene threshold and mix concern layers (type
definition vs. class implementation). The new module `src/core/cell.ts`
holds: `CellBase`, `LawCell`, `BridgeCell`, `EmergenceCell`, `Cell`,
`confidenceToStatus`. `src/core/tensor.ts` imports from it. This matches
the existing pattern: `tensor.ts` imports from `./types.js`; the new
`cell.ts` is a natural second import at the same level.

### Decision #9 — Adam+Eve adversarial review uses Opus subagents

Per Decision #9 of `v0.6.1-Design.md`, and the v0.5.1 carry-forward
lesson ("Adam+Eve MCP availability is fragile"), two parallel Opus
subagents serve as Adam (steel-manning skeptic) and Eve (devil's-advocate
red-team) for both this design doc and the upcoming Implementation Plan.
The review runs after this design lands; findings consolidate into
`docs/planning/v0.7-Proposal-3-Review-Findings.md` and feed the
Implementation Plan.

The Adam+Eve vet on the plan must explicitly grep-confirm the per-arm
switch assignments against HEAD before any TDD cycle starts — the v0.5.0
lesson ("never assume the plan inherits the design's fixes") applies here.

### Phase 1 — `src/core/cell.ts`

**Motivation:** The `Cell` discriminated union is the primary deliverable
of Proposal 3. Defining it in isolation (before wiring into
`UniversalTensor`) lets Phase 1 tests run purely against the type
definitions and the `confidenceToStatus` adapter, with no risk of
regressions in existing query methods.

**Components:**

- **Task 1.1 — `CellBase` interface.** Fields: `id: string`,
  `confidence: 'established' | 'speculative' | 'highly-speculative'`,
  `equation: string`, `references: string[]`. Aligns with the field
  shapes present across `PhysicalLaw`, `BridgeEquation`,
  `EmergentPhenomenon` (minus the numeric `confidence`).
- **Task 1.2 — Three variant interfaces.** `LawCell` (extends CellBase,
  adds `kind: 'law'`, `name: string`, `scales: PhysicalScale[]`,
  `forces: Force[]`, `symmetries: Symmetry[]`). `BridgeCell` (adds
  `kind: 'bridge'`, `source: TensorIndices`, `target: TensorIndices`,
  `validated: boolean`). `EmergenceCell` (adds `kind: 'emergence'`,
  `name: string`, `order: number`, `indices: TensorIndices[]`). Field
  shapes verified against existing interfaces in `src/core/types.ts`
  before TDD starts (Phase 0 gate).
- **Task 1.3 — `Cell` union + `confidenceToStatus` adapter.** `type Cell
  = LawCell | BridgeCell | EmergenceCell`. `confidenceToStatus(n: number):
  'established' | 'speculative' | 'highly-speculative'` maps the numeric
  confidence from old interfaces to the string vocabulary (thresholds:
  `n >= 0.8` → 'established', `n >= 0.4` → 'speculative', else
  'highly-speculative' — note UNVERIFIED: this mapping is not specified
  in the proposals doc and the thresholds are a design decision for the
  Implementation Plan to confirm or adjust with the maintainer).
- **Task 1.4 — `@deprecated` JSDoc on old interfaces.** Add
  `@deprecated Use LawCell, BridgeCell, EmergenceCell from
  './cell.js'.` to `PhysicalLaw`, `BridgeEquation`, `EmergentPhenomenon`
  in `src/core/types.ts`. No other change to that file.

**Tests:** `tests/core/cell.test.ts` (new file). Tests cover:
  - TypeScript narrowing is exhaustive: a function that switches on `cell.kind`
    and has `default: { const _: never = cell; }` compiles without error.
  - `LawCell` with `kind: 'bridge'` is a TypeScript error (compile-time
    test via `@ts-expect-error`).
  - `confidenceToStatus(0.9)` === 'established', `confidenceToStatus(0.6)` ===
    'speculative', `confidenceToStatus(0.1)` === 'highly-speculative'.
  - Existing suite stays green.

**Deliverable:** `src/core/cell.ts` + `tests/core/cell.test.ts` +
`@deprecated` annotations in `src/core/types.ts`. 4 commits (one per
task).

## Risks

1. **Confidence threshold mapping is arbitrary.** The conversion from
   numeric `[0,1]` confidence (old interfaces) to the string literal
   union (new `Cell` variants) requires choosing thresholds.
   The proposals doc does not specify them. Risk: wrong thresholds
   produce misleading epistemic labels on migrated entries.
   Mitigation: the `confidenceToStatus` adapter is marked clearly as
   a migration helper, not a physics claim. Its thresholds are a
   `// TODO: confirm with maintainer` annotation in the Implementation
   Plan. Alternatively, the adapter is not shipped and callers are
   required to pass the string confidence directly when constructing
   a `Cell` — forcing an explicit migration decision at each call site.

2. **`@deprecated` markers on old interfaces may break downstream
   consumers.** If a downstream consumer (UNVERIFIED: whether any exist)
   has lint rules that treat `@deprecated` usage as errors, adding the
   markers breaks their build.
   Mitigation: the markers use `@deprecated` JSDoc, which TypeScript
   surfaces as warnings (squiggly underline), not errors, unless
   `@typescript-eslint/no-deprecated` is configured at `error` level.
   The proposals doc explicitly requires backward compatibility. If this
   is a concern, delay the `@deprecated` markers to a future minor
   release.

3. **Divergence between proposals-doc illustrative TypeScript and HEAD
   field shapes.** The proposals doc §4.2 is acknowledged as illustrative
   (per §10.1: "code sketches will need light adjustment against real
   exports"). Specifically, `BridgeEntry.from: AxisCoordinate` does not
   exist in HEAD (Proposal 1 creates `AxisCoordinate`). Using it in this
   sprint would introduce a forward dependency.
   Mitigation: Decision #7 resolves this explicitly — `BridgeCell` uses
   `source: TensorIndices` / `target: TensorIndices` (existing types).
   Phase 0 Task 0.2 verifies the field shapes before any TDD starts.

4. **Public surface snapshot test.** `tests/api/public-surface.test.ts`
   and its snapshot pin the exact set of `src/index.ts` re-exports.
   Adding `Cell`, `LawCell`, `BridgeCell`, `EmergenceCell`, `compose`
   to the manifest will require the snapshot to be regenerated, which
   Phase 2 Task 2.3 accounts for. Risk: forgetting to regenerate causes
   a CI failure that looks like a test bug.
   Mitigation: the task description in the Implementation Plan explicitly
   requires snapshot regeneration as a step.

5. **`kind: 'emergence'` vs. `kind: 'emergent'` spelling.** The proposals
   doc §4.2 uses `kind: 'emergence'` throughout. No existing codebase
   symbol uses either spelling (Proposal 3 is the first to introduce the
   discriminated-union vocabulary for the E component). Risk: a future
   proposal (e.g., Proposal 2's `EmergenceEntry` type) uses a different
   spelling, causing an inconsistency.
   Mitigation: lock `'emergence'` in this design. The Implementation Plan
   must spell it exactly this way in all code snippets and task
   descriptions. Adam+Eve vet confirms the spelling is consistent
   across all three doc artifacts.

## Non-goals

The following are explicitly out of scope for this sprint:

- **No changes to the 42-bridge catalog** (`src/bridges/index.ts`). The
  `BridgeEquationEntry` interface in the catalog is a different shape
  from `BridgeCell` and serves a different purpose (spec-fidelity catalog
  vs. typed storage cell). Unifying them is a future concern, not v0.7.
- **No merger with Proposals 1 and 2.** This sprint does not implement
  `UniversalIndex`, `AxisCoordinate`, `FluxRule`, or the sparse
  `Map<TupleKey, Cell>` redesign. Those belong to Proposals 1 and 2.
  `BridgeCell` uses the existing `TensorIndices` type as a deliberate
  placeholder.
- **No change to AST node-kind discriminators** in `src/dimensional/`.
  The `ExprNode` union's `kind` field and all the curvature-node kinds
  (`'riemann-tensor'`, `'killing-vector'`, etc.) are untouched. This
  sprint does not touch `src/dimensional/` at all.
- **No new physics** (bridges, law statements, emergent phenomena, or
  dimensional signatures).
- **No removal of `addLaw`, `addBridge`, `addEmergence`** from
  `UniversalTensor`'s public API.
- **No `liftToUptAst` or Bridge DSL** — that is Proposal 4's scope.
- **No `defineRegime` extension API** — that is Proposal 5's scope
  (v0.8 target).
- **No workbook authoring or MathTS consumption** — Proposals 7 and 8.
