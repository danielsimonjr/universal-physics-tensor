## 1. Context

UPT v0.3.5 (tag `v0.3.5`, commit `7786027`, 2026-05-14) shipped the **numerical-contraction backend**: a `TensorEngine` interface with two interchangeable implementations (`Float64ReferenceEngine` zero-dep default, `MathTSEngine` over `@danielsimonjr/mathts-tensor`), AST→engine lowering driven by `computeContraction`, two-way numerical partial derivatives, `InverseMetricInconsistencyWarning`, and the BE-37 Shapiro-delay eikonal end-to-end at ±10⁻¹⁰ relative error. v0.3.5 is the first *executable* layer of UPT.

v0.4.0 adds the **connection layer**: Christoffel symbols `Γ^λ_μν` + the covariant derivative `∇_μ`, both symbolically (new AST surface) and numerically (engine lowering). The numerical side requires automatic differentiation — added to the `TensorEngine` interface as forward-mode AND reverse-mode optional methods. As a release-time step, `MathTSEngine` is promoted from `optionalDependencies` to `dependencies` and becomes the registry default. This is the canonical GR "first executable curved-spacetime calculation" milestone — moving from light-in-Schwarzschild (v0.3.5 BE-37 eikonal) to massive-particle-in-Schwarzschild (v0.4.0 geodesic equation).

Per the v0.3.5-refreshed TensorJS roadmap: v0.4.0 ships the connection layer; v0.5.0+ adds curvature (Riemann, Ricci, Bianchi), the Faraday-cascade BREAKING refactor (Part-VIII §VIII.10), and threejs visualization bootstraps.

## 2. Scope

### In scope

1. **`covariant-derivative` AST node**: a new `ExprNode` kind that parallels v0.3.0's `tensor-partial-derivative`. Shape `{ kind: 'covariant-derivative', of, wrt, wrtIndex, gLower, gInverse }`. Dedicated validator case with internally-consumed metric indices (§7).
2. **`christoffel()` helper**: a builder function `christoffel(gLower, gInverse, λ, μ, ν): ExprNode` returning a composite tree `(1/2)·g^λρ·(∂_μ g_ρν + ∂_ν g_ρμ − ∂_ρ g_μν)` built from existing v0.3.0 nodes. Parallels the v0.3.0 `raise()` / `lower()` helper precedent (§5).
3. **`derivativeStrategy` field on `metric-tensor`**: optional `'computed' | 'zero' | 'supplied'`, defaults `'computed'`. Mirrors the v0.3.5 `numericalForm` field pattern. Closes the v0.3.0-deferred `varying` question (v0.3.0-Design §13 Q5).
4. **AD on `TensorEngine`**: two optional methods, `forwardGrad?` and `reverseGrad?`. Both v0.4.0 engines implement both; conformance suite capability-detects (§6).
5. **`InverseMetricInconsistencyWarning` extension**: a new sub-rule fires when the same metric name appears in one AST with **conflicting `derivativeStrategy` values** (Eve's M2).
6. **MathTSEngine becomes the registry default** at release time. The publish of `@danielsimonjr/mathts-tensor` (a Daniel-manual step — `npm publish` requires 2FA, deferred from v0.3.5) is the prerequisite. Honest framing: this is a code-path-signal + dependency-shape change, **not** a perf change (both engines have identical naive O(n) algorithms — MathTS gains real perf optimizations in v0.5.0+).
7. **Schwarzschild geodesic numerical evaluator**: `d²x^μ/dτ² + Γ^μ_νρ ẋ^ν ẋ^ρ = 0` RK4-integrated for radial infall in Schwarzschild; cross-checked against the analytic trajectory to **±10⁻⁹ relative**. Integration domain restricted to **r ≥ 10·r_Schwarz** to avoid the coordinate singularity (Adam + Eve H2).
8. **BE-37 covariant-eikonal preview**: `g^μν (∇_μ S)(∇_ν S) = 0` for scalar `S` matches v0.3.5's pderiv-based BE-37 eikonal to machine precision (confirms `∇_μ S = ∂_μ S` for scalars — the Part-VIII §VIII.8 "only the operator changes" promise).
9. **`Part-IX-Connection-Layer.md`**: a new spec section following the Part-VIII pattern (TENSOR-RULE markers, spec↔impl drift-guard test).

### Explicitly out of scope (deferred to later versions)

- **Riemann curvature `R^μ_νρσ`, Ricci, Bianchi identities, Einstein field-equation solvers**: v0.5.0+. v0.4.0 ships the *connection* (covariant derivative + Christoffel); curvature is downstream.
- **Faraday mixed-component-dim BREAKING refactor**: v0.5.0+ (Part-VIII §VIII.10). v0.4.0 only needs uniform-dim metrics.
- **Non-Levi-Civita connections** (teleparallel, Cartan, etc.): v0.5.0+. v0.4.0's `covariant-derivative` carries explicit `gLower`/`gInverse` and uses the metric-derived Christoffel only.
- **High-order or adaptive ODE integrators**: v0.4.0 reuses v0.3.5's fixed-step RK4; if the ±10⁻⁹ target requires step-counts beyond ~10⁵, escalate.
- **Real MathTSEngine performance work** (BLAS, SIMD, GPU): v0.5.0+. The MathTSEngine-default flip is dependency-shape only.
- **AST-size optimization for embedded metric children** (Eve L3): a v0.5.0+ concern when curvature lands and `Γ`-of-`Γ` terms create quadratic blow-up. v0.4.0 documents the issue but does not solve it.

## 3. Approach: ∇_μ as a node, Γ as a helper

The pattern adopted from v0.3.0 (and reaffirmed in v0.3.5) holds: dedicated AST node kinds for fundamental operators; helper functions for composite expressions. Part-VIII §VIII.8 explicitly hints at this: *"v0.4.0 will swap `pderiv` for the covariant derivative `∇_μ`… only the operator changes."* Operator-replacement only reads sensibly if `∇_μ` is a node, like `pderiv`.

- **`covariant-derivative`** is a new node kind. The validator and numerical lowering have dedicated cases. Swapping `pderiv` for `∇_μ` in an existing AST is a one-line node-kind change at the call site.
- **`christoffel()`** is a helper function. The Christoffel formula is composable from existing v0.3.0 nodes (`metric-tensor`, `pderiv`, `op '+'/'−'`, `contract`, scalar) — Part-VIII §VIII.9 already confirms `∂_μ g_νλ` is well-formed and provides the preview test. Wrapping the composite formula in a helper gives clean callsite syntax without inflating the node-kind surface; symmetry of Γ in `μν` is asserted by a dedicated checker function rather than baked into a node-kind validator. Parallels the v0.3.0 `raise()`/`lower()` precedent.

## 4. AST extension

### Existing node types (v0.3.5, unchanged shapes except one additive optional field)

```typescript
// src/dimensional/metric-validators.ts — MetricTensorNode gains one optional field
export interface MetricTensorNode {
  readonly kind: 'metric-tensor';
  readonly name: string;
  readonly indices: ReadonlyArray<TensorIndex>;
  readonly signature: string;
  readonly dim: Dimension;
  readonly derivativeStrategy?: 'computed' | 'zero' | 'supplied';  // NEW in v0.4.0; defaults 'computed'
}
```

`derivativeStrategy` defaults to `'computed'` — every v0.3.x AST is a valid v0.4.0 AST with no change. Numerical lowering branches on this field when computing `∂g` for Christoffel / `∇_μ`:
- `'computed'`: lowering uses `engine.forwardGrad?` on the metric function (the default — what v0.3.5's `'numerical-fn'` numericalForm would have used if v0.3.5 had AD).
- `'zero'`: constant metric — `∂g = 0`, `Γ = 0`, `∇_μ = ∂_μ`. Optimization for flat-space sanity-checks.
- `'supplied'`: lowering looks up `inputs.metricDerivatives.get(`${gName}/${coordLabel}`)` (parallel to v0.3.5's `inputs.derivatives` for `'symbolic'` tensor-symbols).

### The new `covariant-derivative` node

```typescript
// src/dimensional/connection-validators.ts (new module — parallels metric-validators.ts)
export interface CovariantDerivativeNode {
  readonly kind: 'covariant-derivative';
  readonly of: unknown;           // ExprNode — typed unknown to break the module cycle, like TensorPartialDerivativeNode
  readonly wrt: unknown;          // ExprNode — used for its dim only (same as pderiv)
  readonly wrtIndex: CovariantIndex;
  readonly gLower: MetricTensorNode;
  readonly gInverse: MetricTensorNode;
}
```

The `gLower`/`gInverse` slots are full child nodes — they carry their own free indices, but those indices are **consumed internally** by the Christoffel formula's contractions and never propagated upward (see §7 H1 fix).

### `NumericalInputs` extension

```typescript
export interface NumericalInputs {
  // ... existing v0.3.5 fields ...
  /** For 'supplied' derivativeStrategy metrics: ∂g components keyed
   *  `${metricName}/${coordLabel}` (e.g., 'g/μ'). Each value is the full
   *  metric Jacobian slice — same shape as the metric. */
  readonly metricDerivatives?: ReadonlyMap<string, NestedArray>;
}
```

## 5. The `christoffel()` helper

```typescript
// src/dimensional/connection.ts (new module — parallels metric.ts)
import { contract, scalarOp } from './tensor.js';
import { pderiv, metric } from './metric.js';

/**
 * Christoffel symbol Γ^λ_μν = (1/2) g^λρ (∂_μ g_ρν + ∂_ν g_ρμ − ∂_ρ g_μν).
 *
 * Returns a composite tree of existing v0.3.0 nodes. The fresh contracted
 * label `ρ` is generated deterministically (same scheme as raise/lower's
 * `freshLabel`) so the returned tree is reproducible and serializable.
 *
 * Levi-Civita connection only (uses the metric pair). Non-Levi-Civita
 * connections are v0.5.0+.
 */
export function christoffel(
  gLower: MetricTensorNode,
  gInverse: MetricTensorNode,
  upper: string,         // λ
  lowerA: string,         // μ
  lowerB: string,         // ν
  xCoord: TensorSymbolNode,  // the coordinate field, role='coordinate'
): ExprNode;

/** Helper: check Christoffel symmetry Γ^λ_μν = Γ^λ_νμ structurally.
 *  Returns true iff the tree built by christoffel(...,μ,ν,...) is
 *  index-equivalent to the tree built with μ,ν swapped (after alpha-conv). */
export function isChristoffelSymmetric(node: ExprNode): boolean;
```

The fresh-label scheme: `christoffel()` introduces ONE dummy label `ρ` (contracted between `g^λρ` and the `∂g` terms). Per Part-VIII §VIII.5's `raise-lower-fresh-label-deterministic` TENSOR-RULE, the fresh label is `<base>_<counter>` (e.g., `ρ_1`) when `ρ` collides with operand free indices.

## 6. AD interface on `TensorEngine`

Two **optional** methods added to the `TensorEngine` interface:

```typescript
export interface TensorEngine {
  // ... existing v0.3.5 methods ...

  /**
   * Forward-mode AD via dual numbers. Returns the value and the FULL
   * Jacobian. For an input of shape [n_1, n_2, ...] and an output of
   * shape [m_1, m_2, ...], the returned jacobian has shape
   * [m_1, m_2, ..., n_1, n_2, ...] (output-axes first, then input-axes,
   * row-major). Element [i_y, ..., i_x, ...] is ∂y[i_y...] / ∂x[i_x...].
   *
   * @public — required for any engine intending to support v0.4.0
   * Christoffel/∇_μ via the 'computed' derivativeStrategy.
   */
  forwardGrad?(
    fn: (x: EngineTensor) => EngineTensor,
    x: EngineTensor,
  ): { value: EngineTensor; jacobian: EngineTensor };

  /**
   * Reverse-mode AD via tape + backward pass. Returns the value and the
   * vector-Jacobian product (VJP) with respect to the cotangent.
   *   gradient[i_x...] = Σ_y cotangent[y...] · ∂value[y...] / ∂x[i_x...].
   * gradient.shape === x.shape. cotangent defaults to ones-like(value)
   * when value is scalar; for non-scalar value the cotangent is required.
   *
   * @public — additive forward-compat. v0.4.0 doesn't depend on
   * reverseGrad for the release tests (forward-mode is enough for the
   * connection layer's 10×4 Jacobian), but ML-style consumers benefit
   * from the symmetry.
   */
  reverseGrad?(
    fn: (x: EngineTensor) => EngineTensor,
    x: EngineTensor,
    cotangent?: EngineTensor,
  ): { value: EngineTensor; gradient: EngineTensor };
}
```

**Implementation notes:**

- **`Float64ReferenceEngine.forwardGrad`**: dual numbers — every `Float64Tensor` op extends to operate on `{ primal, tangent }` pairs (one tangent per input dimension; loop over `x.size` to fill out the Jacobian). For the connection layer's `n=4` coordinates, four sweeps. No tape, no graph; the AD is local to each engine op.
- **`Float64ReferenceEngine.reverseGrad`**: a small tape (every engine op records its inputs + a backward closure). Backward pass replays in reverse. More machinery than forward-mode but standard textbook reverse-mode AD.
- **`MathTSEngine.forwardGrad` / `reverseGrad`**: thin adapters delegating to the underlying `Tensor`'s AD ops. (MathTS does not currently ship AD; v0.4.0 adds it to `@danielsimonjr/mathts-tensor` as part of the [M] track.)

**Convention (Adam L2):** the `christoffel()` lowering pass requests the **full** `∂g` Jacobian in ONE `forwardGrad?` call (using the metric function `r → g(r)` as `fn`). Component-by-component is forbidden by the design — it would defeat the batched AD path. The conformance suite explicitly tests that a known-derivative function `fn(x) = x · x` returns the correct full Jacobian in one call.

**Closure convention for non-coordinate parameters:** the lowering pass constructs `fn` from the `metric-tensor` AST + the supplied `NumericalInputs`. Non-coordinate parameters that the metric depends on (e.g., `M_kg` for Schwarzschild) are **captured in `fn`'s closure** by the lowering pass — they do not appear as additional arguments to `forwardGrad?`. The only variable seen by the AD engine is the coordinate tensor `x`. This keeps the AD interface clean (one input, one output) and matches the standard partial-derivative semantics (∂/∂x holds all other parameters fixed).

## 7. Validator changes

### Dedicated `covariant-derivative` case (Eve H1 fix)

The validator's `infer()` recursion gains a `case 'covariant-derivative'`. It validates:
- `wrtIndex.variance === 'lower'` (mirrors pderiv).
- `gLower.indices` both `'lower'` variance.
- `gInverse.indices` both `'upper'` variance.
- `gLower.signature === gInverse.signature`.
- `gLower.dim` and `gInverse.dim` form a coherent inverse pair (the v0.3.5 InverseMetricInconsistencyWarning machinery fires here for free — `scanForMetricPair` already detects this pair).
- `node.of` is validated via `inferArgLocal()` (its free indices are merged into the result).
- `gLower` and `gInverse` are validated **without propagating their free indices upward** — they're consumed internally by the Christoffel contractions. (This is the H1 fix: a dedicated case mirroring `tensor-partial-derivative`'s `pderiv-ignores-wrt-own-indices` rule but for the embedded metrics.)

Output:
- `dim = divide(of.dim, wrt.dim)` (same as pderiv).
- `freeIndices = of.freeIndices ∪ { wrtIndex.label: lower }` (matches `∂_μ V^ν` and `Γ^ν_μλ V^λ` by construction — Adam verified by trace).

### Duplicate-`derivativeStrategy` warning (Eve M2 fix)

A post-walk pass scans the AST for any `metric-tensor` nodes sharing a `name` but carrying different `derivativeStrategy` values. If found, push a `severity: 'warning'` Violation with note `DuplicateDerivativeStrategyWarning: metric '<name>' is tagged '<a>' at one site and '<b>' at another — strategies must be consistent across a single AST`. Deduplicated by `(name, strategyA, strategyB)` tuple. Same pattern as v0.3.5's `InverseMetricInconsistencyWarning`.

## 8. Worked examples

### Primary — Schwarzschild geodesic equation (release-criterion test)

The geodesic equation `d²x^μ/dτ² + Γ^μ_νρ ẋ^ν ẋ^ρ = 0` is `∇_v v = 0` for the tangent 4-velocity `v`. Test setup:

- **Metric**: Schwarzschild in Schwarzschild coordinates `(t, r, θ, φ)`, `g_μν = diag(−(1 − 2M/r), 1/(1 − 2M/r), r², r² sin²θ)` (Lorentzian, mostly-plus). Stored as a `metric-tensor` node with `derivativeStrategy: 'computed'`.
- **Initial conditions**: radial infall from `r₀ = 10·r_Schwarz` with `dr/dτ = 0` (initially at rest); equatorial plane `θ = π/2`; `dθ/dτ = dφ/dτ = 0`; `dt/dτ` set so that `g_μν ẋ^μ ẋ^ν = −c²` (timelike normalization).
- **Integration**: 8-dim state vector `[t, r, θ, φ, dt/dτ, dr/dτ, dθ/dτ, dφ/dτ]`; ODE is the geodesic equation; Γ at each step computed via `engine.forwardGrad?` on the metric function. **Domain restriction: integration stops when `r ≤ 3·r_Schwarz`** (safely above horizon — H2). Step count chosen so the cross-check below holds.
- **Cross-check**: integrated trajectory `r(τ)` matches the analytic Schwarzschild radial-infall solution (closed-form via integration of the energy equation) to **±10⁻⁹ relative** on the final state.

This is the canonical "GR has a working connection layer" test. Reuses v0.3.5's `null-ray-integrator` (extended from a 1-dim state to an 8-dim state).

### Secondary — BE-37 covariant-eikonal preview

`g^μν (∇_μ S)(∇_ν S) = 0` for the scalar eikonal phase `S` (a `tsym('S', [], LENGTH)`). For scalar `of`, `∇_μ S = ∂_μ S` (Christoffel terms cancel — they only contribute on tensors of rank ≥ 1). The numerical result must match v0.3.5's `evaluateBE37EikonalNumerical()` eikonal residual to **machine precision** (no relative-error tolerance — same data, same arithmetic; any divergence is a real bug).

This is a low-cost preview test that confirms the §VIII.8 "only the operator changes" promise structurally.

## 13. Risks and open questions

- **Free-index scanner edge on `covariant-derivative`'s embedded metrics** (Eve HIGH H1) — **resolved**: dedicated validator case that consumes the metric children's indices internally (§7).
- **Schwarzschild coordinate singularity at r = 2M** (both HIGH H2) — **resolved**: integration domain restricted to r ≥ 10·r_Schwarz (test exits at r = 3·r_Schwarz; safely above horizon).
- **AD interface shape asymmetry under-specified** (Eve HIGH H3) — **resolved**: shapes pinned in §6 (jacobian.shape = `[...value.shape, ...x.shape]`; gradient.shape = x.shape; row-major flatten).
- **Release-process fragility on the optional → regular dep flip** (both MEDIUM M1) — **mitigated**: explicit release runbook in §17.
- **`derivativeStrategy: 'supplied'` needs public type plumbing + duplicate-tag warning** (Eve MEDIUM M2) — **resolved**: `NumericalInputs.metricDerivatives` is in scope (§4); duplicate-tag warning is in scope (§7).
- **"Cancel structurally" wording imprecision** (Adam LOW L1) — **resolved**: this doc says "match by construction" (§7).

## 14. Forward-compatibility sanity checks

### 14.1 `derivativeStrategy` field is additive
Optional field defaulting to `'computed'`. Every v0.3.x AST is a valid v0.4.0 AST unchanged. JSON round-trip: plain string. SemVer MINOR.

### 14.2 `covariant-derivative` node is additive
New ExprNode union arm. Every v0.3.x AST is a valid v0.4.0 AST (no existing node kind contains a `covariant-derivative`). Validator exhaustiveness check covers it. SemVer MINOR.

### 14.3 AD interface additions are optional
`forwardGrad?` / `reverseGrad?` are optional. v0.3.5 engines that didn't implement them remain valid `TensorEngine` instances; consumers who don't use AD aren't affected.

### 14.4 v0.5.0 curvature numerical composition
Riemann tensor `R^μ_νρσ = ∂_ρ Γ^μ_νσ − ∂_σ Γ^μ_νρ + Γ^μ_ρλ Γ^λ_νσ − Γ^μ_σλ Γ^λ_νρ` uses `∂_ρ` of `Γ`, which under `'computed'` `derivativeStrategy` requires **second-order** AD (∂ of ∂g). Forward-of-forward composes cleanly through the v0.4.0 interface — `engine.forwardGrad(x => forwardGrad(g, x).jacobian, x)` works structurally. v0.4.0's interface is forward-compat with this; v0.5.0 may add a `forwardHessian?` convenience method.

### 14.5 v0.5.0+ AST-size optimization
Each `covariant-derivative` currently carries full `gLower`/`gInverse` trees. Curvature creates Γ-of-Γ terms → AST size grows quadratically. v0.5.0+ refactor candidates: (i) a metric-name pointer (the node carries only `gLower.name` / `gInverse.name` strings, resolved at lowering time via an `inputs.metrics: Map<name, MetricTensorNode>`); (ii) a CSE table (shared metric subtrees deduplicated by structural hash). Either is additive to the v0.4.0 node shape.

### 14.6 v0.5.0+ Faraday-cascade BREAKING refactor
v0.4.0 commits to uniform-dim metrics only (Part-VIII §VIII.10). The `derivativeStrategy` field on `metric-tensor` is orthogonal to the per-component-dim shape — the v0.5.0+ `dim: Dimension | DimensionMatrix` refactor doesn't touch `derivativeStrategy`. Independent axes.

### 14.7 Non-Levi-Civita connections
v0.4.0's `covariant-derivative` carries `gLower` + `gInverse` — implicitly Levi-Civita (Christoffel from metric). For teleparallel/Cartan connections in v0.5.0+, an additive variant `covariant-derivative-general` could carry a `connection: ConnectionSymbol` field instead. The v0.4.0 shape doesn't preclude this addition.
