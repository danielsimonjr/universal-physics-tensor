# v0.7.1 Brainstorm — OPTIMIZE axis

Sister doc to the (forthcoming) MINIMIZE / SIMPLIFY brainstorms for the
v0.7.1 post-v0.7 hygiene sprint. Same shape as v0.6.1 Phase 5 — surface
perf-bench candidates and order them by leverage/risk so the design pass
can pick a subset to actually implement.

**Provenance.** Numbers below come from `docs/architecture/benchmarks.md`
v0.6.1 baselines (PO-1 single-stage Mercury solve at 2,742 hz/0.365 ms;
PO-2 Riemann FD pipeline at 2,303 hz; PD-grid order=4 at 8,388 hz / 3.31 µs
per-call). Recall the v0.6.0 BR-2 win for calibration: migrating
`christoffelFn` from `number[4][4][4]` to `Float64Array(64)` produced a
~5–6× RK4 end-to-end speedup (`+507%` mean across step counts) and as
a side effect dropped the Shapiro residual 4 orders of magnitude.
That's the empirical "high leverage" bar this brainstorm tries to match.

**Scope of OPTIMIZE.** Anything that (a) reduces wall-time of an existing
hot path, (b) reduces GC pressure that masks the inner-loop signal, or
(c) lands a regression-detection bench so a future refactor can't silently
regress an established baseline. **Out of scope** for this axis: API
ergonomics (SIMPLIFY), dead-code removal (MINIMIZE), correctness fixes
(separate audit).

## Cross-cutting observations

1. **The PG metric closes the near-horizon Kretschmann gap with the same
   anti-pattern BR-2 fixed for Schwarzschild.** `painleveGullstrandGFn`
   returns `number[4][4]` on every call (file:lines 89-94 + 121-126). This
   is exactly what made `christoffelFn` the bottleneck before BR-2.
   `painleve-gullstrand-metric.ts` is the canonical near-horizon FD seed
   per the v0.7 design note — if it gets used in a Kretschmann sweep over
   {r/r_s ∈ [1, 5]} × {θ ∈ [0, π]} (e.g., 50×20 grid → 1000 evaluations),
   the nested-array allocation will dominate the same way. O-6 captures
   it; it should be the **first benched** item to confirm the prediction
   before fixing.

2. **The biggest unaddressed win is fixture-side, not module-side.**
   `schwarzschildGInverseFn` and `schwarzschildDgInverseFn` allocate
   `number[4][4]` / `number[4][4][4]` literal arrays on every call
   (`tests/fixtures/schwarzschild.ts:182-200` and `:228-251`). PO-1
   measures `solveGL4Stage`, which calls these closures **4 times per
   Picard iteration × ~35 iters = ~140 nested-array allocations per
   call**. The fixture is consumer-facing (also used in `bench/`,
   `bench/geodesic-conservation.bench.ts`, and many tests), but the
   migration story is mature (BR-2 already established the flat-array
   pattern). O-1 is the highest-leverage swing.

3. **Picard iteration allocates two `number[][]` per iteration** —
   `gl4-integrator.ts:200-201`:
   ```
   const Xnew: number[][] = [new Array(dim).fill(0), new Array(dim).fill(0)];
   const Pnew: number[][] = [new Array(dim).fill(0), new Array(dim).fill(0)];
   ```
   At ~35 Picard iters/step × 1000 steps = 35 000 of each per Mercury
   bench call. O-2 captures this. Combined with O-1, the PO-1 single-stage
   number should drop noticeably (current baseline 0.365 ms/call; target
   <0.15 ms/call would represent the BR-2-class win on this surface).

4. **`christoffelAt` engine round-trip is structural waste.** Line 153
   builds Γ as an `EngineTensor`, immediately calls `engine.toNested`
   (line 154), then `engine.dispose?.()` (line 155). The result is fed
   into pure-JS nested-array math in `buildRiemann` /
   `lowerFirstIndex`. The engine is doing zero useful work for the
   curvature-lowering pipeline — it's a relic of the v0.4.0 covariant-
   derivative pattern. O-4 captures this; the gain compounds because
   `dGammaAt` calls `christoffelAt` 4 times per axis × 4 axes = 16 times,
   and each axis uses the 4-point stencil → 4·4·4 = 64 christoffelAt
   evaluations per `dGammaAt` call. PO-2 baseline (0.434 ms) sets the
   bar; the engine round-trip alone could plausibly be 20–40% of that.

5. **Kretschmann is the one place where 4⁸ vs 4⁴ matters.**
   `kretschmann.ts:62` has a 7-deep nested loop (256² = 65 536 multi-
   plications per call). The module's own JSDoc calls out the symmetry-
   exploitation opportunity (lines 9-13) and estimates "~12×" — the
   v0.6.0 brainstorm carry-forward originally tracked it. The risk tier
   is HIGH because the symmetry math (`R_{ρσμν} = -R_{σρμν}`, etc.) has
   to be re-derived as compile-time index reductions. O-3 captures it;
   recommend designing it as a wrapper around the existing simple form
   so the analytic cross-pin (vs Schwarzschild closed-form K =
   48 G²M²/(c⁴ r⁶)) keeps both implementations honest.

6. **Validator hot-path is informational only.** O-10 (validator
   allocation reduction) won't move user wall-time meaningfully — the
   suite cold-start is dominated by vitest's TS compile/transform (3-5 min
   on Windows per CLAUDE.md), not by validator allocator pressure.
   Worth measuring once to confirm, not worth optimizing speculatively.

7. **AD path is not the place to optimize this sprint.** P8
   bridge-gradient is bounded by the autograd peer (which is documented
   absent on this dev box). Optimizing the wrapper around an absent
   dependency is premature. Defer until the peer is reliably present in
   CI.

## Per-candidate detail

### O-1 — Migrate Schwarzschild fixture metric closures to flat `Float64Array`

**Target.** `tests/fixtures/schwarzschild.ts:182-200`
(`schwarzschildGInverseFn`) and `:228-251`
(`schwarzschildDgInverseFn`). Both return fresh nested arrays on every
call. Consumed by every GL4 bench, every Mercury / Shapiro test, and
PO-1.

**Hypothesis.** Mirror the BR-2 pattern: return
`Float64Array(16)` (g_inverse, row-major 4×4) and `Float64Array(64)`
(dg_inverse, λ-major as in `christoffel-flat.ts`). At
~140 closure-calls per PO-1 single-stage iteration × the existing
allocation cost, this should shave 30–60% off PO-1 mean. Combined with
O-2 (Picard alloc), the target is to push PO-1 from 0.365 ms → ≤0.15 ms.

**Measurement plan.** PO-1 + a new
`bench/schwarzschild-metric-closure.bench.ts` that benches the
isolated `gInverseFn(x)` and `dgInverseFn(x)` calls in a tight loop
(mirrors PD-grid's structure — "informational-only, no threshold").
Capture both pre/post under the same vitest 4.1.7 reporter (hz column
now displays for async benches — see `benchmarks.md` measurement
notes update).

**Estimated impact.** HIGH (suspected 2-5× on PO-1; potential 1.5-3×
end-to-end on `bench/gl4-mercury-1000step.bench.ts` via Amdahl).

**Risk.** MEDIUM. The `GL4Options.gInverseFn` and `dgInverseFn`
signatures (`gl4-integrator.ts:112-118`) are `(x) => readonly (readonly
number[])[]` and `(x) => readonly (readonly (readonly number[])[])[]`.
Switching to `Float64Array` is a breaking change to those types —
mirrors BR-2's surface impact. Requires consumer-side migration in:
- `bench/gl4-picard-alloc.bench.ts`
- `bench/gl4-mercury-1000step.bench.ts`
- `bench/geodesic-conservation.bench.ts`
- `src/numerical/be37-covariant-eikonal.ts`
- All `tests/numerical/gl4-*` tests

Possible mitigation: ship an overload accepting both shapes during a
deprecation window. The BR-2 precedent took the breaking-change
approach — cleaner.

### O-2 — Pre-allocate Picard ping-pong buffers in `solveGL4Stage`

**Target.** `src/numerical/gl4-integrator.ts:196-201`. Each Picard
iteration re-allocates `Xnew` and `Pnew` as nested `number[][]`.

**Hypothesis.** Replace with two pre-allocated `Float64Array(8)` (or
`Float64Array(2*dim)`) buffers and a ping-pong index. The convergence
loop and the final `stageX`/`stageP` materialization are unchanged. At
35 iters × 4 allocations/iter = 140 allocations/call eliminated.

**Measurement plan.** PO-1 mean ms (existing bench). Expect mean to
drop 0.365 ms → 0.20–0.25 ms range purely from this change. Layered
with O-1, target ≤0.15 ms.

**Estimated impact.** HIGH (1.5-2.5× on PO-1 standalone).

**Risk.** LOW. `solveGL4Stage` is `@internal` (not exported from
public surface — confirmed at `gl4-integrator.ts:155-159` comment
"v0.6.1: dropped export"). The Picard loop has bit-exact tests
(`tests/numerical/gl4-*`) that will catch any algebraic regression.

### O-3 — Exploit Riemann symmetries in `computeKretschmann`

**Target.** `src/numerical/kretschmann.ts:62-90`. Current implementation
is 7-deep loop, 256² = 65 536 inner multiplications.

**Hypothesis.** Riemann symmetries in d=4:
- `R_{ρσμν} = -R_{σρμν}` (antisymm first pair)
- `R_{ρσμν} = -R_{ρσνμ}` (antisymm second pair)
- `R_{ρσμν} = R_{μνρσ}` (pair-exchange)
- First Bianchi `R_{ρ[σμν]} = 0`

reduce the 256 components to **20 independent ones in d=4**. Module's
own JSDoc estimates ~12× speedup (line 11). At Schwarzschild's 12
non-zero independent components (per the `christoffel-flat.ts`
docstring analog), the contracted sum has even fewer terms — exploiting
both symmetry **and sparsity-aware iteration** could compound past 12×.

**Measurement plan.** New
`bench/kretschmann-symmetry.bench.ts` comparing the naive 4⁸ form vs
the symmetry-reduced form. **Correctness gate**: cross-pin against
Schwarzschild closed-form `K = 48 G²M²/(c⁴ r⁶)` at r = {3, 5, 10, 20}·r_s
to relErr ≤ 1e-9. Both forms must agree to ≤ machine epsilon × 256
(round-off compounding across the contraction).

**Estimated impact.** HIGH for Kretschmann standalone (10-15×). Caveat:
Kretschmann is currently a diagnostic call, NOT in a tight integration
loop (per the module's own warning at lines 8-12). So end-to-end impact
on the suite is minimal — this is a "future-proofing the near-horizon
sweep" optimization. If the v0.7 near-horizon Kretschmann gap-closing
plan calls Kretschmann at 1000 sample points, it becomes load-bearing.

**Risk.** HIGH. Algorithm change. The symmetry-reduced form is not a
mechanical refactor — it needs index-pair canonicalization (probably
hoist to a compile-time table of the 20 independent (ρ,σ,μ,ν) tuples
+ multiplicities). **Recommend Adam+Eve design-vet** before
implementation: easy to get wrong in subtle ways (e.g., the pair-
exchange symmetry interacts non-trivially with the metric-raising
when one index sits on a g_{σμ} non-diagonal — but Schwarzschild is
diagonal, masking the bug until a Kerr fixture exposes it).

### O-4 — Flat-array `christoffelAt` to skip engine round-trip in FD pipeline

**Target.** `src/numerical/curvature-lowering-helpers.ts:139-162`
(`christoffelAt`) + its 16-time consumption inside
`dGammaAt` (`:171-222`).

**Hypothesis.** `christoffelAt` builds Γ as an `EngineTensor`
(line 153 `computeChristoffelTensor`), calls `engine.toNested(tensor)`
(line 154), then `engine.dispose?.(tensor)` (line 155). The nested
output is fed into pure-JS arithmetic in `buildRiemann` and
`lowerFirstIndex`. The engine round-trip is structurally pointless for
this lowering pipeline. Add a sibling `christoffelAtFlat` that returns
`number[N³]` directly (skipping `engine.fromNested` /
`engine.toNested`) and route `dGammaAt`, `riemannUpperAt`, and
`lowerWeylTensor` to it.

**Measurement plan.** PO-2 baseline 2,303 hz / 0.434 ms. Expect 1.5-2×
on PO-2 + slightly more on the Weyl-tensor lowering arm. Add
`bench/christoffel-flat-vs-engine.bench.ts` to isolate the round-trip
overhead.

**Estimated impact.** HIGH (PO-2 is dominated by the FD pipeline per
the v0.6.1 baseline — "Ricci contraction is essentially free, 1.01×").

**Risk.** MEDIUM. `computeChristoffelTensor` is exported, and the
return-type change would be breaking. Cleanest path: keep the existing
engine-returning function and add `computeChristoffelTensorFlat` as a
sibling; route only the FD-lowering path. (Same pattern as O-1.)

### O-5 — Reduce per-call allocation in `pderivNumericalFn`

**Target.** `src/numerical/pderiv.ts:122-153`. Order-4 path allocates
4 fresh coord vectors (`[...coords]`) per call + uses `.map()` for the
difference computation.

**Hypothesis.** `pderivNumericalFn` is called from the inner FD layer
(`makeInnerGradFn` for ∂g) AND the outer layer (`dGammaAt` for ∂Γ).
PD-grid order=4 bench is at 8,388 hz / 3.31 µs per call.
Per-call allocations:
- 4× `[...coords]` (coords is `readonly number[]`, length 4) → 4
  small arrays
- 4× `flattenNA` walk over fn returns (each allocates internally — see
  `connection-lowering-helpers.ts:31-40`)
- 1× `.map()` final difference → 1 array of size N²·N or N²·N²

Pool the coord scratch buffer; replace `.map()` with a `for` loop into
a pre-sized `Float64Array`. Expect 1.3–1.6× on PD-grid; layered with
O-9 (`flattenNA` flattening cost) the compound could approach 2×.

**Measurement plan.** Re-run PD-grid order=4 + order=2 (existing
bench). The order=2/order=4 ratio (currently 2.41× — order=4 slower)
should compress if the per-call overhead is what dominates rather than
the FD math.

**Estimated impact.** MEDIUM (1.3–1.6×; secondary effect on PO-2 since
`pderivNumericalFn` is also in the dGamma layer).

**Risk.** LOW. Internal function (interface dropped export in v0.6.1).
Pure-allocation refactor.

### O-6 — Migrate Painlevé-Gullstrand metric closures to `Float64Array`

**Target.** `src/numerical/painleve-gullstrand-metric.ts:80-95`
(`painleveGullstrandGFn`) + `:112-127` (`painleveGullstrandGInverseFn`).
Both return fresh `number[4][4]`.

**Hypothesis.** Same anti-pattern Schwarzschild had pre-BR-2.
PG is the near-horizon FD seed per the v0.7 design note; if a
Kretschmann sweep over 50×20 = 1000 sample points lands in v0.7.1+,
the closure allocation will dominate the same way christoffelFn did.

**Measurement plan.** New `bench/pg-metric-closure.bench.ts` benching
the isolated PG closure calls (mirror O-1's bench shape). Then compare
a 50×20 sample-grid Kretschmann pass before/after.

**Estimated impact.** MEDIUM standalone, HIGH if the near-horizon
sweep ships. Best framed as a **prophylactic** — the gain is recoverable
later; the cost now is small (these are two ~15-line closures).

**Risk.** MEDIUM. The PG closures are `@public` (newly added in v0.7);
no existing consumers besides tests. Breaking the return shape is
cheap in raw consumer count but uses a stable-since-v0.7 public API.

### O-7 — Flat-array `buildRiemann` output

**Target.** `src/numerical/curvature-lowering-helpers.ts:233-262`.
Output allocates 4-deep nested array via `Array.from` of `Array.from`
of `Array.from` of `new Array(N).fill(0)` = 4 + 16 + 64 + 256 = 340
small allocations per call.

**Hypothesis.** Return `Float64Array(N⁴)` with row-major layout
`R[ρ*N³ + σ*N² + μ*N + ν]`. Consumers (`lowerFirstIndex`,
`riemannLowerAt`, `bianchiResidualAt`, `lowerWeylTensor`,
`computeKretschmann`) all eventually flatten anyway. Eliminates 340
allocations per call + cache-friendlier inner loop.

**Measurement plan.** PO-2 baseline. Expect 1.2–1.5×. Layered with O-4
(christoffelAt flat) and O-3 (Kretschmann symmetries), the cumulative
PO-2 wins could approach 3×.

**Estimated impact.** MEDIUM.

**Risk.** MEDIUM. Three downstream consumers need migration:
- `lowerFirstIndex` (private helper)
- `riemannLowerAt` (exported)
- `lowerWeylTensor` (exported, but calls `computeWeylTensor` which
  takes nested `number[][][][]` — would need a `computeWeylTensorFlat`
  sibling)

Risk is moderate because the symmetry of the flat-array migration is
well-established (BR-2 precedent).

### O-8 — Hoist `einsum` axis-coverage guard + `idx` scratch buffer

**Target.** `src/numerical/float64-engine.ts:526-541` (axis-coverage
`Set<number>` per einsum call) + `:560-567` (`new Array<number>(rank)`
inside `operandFlatIndex` for every output cell).

**Hypothesis.** Axis-coverage guard runs in O(rank · ops + free + contract)
per call but `new Set()` is a heap allocation. For typical use
(rank-4 einsum with 4 operands) this is ~16 small Set ops per call.
Hoisting to a per-spec memo (the spec object is typically shared
across many calls in a pipeline) saves the alloc.

The inner `operandFlatIndex` allocates `new Array(rank).fill(0)` PER
OUTPUT CELL — at a 4×4 output × 4×4×4×4 contractions iterated, that's
256 allocations per einsum call. Pre-allocate ONE scratch idx buffer
per operand outside the `forEachIndex` callback.

**Measurement plan.** New `bench/einsum-hot-loop.bench.ts` with a
typical curvature einsum (4-operand metric-raising of Riemann).
Compare pre/post.

**Estimated impact.** LOW–MEDIUM (informational; depends on how often
einsum is on the hot path — currently `lowerWeylTensor` and several
catalog evaluators use it).

**Risk.** LOW. Engine-internal optimization.

### O-9 — Iterative two-pass `flattenNA`

**Target.** `src/numerical/connection-lowering-helpers.ts:31-40`.
Current recursive implementation allocates intermediate `out: number[]`
and `walk` closures.

**Hypothesis.** Two-pass impl: pass 1 counts leaves into a known
size; pass 2 fills a pre-sized `Float64Array(count)`. Eliminates
unbounded `out.push()` resizes. Used in every FD round-trip and every
metric closure flattening — touches PO-1, PO-2, PD-grid.

**Measurement plan.** Standalone microbench
`bench/flatten-na.bench.ts` over nested arrays of shapes [16], [64],
[256] (the Christoffel + Riemann sizes). Then re-run PO-2 to see if
the bridge layer benefits.

**Estimated impact.** LOW–MEDIUM (microsecond shavings × thousands of
calls).

**Risk.** LOW. Pure replacement; signature unchanged (still returns
`number[]`).

### O-10 — Validator probe-map pooling

**Target.** `src/dimensional/validator.ts:206` (`inferArgLocal` creates
`new Map()`) and the multiple `freeIndices: new Map()` sites at lines
259, 373, 659, 691.

**Hypothesis.** Each validate call may invoke `inferArgLocal` dozens
of times for a complex AST. Pool one `Map` and `.clear()` between
probes. Won't move wall-time noticeably because the test suite is

**Measurement plan.** `bench/validator-bench.ts` running each of
`tests/dimensional/dimensional-signature-catalog.test.ts`-style
validate calls in a tight loop.

**Estimated impact.** LOW (suspected <1.2×; almost certainly not worth
fixing).

**Risk.** LOW.

### O-11 — Memoize `ingestCatalog` report

**Target.** `src/bridges/catalog-adapter.ts:348-360`. Catalog is
frozen at module load (`BRIDGE_EQUATIONS` is a const array). Each
call rebuilds the same diagnostic strings.

**Hypothesis.** Cache the report keyed by the catalog identity
(`WeakMap<readonly BridgeEquationEntry[], CatalogIngestionReport>`).
Subsequent calls hit the cache. Helps any caller that does
`ingestCatalog(tensor, BRIDGE_EQUATIONS)` repeatedly (e.g., in a
per-test setup).

**Measurement plan.** Time `ingestCatalog` in a tight loop pre/post.

**Estimated impact.** LOW (informational; the catalog is small enough
that the cold call is fast).

**Risk.** LOW (idempotent — mutation via `tensor.addCell` happens
outside the cached report).

### O-12 — Reduce trajectory snapshot allocation in `integrateGeodesicGL4`

**Target.** `src/numerical/gl4-integrator.ts:449`. Every step pushes
`{ tau, x: x.slice(), p: p.slice() }` — two `.slice()` calls per step
× 1000 steps = 2000 small allocations per Mercury integration.

**Hypothesis.** Offer a "no per-step snapshots" mode that only returns
the final state (matches what the BE-37 Shapiro path needs).
Alternative: emit snapshots into a pre-allocated `Float64Array((steps+1)
* 8)` and have the public API return a view-backed `GL4Snapshot[]`
constructed on-demand.

**Measurement plan.** `bench/gl4-mercury-1000step.bench.ts` (existing)
with two new bench arms: `noSnapshots: true` and `flatSnapshots: true`.

**Estimated impact.** LOW–MEDIUM (1.1–1.3× on the existing Mercury
bench; reduces GC tail).

**Risk.** LOW–MEDIUM. Public API signature for snapshots would change
or gain an option. The snapshot shape is documented (`GL4Snapshot`
interface, public).

## Out of scope

- **Mathts-engine optimization** — the optional peer is documented
  absent on the canonical dev box; can't bench, can't ship.
- **GL4 algorithm change** (e.g., Newton inner solver vs Picard) — out
  of scope for the OPTIMIZE axis; that's a v0.7-series proposal-class
  change, not a hygiene-sprint item.
- **AD path optimization** (P8 bridge-gradient) — bounded by peer
  presence; not the place to invest sprint cycles.
- **Test-suite cold start (3-5 min on Windows)** — dominated by vitest
  TypeScript transform / module-graph cost, not anything UPT controls.
  Defer to a separate "test infrastructure" investigation; not a
  numerical-kernel optimization.
- **Catalog AST validation cost** — already characterised as <1% of
  test-suite wall time in v0.5.x audits; no leverage.
- **Christoffel-flat layout change** (already `Float64Array(64)` per
  BR-2; layout is locked by `encodeChristoffelIndex`).
