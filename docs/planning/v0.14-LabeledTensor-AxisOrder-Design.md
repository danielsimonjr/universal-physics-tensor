# v0.14 — `LabeledTensor` explicit axis-order invariant (Design Note)

Fixes the latent axis-ordering inconsistency the mergeAxes Adam vet surfaced
(`docs/planning/v0.14-MergeAxes-SplitAxis-Design.md` status banner). This is the
prerequisite foundation fix; `mergeAxes`/`splitAxis` are a SEPARATE follow-up
(one foundation change at a time).

## The defect (confirmed against HEAD)

`LabeledTensor` (`src/core/labeled-tensor.ts`) stores `tensor: EngineTensor`
(positional axes) and `labels: Record<string, UniversalIndex>` (string-keyed),
and derives the label→engine-axis mapping IMPLICITLY as
`canonicalLabelOrder(labels)` — the SORTED key order (`:151`). Engine axis `i` is
assumed to be the i-th sorted key. Two operations break this:

1. **`transpose`** (`:277-298`) permutes the engine axes via `engine.transpose`
   but returns `new LabeledTensor(..., this.labels)` with labels UNCHANGED. Since
   sorting the same keys always yields the same order, `canonicalLabelOrder` is
   invariant under transpose — so after any non-identity transpose the engine
   axis order no longer matches the (still-sorted) canonical order. The class
   has NO way to represent "axes in a non-sorted order", so `transpose` cannot
   produce a consistent result for any non-identity permutation. The existing
   test (`labeled-tensor.test.ts:165`) only checks `.tensor.shape`, never re-maps
   labels — the desync is untested.
2. **`contract`** (`:202-268`) maps labels→axes via `canonicalLabelOrder` for
   each operand (correct ONLY when each operand's engine axes are in sorted
   order), and builds the result tensor in einsum-free-emission order while
   building `resultLabels` as a plain record (whose canonical order is sorted).
   When the free-emission order ≠ sorted order, the result violates the
   invariant too.

The bug is currently LATENT: the only `src/` consumer
(`perihelion-precession-labeled.ts:61`) merely CONSTRUCTS a LabeledTensor; no
shipped path does transpose-then-contract. So this is correctness-enablement
(for a correct `transpose` and for future `mergeAxes`), not an active-bug fix.

## The fix: an explicit `axisOrder`

Stop deriving axis position from sorting. Add an explicit, authoritative
`axisOrder: readonly string[]` — the label keys in ENGINE-AXIS order
(`axisOrder[i]` is the key of engine axis `i`). Every operation maintains it.

### Constructor (backward-compatible)

```ts
constructor(tensor, engine, labels, axisOrder?: readonly string[])
```
- `axisOrder` OPTIONAL. When omitted, default to `canonicalLabelOrder(labels)`
  (sorted) — EXACTLY today's implicit behavior, so every existing
  `new LabeledTensor(t, e, labels)` caller is unchanged and correct (their
  tensors are already built in sorted-key order per the current implicit
  contract).
- Validate: `axisOrder` is a permutation of `Object.keys(labels)` (same set,
  length = rank) — throw `LabeledTensorConstructionError` (or a focused new
  error) otherwise. The existing count check stays.
- Expose `public readonly axisOrder` + a helper `axisOf(key): number` /
  `labelKeyAt(axis): string` so consumers never re-derive position by sorting.

### `transpose(newKeyOrder)`
Compute `perm` relative to the CURRENT `this.axisOrder` (not
`canonicalLabelOrder`), permute the engine tensor, and set the result's
`axisOrder = newKeyOrder`. Labels (the id map) are unchanged; only the ORDER
changes. Now correct for any permutation.

### `contract(other)`
Map each operand's label→axis via its own `this.axisOrder` / `other.axisOrder`
(not `canonicalLabelOrder`). Build `resultAxisOrder` by pushing each free axis's
result key IN THE SAME ORDER the free axes are emitted into the einsum `free`
spec (the order that determines the result tensor's axis order). Pass
`resultAxisOrder` to the result `LabeledTensor`. (The result-label COLLISION
suffix logic is unchanged; resultAxisOrder records the possibly-suffixed key.)

### `reshape(shape)`
Same-rank, no axis reorder → pass `this.axisOrder` through unchanged.

### `canonicalLabelOrder`
No longer used for axis mapping; retained as the constructor's default-axisOrder
helper (and any external consumer). Its determinism rationale still holds for
the default case.

## Why an explicit field (not insertion-order)

JS preserves string-key insertion order, so one could use `Object.keys(labels)`
as the order — but `canonicalLabelOrder`'s own docstring (`:142-150`) says it
exists precisely so the algorithm does NOT "accidentally depend on
constructor-call ordering." An explicit `axisOrder` array keeps that determinism
while making the engine-axis mapping authoritative and self-documenting, instead
of swapping one implicit dependency (sorting) for another (insertion order).

## Public surface

`LabeledTensor` is `@public` (`src/index.ts:90`). Changes are ADDITIVE: a new
optional constructor param + a new readonly field + helper method(s). No new
named export ⟹ no `EXPECTED_RUNTIME_EXPORTS` / snapshot / `ALL_TYPE_EXPORTS`
change (those track export NAMES, not class shape). Existing 3-arg construction
is unchanged.

## Test plan

- **Transpose correctness (the previously-broken path):** build a rank-3 tensor
  with known data, `transpose` to a non-sorted key order, and assert (a)
  `.axisOrder` equals the new order, (b) `.tensor` data matches the engine
  transpose at matched positions (via `engine.toNested`), (c) `axisOf(key)`
  returns the correct new position for each label.
- **Transpose-then-contract:** transpose one operand into a non-sorted order,
  then contract with another on a shared id — assert the numerical result equals
  the contract WITHOUT the transpose (the contraction is axis-order-invariant by
  identity), proving `contract` reads axes via `axisOrder` not sorting. This is
  the test that FAILS on the current code and passes after the fix.
- **Contract result axisOrder:** assert the result's `axisOrder` matches its
  engine-axis order (free-emission order), and `axisOf` is consistent.
- **Round-trip:** `transpose(a).transpose(original)` recovers data + axisOrder.
- **Backward-compat:** every existing labeled-tensor test stays green unchanged;
  3-arg construction defaults axisOrder to sorted.

## Open questions for the Adam+Eve vet

1. New focused error for a bad `axisOrder` permutation, or reuse
   `LabeledTensorConstructionError`? (Lean: reuse — same "construction shape is
   wrong" class; add a discriminating message.)
2. Expose `axisOf`/`labelKeyAt` helpers publicly, or keep the `axisOrder` field
   sufficient? (Lean: ship `axisOf` — it's the safe way for consumers, incl. the
   future `mergeAxes`, to get a position without re-sorting.)
3. Does `engine.einsum` actually emit free axes in `spec.free` order across all
   engines (Float64 + MathTS)? (Must verify before relying on it for
   `resultAxisOrder`; the current code already implicitly depends on this.)
