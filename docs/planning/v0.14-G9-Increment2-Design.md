# v0.14 — G-9 Increment 2 (Geometrized Boundary, additive core) — Design Note

Builds on increment 1 (`src/numerical/geometrized.ts`: `geometrizedFactor` /
`toGeometrized` / `fromGeometrized`, internal, `G^M·c^(T−2M)`). The full G-9
increment-2 wishlist (main note `v0.10.0-Units-Normalization-Design-Note.md` r2
§5) is broad and high-blast-radius. This note scopes the **additive, vettable
core** and explicitly defers the disruptive consumer-wide migration to a named
increment 3 — honoring the design's own "do not stack two foundation
re-derivations in one cycle" caution (§"Why not now").

## In scope (additive — existing SI pipeline untouched)

1. **Public-API geometrized adapters.** Surface the three increment-1 functions
   (`toGeometrized`, `fromGeometrized`, `geometrizedFactor`) +
   `NonGeometrizableDimensionError` on the public manifest (`src/index.ts`), so
   consumers can convert at the boundary. They are currently `@internal`; this
   is the "public-API adapters at the boundary" the main note names (r2 §5).
   Re-tag `@internal` → `@public`; export from `src/index.ts`. **All four are
   RUNTIME values** (three functions + one class) — they go in
   `EXPECTED_RUNTIME_EXPORTS` and the snapshot, NOT `ALL_TYPE_EXPORTS` (which is
   type-only) — Adam N2 correction. Acknowledge the countervailing precedent:
   CLAUDE.md keeps `MathTSEngine` deliberately subpath-only, so the repo is NOT
   uniformly pro-exposure; these three are tiny pure dimension-functor helpers
   with no engine coupling (unlike `MathTSEngine`), so surfacing them at the
   boundary is the right call here.

2. **Geometrized-native Schwarzschild fixture.** Add a `G = c = 1` Schwarzschild
   metric fixture (mass in geometrized length units `M_geom = GM/c²`) ALONGSIDE
   the existing SI fixture — NOT replacing it, NOT touching the `unitless*`
   family (that subsumption is increment 3). The coordinate convention is
   **x⁰ = ct** (main note r2 §1: makes all g_μν components dimensionless and the
   conversion uniform — the standard NR choice). In this chart the Schwarzschild
   metric is `g_tt = −(1 − 2M/r)`, `g_rr = (1 − 2M/r)⁻¹`, `g_θθ = r²`,
   `g_φφ = r² sin²θ` with `r_s = 2M`.

   **Chart honesty (Adam M2).** This is NOT a "literal c=G=1 specialization" of
   the SI fixture: `tests/fixtures/schwarzschild.ts` uses the **x⁰ = t** chart
   with an explicit c² in `g_tt` (`g[0][0] = −f·c²`, `schwarzschild.ts:161`,
   threaded through `gInverseFn`/`dgInverseFn`/the Riemann components). The
   geometrized fixture is a DIFFERENT chart (x⁰ = ct), the standard NR choice —
   not a unit-rescale of the same chart. The Kretschmann scalar is invariant
   under the constant single-axis x⁰-rescale (a constant Jacobian on one axis),
   so the two fixtures yield the SAME numerical `K` at matched `(r, θ)`; the
   fixture is validated on its own first against `K = 48 M_geom²/r⁶` before any
   cross-comparison. **The fixture ships `gFn` AND `gInverseFn`** (Eve Y1) — the
   Kretschmann path (`christoffelAt`→`riemannLowerAt`→`computeKretschmann`)
   consumes both; the `Float64Array(16)` inverse layout is accepted by
   `computeKretschmann` directly. It does NOT need `dgInverseFn`/`dgFn`/
   `riemannFn` (those serve Killing/Bianchi/cross-pin paths, out of scope here).

3. **SI-vs-geometrized closed-form equivalence test** (the main note's "one
   pipeline equivalence test", r2 §6 — RESPEC'd per Adam M1). The Kretschmann
   scalar `K` has dimension `L⁻⁴` (pure length), so `geometrizedFactor(L⁻⁴) =
   G⁰·c⁰ = 1` — converting K's OUTPUT is the identity (pinned:
   `geometrized.test.ts:50`), which would make a `fromGeometrized(K_geom, L⁻⁴)`
   test CIRCULAR. The adapter has teeth on the dimensionful INPUTS, not the
   output. So instead: exercise the adapter on the MASS input —
   `M_geom = toGeometrized(M_kg, MASS) = GM/c²` (factor `G/c²`, genuinely
   non-trivial) — then assert the geometrized fixture reproduces its closed form
   `K = 48 M_geom²/r⁶` AND that this equals the SI closed form
   `K = 48 G²M²/(c⁴r⁶)` identically (since `48 G²M²/(c⁴r⁶) = 48 (GM/c²)²/r⁶`).
   That is the real content of "the geometrized path is physically equivalent" —
   the adapter does the c/G work on the mass, not on the L⁻⁴ scalar.

~~4. FD order-2 claw-back / stencil guard~~ — **CUT (Eve Y3).** Per-component
central-difference RELATIVE error `ε|f|/(h|f′|)` is provably scale-invariant
(multiply `f` by c² and numerator + truncation term scale identically), so a
geometrized FD test would measure a UNIT-INVARIANT stencil property that says
nothing about geometrization — and order-2-vs-order-4 stencil behavior is ALREADY
covered by `tests/numerical/pderiv-order.test.ts` + `pderiv-order-default.test.ts`.
A test the author proves a-priori must pass adds no falsification value (ceremony).
The order-4 default stands unchanged. The genuine geometrization precision
question (absolute catastrophic-cancellation in mixed-scale sums like
`g_tt=−f·c²` beside `g_θθ=r²`) is partly already engineered away in SI (the inner
FD step + `schwarzschildDgFn` analytic bypass), so it is NOT a clean win to chase
here; it belongs to the increment-3 default-pipeline migration if anywhere. So
increment 2 ships deliverables 1–3 only.

## Out of scope — increment 3 (named, with rationale)

- **Subsuming the `unitless*` (c=1) fixture family** into the geometrized
  convention (so the repo doesn't carry three conventions). High-churn; touches
  every consumer of `unitlessMinkowski*`/`unitlessSchwarzschild*`.
- **Routing the DEFAULT GR pipeline** (christoffelAt → dGammaAt → buildRiemann →
  GL4, kretschmann/weyl, killing, bianchi, BE-37 eikonal, BE-51/52, perihelion)
  onto a geometrized fast path. This is the blast-radius the main note warns
  about; it is a migration, not an addition, and earns its own plan + vet.
- **The Eve M-1 per-quantity unit-convention tag** (GeV/J, bits/nats) — a
  separate axis from c/G geometrization (main note r2 §7).

Deferring these keeps increment 2 strictly additive: nothing that currently
passes changes behavior; the only new surface is three adapters + one error.
