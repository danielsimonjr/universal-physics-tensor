## Dependency Preconditions (Honest State)

### `mathts-autograd` in `optionalDependencies` — confirmed

`package.json` lists `@danielsimonjr/mathts-autograd: "^0.1.0"` under
`optionalDependencies`. The ambient shim at `src/numerical/mathts-
autograd.ambient.d.ts` (added in v0.5.1, TS-4) permits `tsc` to
resolve the dynamic-import specifier without a `@ts-ignore` directive.
The ambient body is intentionally empty; runtime narrowing happens at the
call sites in `MathTSEngine.forwardGrad` and `MathTSEngine.reverseGrad`
via `as unknown as MathTSAutograd`.

### `mathts-autograd` installation state — confirmed present in dev env

Running `ls node_modules/@danielsimonjr/` in the repo confirms that the
`@danielsimonjr` scope exists in `node_modules`. The package is installed
in the development environment. However, optional peer presence is NOT
guaranteed in a consumer's install (that is the definition of
`optionalDependencies`). Proposal 8's public surface MUST degrade
gracefully when the import fails, using the existing `EngineCapabilityError`
pattern already wired in `MathTSEngine.forwardGrad` / `reverseGrad`.

### Existing AD infrastructure — what v0.4.0 already shipped

`MathTSEngine` already implements `TensorEngine.forwardGrad` and
`TensorEngine.reverseGrad` (both async, both delegating to the lazy-
imported `mathts-autograd`). The engine contract in `tensor-engine.ts`
exposes both as optional methods; `hasAutogradSupport(engine)` is the
capability guard. `EngineCapabilityError` is the standard throw shape
when the optional peer is absent.

What does NOT yet exist: any bridge-specific surface. The existing AD
methods operate on raw `EngineTensor` inputs and return raw `EngineTensor`
gradients. There is no concept of "bridge parameters" as a named,
typed entity separate from tensor inputs. Proposal 8's value-add is
exactly this layer: map catalog bridges' typed scalar-evaluator
signatures onto the `(paramTensor) → outputScalar` shape that `reverseGrad`
expects, and expose the result under a bridge-idiomatic API.

## Architectural Decisions (locked)

### Decision #1 — Thin wrapper layer in `src/diff/`, not a change to `src/bridges/`

Bridge evaluators (`evaluateShapiroDelay`, `evaluatePerihelionPrecession`,
`evaluateKibbleZurek`, etc.) are typed TypeScript functions that take
a named-field struct and return a scalar (or struct). They are NOT
`EngineTensor → EngineTensor` functions. The autograd package expects the
latter shape.

The design adds a thin parameter-packing layer in `src/diff/` that:

1. Accepts a catalog-idiomatic `(params: P) => number` function and a
   parameter vector `number[]`.
2. Packs the parameter vector into a rank-1 `EngineTensor` (shape `[n]`).
3. Wraps the scalar evaluator as `(x: EngineTensor) => EngineTensor`
   where `x` is the packed parameter tensor and the output is a rank-0
   scalar tensor.
4. Delegates to `MathTSEngine.forwardGrad` or `reverseGrad`.
5. Unpacks the result into `{ value: number; gradient: number[] }`.

This keeps `src/bridges/` free of AD machinery. The existing bridge
evaluators are not modified. Bridge authors need not know about AD; they
write typed scalar functions as before.

### Decision #2 — `MathTSEngine` is required; `Float64ReferenceEngine` is not extended

`Float64ReferenceEngine` does not implement AD (it is a zero-dependency
fallback). Proposal 8 requires `MathTSEngine` explicitly. The public API
requires the caller to provide a `MathTSEngine` instance or throws
`EngineCapabilityError`. This is consistent with the existing `hasAutogradSupport`
guard pattern in `tensor-engine.ts`.

Rationale: extending `Float64ReferenceEngine` with numerical-differentiation
(finite-differences) would duplicate the `mathts-autograd` capability with
O(n) extra evaluations per gradient. That path is an attractive fallback
but is out of scope for v0.9. A caller without `mathts-autograd` can
implement finite-difference gradients themselves using `evaluateShapiroDelay`
et al. directly — the UPT library does not need to own that fallback.

### Decision #3 — Forward vs. reverse mode: caller chooses, docs recommend

The public API exposes both modes via `ADMode = 'forward' | 'reverse'`.
Documentation recommends:

- **Forward mode** when there are few parameters relative to outputs
  (e.g. ∂(Δt)/∂M for one scalar parameter). The Jacobian is computed in
  one forward pass.
- **Reverse mode** for calibration: fitting parameters against observations
  via loss-gradient descent. One reverse pass yields ∂Loss/∂θ for all θ
  simultaneously, regardless of the parameter count n.

For the initial 42-bridge catalog, most queries are ∂(one output)/∂(few
params) — forward mode is fine. Reverse mode becomes essential at
composition depth (Proposal 6), where a composed bridge may have five or
more internal parameters. Both modes are tested at v0.9; the `ADMode`
selector at call time is the right granularity.

### Decision #4 — Parameter vector semantics: positional, not named

Bridge evaluators use named-field structs (`ShapiroInputs`, etc.)
because names matter for physics legibility. The AD surface requires a
positional `number[]` vector because `mathts-autograd` operates on flat
`Float64Array`-backed tensors.

`BridgeGradSpec.pack` / `unpack` bridge the two representations. They
are trivial for most bridges (field-order declarations). Auto-generation
is rejected because TypeScript key enumeration order is not a stable
API contract. `paramNames` doubles as documentation: `gradient[i]`
unambiguously corresponds to `∂output / ∂paramNames[i]`.

### Decision #5 — No changes to `src/bridges/index.ts` bridge catalog entries

The catalog (`BRIDGE_EQUATIONS`) is not extended with AD metadata in this
sprint. The per-bridge gradient audit (`docs/architecture/bridge-gradient-
audit.md`) is a standalone markdown document, not a new field on
`BridgeEquationEntry`. Adding a `gradientCapability` field to
`BridgeEquationEntry` is a future v0.9+ concern that requires a catalog
schema migration; it is deferred.

### Decision #6 — Adam+Eve adversarial review per the v0.6.1 precedent

Design and plan artifacts each get two parallel Opus subagent reviewers:
one as Adam (steel-manning skeptic, focuses on physics correctness and
AD mode choice), one as Eve (devil's-advocate red-team, focuses on API
surface leakage and graceful-degradation coverage).

## Public API Surface

The new module is `src/diff/bridge-gradient.ts`, re-exported from
`src/index.ts`. The subpath `universal-physics-tensor/diff/bridge-gradient`
is NOT added as a separate exports subpath — the diff surface is small
enough to live in the root barrel.

### Core types

```typescript
// src/diff/bridge-gradient.ts

/** Mode selector for automatic differentiation. */
export type ADMode = 'forward' | 'reverse';

/**
 * Specification that maps a bridge's typed scalar evaluator onto the
 * AD boundary. P is the bridge's parameter struct type (e.g. ShapiroInputs).
 *
 * @public
 */
export interface BridgeGradSpec<P extends object> {
  /** Human-readable bridge label, used in error messages. */
  readonly label: string;
  /**
   * Parameter names in vector order.
   * gradient[i] = ∂output / ∂paramNames[i].
   */
  readonly paramNames: ReadonlyArray<string>;
  /** Pack the typed parameter struct into a flat number array. */
  pack(params: P): number[];
  /** Unpack a flat number array back to the typed parameter struct. */
  unpack(vec: number[]): P;
  /** The scalar evaluator: typed params → one output number. */
  evaluate(params: P): number;
}

/**
 * Result of a differentiated bridge evaluation.
 *
 * @public
 */
export interface BridgeGradResult {
  /** The scalar output value f(params). */
  readonly value: number;
  /**
   * Gradient vector: gradient[i] = ∂f / ∂params[paramNames[i]].
   * Length matches spec.paramNames.length.
   */
  readonly gradient: ReadonlyArray<number>;
  /** AD mode used. */
  readonly mode: ADMode;
}
```

### Core function

```typescript
/**
 * Evaluate a bridge's scalar output and compute its gradient with respect
 * to the specified parameters via automatic differentiation.
 *
 * Requires `@danielsimonjr/mathts-autograd` to be installed. Throws
 * `EngineCapabilityError` if the optional peer is absent.
 *
 * @param engine   A MathTSEngine instance (Float64ReferenceEngine does not
 *                 support AD and will throw EngineCapabilityError).
 * @param spec     Bridge gradient specification (paramNames, pack, unpack,
 *                 evaluate).
 * @param params   The parameter values to differentiate at.
 * @param mode     'forward' for Jacobian-vector product (best for few params);
 *                 'reverse' for vector-Jacobian product (best for many params
 *                 or calibration/fitting tasks). Default: 'reverse'.
 *
 * @returns { value, gradient, mode } where gradient[i] = ∂output / ∂paramNames[i].
 *
 * @throws EngineCapabilityError  if the engine lacks AD support or
 *                                mathts-autograd is not installed.
 * @throws RangeError             if spec.pack(params).length !== spec.paramNames.length.
 *
 * @public
 */
export async function evaluateBridgeWithGradient<P extends object>(
  engine: TensorEngine,
  spec: BridgeGradSpec<P>,
  params: P,
  mode: ADMode = 'reverse',
): Promise<BridgeGradResult>;
```

### Companion helper: finite-difference cross-validator

```typescript
/**
 * Central-finite-difference gradient approximation. Test oracle for AD.
 * Not intended for production use (O(n) evaluations per call).
 * h defaults to 1e-7 × max(|param|, 1) per coordinate (adaptive,
 * avoids catastrophic cancellation on large-magnitude params like M_kg).
 * @public
 */
export function finiteDifferenceGradient<P extends object>(
  spec: BridgeGradSpec<P>,
  params: P,
  h?: number,
): number[];
```

`finiteDifferenceGradient` is the test oracle for every worked example
and is useful to downstream consumers without the optional peer.

## Bridge-Parameter Taxonomy: Differentiability Audit

### Classification framework

Bridges split into three classes for differentiability of the scalar
output w.r.t. catalog parameters:

**Class D (differentiable):** The bridge has a numerical scalar evaluator
whose output is a smooth function of its named parameters over the
physical domain. `forwardGrad` / `reverseGrad` apply directly after
parameter packing. 28 of the 42 catalog entries fall here based on their
`tractability_class` values (`closed-form`: 28, `numerical-tractable`:
13 — but see Class P).

**Class P (partially differentiable):** The bridge has a numerical
evaluator, but one or more parameters appear in a branch condition or
absolute-value boundary that makes the scalar non-differentiable at
isolated points or over measure-zero boundaries. AD is valid away from
those boundaries; callers should avoid evaluating at exact branch points.
7 of the 42 bridges fall here.

**Class N (not differentiable):** The bridge's "output" is a discrete
predicate, a dimensionless ratio used as a bound check, or a formally-
divergent quantity. No continuous gradient is defined. 7 of the 42
bridges fall here.

### Per-bridge classification (sampled — full table in `bridge-gradient-audit.md`)

The five highest-value bridges for AD are those with closed-form,
differentiable outputs and physically-interpretable partial derivatives:

| Bridge | Formula | Key params | Class | AD mode recommendation |
|--------|---------|------------|-------|----------------------|
| BE-37 Shapiro delay | Δt = 2GM/c³ · ln(R_far/R_near) | M, R_far, R_near | D | Forward (few params; analytic check trivial) |
| BE-52 Perihelion precession | Δφ = 6πGM / (a(1−e²)c²) | M, a, e | D | Reverse (three params; calibration from ε obs.) |
| BE-42 Hawking temperature | T_H = ℏc³ / (8πGMk_B) | M | D | Forward (one param; analytic ∂T/∂M = −T/M) |
| BE-11 Decoherence rate | γ_k(λ) = γ_0 (λ/λ_0)² | γ_0, λ, λ_0 | D | Forward (three params; analytic ∂γ/∂λ = 2γ/λ) |
| BE-34 Kibble-Zurek | n ∝ (τ_Q/τ_0)^exp · e^(−mc²/k_BT) | τ_Q, m, T | D | Reverse (calibration of d,ν,z exponents from defect-count obs.) |

Bridges that are non-differentiable or partially differentiable and should
be excluded from the initial AD surface:

- **BE-20 Cosmological constant (vacuum energy):** `formally-divergent`
  tractability — the integral is not a Turing-computable number. No gradient.
- **BE-50 Wheeler-Feynman path integral:** `formally-divergent`. No gradient.
- **BE-36 GW speed bound (|c_GW − c|/c):** An observational bound, not a
  smooth scalar. The "output" is an upper bound on a ratio; no continuous
  differentiable parameter dependence.
- **BE-31 Causal-set Benincasa-Dowker:** `numerical-tractable` via combinatorial
  counting (Ricci scalar from inclusion-exclusion). The output is a
  continuous function of the sprinkle density ρ, but it is computed
  stochastically. AD through a stochastic process requires REINFORCE-style
  estimators, not direct tape differentiation.
- **BE-25 IIT Φ_max:** The outer MIP minimization is a discrete optimization
  over bipartitions; the inner ii(s,s̃) kernel is a smooth scalar and is
  Class D, but Φ_max is Class N at the partition-selector level.
- **BE-28 Onsager entropy production:** Encoded as `σ = Σᵢ Jᵢ Xᵢ` — the
  definiendum of MEPP, not the variational principle. The definiendum is
  Class D; the variational maximization (the actual bridge claim) is Class N.

## Worked Examples

### Example 1 — BE-37 Shapiro Delay: ∂(Δt)/∂M

**Formula:** Δt = (2G/c³) · M · ln(R_far/R_near)

**Analytic gradient:**
- ∂Δt/∂M = (2G/c³) · ln(R_far/R_near) = Δt/M
- ∂Δt/∂R_far = (2GM/c³) · (1/R_far)
- ∂Δt/∂R_near = −(2GM/c³) · (1/R_near)

**Scenario:** Solar mass (M = 1.989 × 10³⁰ kg), R_far = 1.5 × 10¹¹ m (1 AU),
R_near = 1.0 × 10⁹ m. Evaluates to Δt ≈ 5.3 × 10⁻⁵ s (53 μs).

**BridgeGradSpec definition:**

```typescript
const shapiroSpec: BridgeGradSpec<ShapiroInputs> = {
  label: 'BE-37 Shapiro gravitational time-delay',
  paramNames: ['M_kg', 'R_far_m', 'R_near_m'],
  pack: (p) => [p.M_kg, p.R_far_m, p.R_near_m],
  unpack: ([M_kg, R_far_m, R_near_m]) => ({ M_kg, R_far_m, R_near_m }),
  evaluate: evaluateShapiroDelay,
};
```

**Expected gradient at solar-mass scenario:**
- ∂Δt/∂M ≈ (Δt / M) ≈ 2.66 × 10⁻³⁵ s/kg
- ∂Δt/∂R_far ≈ (2GM/c³) / R_far ≈ 3.54 × 10⁻¹⁶ s/m
- ∂Δt/∂R_near ≈ −(2GM/c³) / R_near ≈ −5.31 × 10⁻¹⁴ s/m

**Sanity check:** finite-difference cross-validation with h = 1 × 10⁻⁷ · |param|
should match all three components to relative error < 1 × 10⁻⁶.

**AD mode recommendation:** Forward (3 parameters is "few"; forward Jacobian
has shape [1] × [3] and is exactly what `forwardGrad` returns natively).

### Example 2 — BE-52 Perihelion Precession: ∂(Δφ)/∂(M, a, e)

**Formula:** Δφ_rad = 6π G M / (a (1−e²) c²)

**Analytic gradient:**
- ∂Δφ/∂M = Δφ/M
- ∂Δφ/∂a = −Δφ/a
- ∂Δφ/∂e = Δφ · 2e/(1−e²)

**Scenario:** Mercury (M_sun = 1.989 × 10³⁰ kg, a = 5.791 × 10¹⁰ m,
e = 0.2056, T = 0.2408 yr). Evaluates to Δφ_arcsec_per_century ≈ 42.98 arcsec/century
(Einstein's celebrated 43 arcsec/century prediction).

**BridgeGradSpec definition:**

```typescript
// Differentiate Δφ_rad_per_orbit with respect to (M_kg, a_m, e).
// T_yr is held fixed (it affects only the per-century conversion, not the
// per-orbit radian value). T_yr is excluded from the gradient vector.
const perihelionSpec: BridgeGradSpec<Omit<PerihelionPrecessionInputs, 'T_yr'>> = {
  label: 'BE-52 Perihelion precession Δφ/orbit',
  paramNames: ['M_kg', 'a_m', 'e'],
  pack: (p) => [p.M_kg, p.a_m, p.e],
  unpack: ([M_kg, a_m, e]) => ({ M_kg, a_m, e }),
  evaluate: (p) =>
    evaluatePerihelionPrecession({ ...p, T_yr: 0.2408 }).dphi_rad_per_orbit,
};
```

**Use case — reverse mode for calibration:** Given a set of observed
perihelion advances for multiple solar-system objects (Mercury, Venus,
Earth, Mars, Saturn — each with different a, e, T), fit a single "effective G M_sun"
by gradient descent on ∑ (Δφ_pred − Δφ_obs)². Reverse mode gives the
gradient of the total loss with respect to the single GM_sun parameter
in one pass. Forward mode would also work here (one parameter), but the
reverse-mode pattern generalizes to multi-parameter fits.

**AD mode recommendation:** Reverse mode for calibration (loss gradient w.r.t.
GM is ∂Loss/∂(GM) = ∑ 2(Δφ_pred − Δφ_obs) · ∂Δφ_pred/∂(GM)); forward
mode for sensitivity (which parameter most affects Δφ?).

### Example 3 — BE-42 Hawking Temperature: ∂(T_H)/∂M

**Formula:** T_H = ℏ c³ / (8π G M k_B)

**Analytic gradient:** ∂T_H/∂M = −T_H / M (inverse-linear in M, negative).

**Scenario:** Solar-mass black hole (M = 1.989 × 10³⁰ kg).
T_H ≈ 6.17 × 10⁻⁸ K (textbook Wald GR eq. 14.3.7).

**BridgeGradSpec definition:**

```typescript
const hawkingSpec: BridgeGradSpec<{ M_kg: number }> = {
  label: 'BE-42 Hawking temperature',
  paramNames: ['M_kg'],
  pack: ({ M_kg }) => [M_kg],
  unpack: ([M_kg]) => ({ M_kg }),
  evaluate: ({ M_kg }) => evaluateHawkingTemperature(M_kg),
};
```

**Analytic sanity check:** ∂T_H/∂M at M_sun:
−(6.17 × 10⁻⁸) / (1.989 × 10³⁰) ≈ −3.1 × 10⁻³⁸ K/kg.

**AD mode recommendation:** Forward (one parameter; Jacobian is a scalar).

### Example 4 — BE-11 Decoherence Rate: Coupling-strength sensitivity

**Formula:** γ_k(λ) = γ_0 · (λ/λ_0)²

**Analytic gradient:**
- ∂γ/∂γ_0 = (λ/λ_0)²
- ∂γ/∂λ = 2 γ_0 λ / λ_0²
- ∂γ/∂λ_0 = −2 γ_0 λ² / λ_0³

**Scenario:** γ_0 = 1.0 × 10⁶ s⁻¹, λ = 0.1, λ_0 = 1.0 (dimensionless
coupling ratio). Evaluates to γ_k = 1.0 × 10⁴ s⁻¹.

**Physical interpretation of gradient:** ∂γ/∂λ = 2γ/λ tells the experimenter
how sensitive the decoherence rate is to changes in coupling strength. For
small λ/λ_0, decoherence rates are highly sensitive to coupling fluctuations
(the quadratic scaling amplifies small-λ variation).

**BridgeGradSpec definition:**

```typescript
interface DecohRateParams { gamma0_hz: number; lambda: number; lambda0: number; }

const decohSpec: BridgeGradSpec<DecohRateParams> = {
  label: 'BE-11 Caldeira-Leggett decoherence rate γ_k(λ)',
  paramNames: ['gamma0_hz', 'lambda', 'lambda0'],
  pack: ({ gamma0_hz, lambda, lambda0 }) => [gamma0_hz, lambda, lambda0],
  unpack: ([gamma0_hz, lambda, lambda0]) => ({ gamma0_hz, lambda, lambda0 }),
  evaluate: ({ gamma0_hz, lambda, lambda0 }) =>
    evaluateDecohRate(gamma0_hz, lambda, lambda0),
};
```

**AD mode recommendation:** Forward (three parameters, single output;
forward Jacobian is the full [1×3] Jacobian in one pass).

### Example 5 — Composition depth (forward look)

When Proposal 6 (bridge composition) lands, a composed prediction may
chain BE-37 and BE-52 into one function with five parameters (M, a, e,
R_far, R_near). Reverse mode computes the full ∂f/∂θ vector in one
backward pass; forward mode would require five separate passes. The
`BridgeGradSpec` composed spec simply calls two sub-specs' `evaluate`
functions — no new API needed.

## Phase 2 — Bridge-Specific Specs and Cross-Validation Tests

Four `BridgeGradSpec` instances in `src/diff/specs/`. Each is a regression

## Honest Limitations and Open Questions

**Jacobian shape for scalar output.** The MathTS CHANGELOG gives
`jacobian.shape = [...y.shape, ...x.shape]`. For rank-0 output `y`
and rank-1 input `x` of length n, this implies shape `[n]`, not `[1, n]`.
This must be confirmed by reading `mathts-autograd` source before Task 1.4.
If the shape differs, the Phase 1 unpack step needs adjustment.

**WASM-kernel AD coverage.** The proposals doc (§10.2) notes uncertainty
about whether `mathts-autograd`'s reverse-mode tape covers operations
routed through Rust WASM (FFT, eig, SVD). For the four Phase 2 bridges
this is not a concern — all four evaluators use only `Math.*` scalar
arithmetic. The concern would arise for future bridges that delegate to
Tensor-level operations.

**ODE-integrated bridges (Class D caveat).** The 13 `numerical-tractable`
bridges include ODE-integrated evaluators (BE-47 BBN, BE-26 WKB,
`evaluateBE37EikonalNumerical`). AD through Runge-Kutta is well-defined
in principle; in practice it requires the integrator to propagate tape
operations, not just `Math.*` scalars. Full ODE-bridge AD is deferred to
v0.9.x. Stochastic bridges (BE-31 causal-set) are Class N; REINFORCE
estimators are out of scope.

**Finite-difference fallback mode.** Consumers without `mathts-autograd`
have access to `finiteDifferenceGradient` (zero-dependency, O(n) evaluations).
Promoting it to a first-class `ADMode = 'finite-diff'` value is a low-risk
v0.9.x extension. Deferred from v0.9.0 to keep the optional-peer degradation
path clean.
