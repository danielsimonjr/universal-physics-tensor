## Q1 — Composition surface: shared `Observable` vs per-pair `BridgeAdapter`?

**Context.** Per `docs/specification/Part-IX-Composition.md` §4 +
Adam-F2 finding: existing bridge evaluators return ad-hoc TS
interfaces. A `compose(B_A, B_B)` operator requires a contract.

**Three candidates:**

- (a) **Shared `Observable<RegimeT, ValueT>` interface.** Every
  bridge evaluator returns an `Observable`. Composition is
  structural-typed. **Cost:** breaking change to v0.7+ evaluators
  (would need a v0.10 major bump or a parallel surface).
- (b) **Per-bridge-pair `BridgeAdapter` registry.** A function
  `adapter(B_A_output): B_B_input` registered per composable
  `(B_A, B_B)` pair. **Cost:** combinatorial blowup (42 × 41 / 2
  potential pairs; in practice ~10-15 plausible pairs at v0.9α).
- (c) **Purely numerical cascade on rank-1 tensors.** Treat every
  bridge as `numbers → numbers`. **Cost:** loses all type
  safety; can't enforce dimensional consistency between B_A's
  output and B_B's input.

**Recommendation:** (b) for Phase B; revisit (a) at v1.0 with
all calibration cases lined up to inform the shared shape.

**Phase B must answer this before opening composition code.**

## Q2 — Tolerance discipline for "matches the literature"?

**Context.** Section 6 of Part-IX-Composition.md commits to
"matches the literature within the tolerance the calibration
case admits." Phase B must operationalize.

**Three candidates:**

- (a) **Per-derivation epsilon.** Each of C1-C5 names its own
  tolerance (some are 5%; some require 1 part in 10⁶).
- (b) **Global epsilon by regime gap.** Tolerance scales with
  the regime-axis distance (e.g., quantum→classical jumps allow
  5%; classical→cosmological allow 10%).
- (c) **Categorical tolerance.** Match within whatever the
  composing bridge's confidence-tier admits (`'established'`
  bridges → 1%; `'speculative'` → 10%).

**Recommendation:** (a) for Phase B (matches the empirical-claims
discipline from the v0.7 sprint — every claim grep-verifiable).

## Q3 — Does composition commute with the existing flux rules?

**Context.** v0.7 ships three flux rules
(`'lbe-coordinate' | 'causality' | 'regime-consistency'` after
P5). If a composite `B_B ∘ B_A` is added as a derived `BridgeCell`
to a `UniversalTensor`, do the flux rules fire on the composite,
on the constituents, or both?

**Cases to consider:**

- **Causality.** If `B_A` is forward (quantum→classical) and
  `B_B` is forward (classical→cosmological), the composite is
  forward. But if `B_B ∘ B_A: quantum → quantum` (round-trip
  through classical) and `B_A`'s reverse fires a causality
  warning, does the composite inherit that warning?
- **Regime consistency.** If `B_A` is tagged with a quantum
  regime and `B_B` is tagged with a classical regime, the
  composite spans both. The current rule only checks
  single-cell attachment; composite cells need
  multi-regime semantics.

**Phase B must extend `regime-rule-install.ts` (or write a new
rule body) to handle composite cells.**

## Q4 — Identity morphism for the categorical layer?

**Context.** Section 3 of Part-IX-Composition.md mentions
`id_R: R → R`. Phase A leaves it unspecified.

**Three candidates:**

- (a) **A trivial passthrough bridge** with `source === target`
  and `equation === 'I'`. **Cost:** the v0.7 `addCell` Rule 2
  REJECTS bridges where source === target. Either Rule 2 is
  patched (Phase B work) or `id_R` lives outside the catalog.
- (b) **An identity-marker (`isIdentity?: true` on `BridgeCell`).**
  **Cost:** new optional field on P3's surface.
- (c) **No identity in v0.9.** Compose only handles non-identity
  morphisms; associativity tests skip the identity edge cases.

**Recommendation:** (c) for v0.9α; reconsider for v1.0.

## Q5 — How is "no clear yes-or-no" detected and escalated at v1.0?

**Context.** P6 Decision (success/failure criterion in
Part-IX-Composition.md §6) says the track FAILS if v1.0 ends
without a clear yes-or-no. Operationalize.

**Detection signal:** Phase C's "stress tests" Phase D's
"hypothesis generation" produce ≥1 RED-tier result (clear
failure) OR ≥1 GREEN-tier result (clear pass). A YELLOW-tier
("ambiguous, needs more data") is the failure mode.

**Escalation:** v1.0 ships a research-track findings doc
(`docs/architecture/v1.0-composition-findings.md`). If at v1.0
RC time the doc has ≥2 unresolved YELLOW findings, the track
is escalated to v1.1 with a re-scoped definition (NOT silently
deferred).

**Phase B should not block on this — it's a v1.0 process
question.**
