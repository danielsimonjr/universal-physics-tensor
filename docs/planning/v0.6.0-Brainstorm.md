## Carry-forward from v0.5.1

### BR-2 — `christoffelFn` flat-array return shape (breaking)

The v0.5.0 Christoffel closure (`schwarzschildChristoffelFn`,
`computeChristoffelTensor`, etc.) returns a nested
`number[4][4][4]` array. Every per-step RK4 / GL4 call in the geodesic
integrator allocates and walks this nested structure. Profiling during
v0.5.1's bench-harness discussion (deferred to v0.5.2 — see Phase 7
Tasks 27-29 in `v0.5.1-Implementation-Plan.md`) suggested a 2–3× speedup
is plausible if the return shape becomes a single `Float64Array(64)` with
explicit row-major strides.

- **Why deferred from v0.5.1**: breaking change — every fixture and
  validator that consumes `christoffelFn` would need a coordinated
  migration. v0.5.1 is a hygiene patch, not a minor-bump-worthy
  surface change.
- **Migration plan for v0.6.0**:
  1. Add `christoffelFnFlat()` variant returning `Float64Array(N³)`.
  2. Provide one-minor `christoffelFnFlatToNested(fn)` adapter shim so
     legacy consumers keep working.
  3. Migrate `computeChristoffelTensor` internals to the flat path.
  4. Re-bench RK4 + GL4 on Mercury 1000-step segment — gate at ≥30%
     speedup before removing the nested shim.
  5. Deprecate the nested return in v0.6.0 docs; remove in v0.7.0.

## Future-curvature triggers (PD-6)

v0.5.0 shipped four parallel curvature composite-AST instances
(Riemann, Ricci, Einstein, Bianchi residual). v0.5.1's PD-6 doc note
(`docs/architecture/COMPONENTS.md` — "Curvature layer pattern") pins
the explicit extraction trigger: the FIFTH curvature primitive triggers
extraction into a `CurvatureCompositeNode<K, S>` factory.

Candidate fifth instances (one of these arriving signals "extract now"):

- **Weyl tensor `C^ρ_{σμν}`** — trace-free part of Riemann. Standard
  vacuum-test object; commonly needed alongside Ricci for de Sitter /
  FLRW classification.
- **Kretschmann scalar `K = R_{ρσμν} R^{ρσμν}`** — full-trace scalar
  curvature invariant. Black-hole horizon-piercing diagnostic.
- **Bianchi-2nd-form `∇_λ ∇_μ R_{...}`** — second-derivative curvature
  object. Pure ∇-cascade, but introduces a new metric-pair traversal
  pattern.
- **Riemann–Cartan torsion piece `T^ρ_{μν}` + contracted torsion
  `T_μ = T^λ_{λμ}`** — departure from Levi-Civita (non-symmetric
  connection). Same composite-AST pattern, different physics.

Extract on the FIRST of these to land. Until then, the explicit per-kind
arms in `lowering.ts` remain the right structure — premature
abstraction risk dominates marginal LOC savings while the curvature
surface has exactly four consumers.

## Deferred performance from v0.5.1

### PO-2 — Grid `pderiv` optimization (deferred)

`src/numerical/pderiv.ts` `pderivGrid` walks N⁴ entries per Riemann
sample with no caching. v0.5.1 documented this as a known cost
(`docs/architecture/benchmarks.md`) without optimizing — the grid path
isn't hot today.

**Trigger**: grid-field curvature lowering enters the perf path
(e.g., Mercury N-orbit GL4 integration consumes grid Riemann instead
of closed-form Schwarzschild). At that point: memoize per-coordinate
samples, batch FD evaluations across multiple Riemann components, or
introduce a `christoffelBatchAt(x, h)` primitive that emits all 64 Γ
components in a single FD pass.

### PO-3 — 4th-order FD memoization (deferred)

The v0.5.1 PD-7 migration moved the curvature-lowering helpers onto
the shared `pderivNumericalFn(..., {order: 4})` path. Each Riemann
component requires ~1024 effective Christoffel evaluations
(4-axis 4th-order stencil × 4 Christoffel components per axis ×
the inner Γ evaluations). On Schwarzschild's analytic
`schwarzschildChristoffelFn` this is fine; on a grid-field Γ it would
dominate the integration loop.

**Trigger**: grid-field Riemann arrives. Memoize Γ(x, x+h, x-h, ...)
evaluations across the 4-component sweep.

## Other v0.6.0 candidates

### Unconditional 2nd→4th-order FD upgrade in `pderiv.ts`

v0.5.1 added an opt-in `order: 2 | 4` parameter to `pderivNumericalFn`
(default 2nd, for backwards-compat). The curvature-lowering helpers
migrated to `{order: 4}` in v0.5.1; the rest of the codebase still
defaults to 2nd.

**Trigger**: once enough consumers have opted-in via the `order`
parameter and we have empirical evidence that the precision improvement
outweighs the truncation/round-off rebalance, flip the default to 4 in
v0.6.0. This is a semantically-breaking (precision-affecting) default
change → minor bump.

### NEW-3 — minor JSDoc / type-export polish (carry-forward from v0.5.1)

`v0.5.1-audit.md` flagged a handful of small public-API JSDoc nits
that v0.5.1 deliberately deferred as "below the patch-pass bar":

- `evaluateBE37CovariantEikonalNumerical` return-shape JSDoc could
  pin the `affineLength` field semantics more precisely.
- `findPerihelion` could document the bisection-tolerance argument's
  default policy.
- A handful of `@public` exports lack `@example` blocks.

Roll these into a one-shot "v0.6.0 polish pass" alongside the BR-2
breaking change.

## v0.5.1 Empirical Findings (carry-forward)

### PC-1 hypothesis was REFUTED

v0.5.1 Phase 1 (Tasks 0-4) was designed around the audit hypothesis
that **BE-37 covariant-eikonal Shapiro residual ~1.76e-4 (v0.5.0)
was dominated by truncated constants** (`c = 2.998e8` instead of the
exact-SI 299792458). The constants migration achieved its hygiene
goal but the headline physics number did NOT improve:

- **v0.5.0 baseline**: BE-37 Shapiro relErr = 1.76e-4.
- **Post-Task-1** (BE-37 module migrated to canonical `C_SI/G_SI`):
  relErr = 2.51e-4 (slight INCREASE — within step-count noise band,
  not a regression, but no improvement either).
- **Post-Task-4** (fixture + 3 downstream consumers migrated):
  relErr = 2.51e-4 (identical to post-Task-1).

The constants migration is therefore NOT the load-bearing fix for
PC-1. The residual floor at ~2.5e-4 is **integrator-driven**, not
constants-driven. Candidate sources to investigate in v0.5.2 or
v0.6.0:

1. **GL4 step count** in `evaluateBE37CovariantEikonalNumerical`'s
   internal integration — currently defaulted; may need higher step
   count for Earth-Mars geometry.
2. **Null-IC reconstruction** — the initial null vector is built from
   the metric at the start point; numerical inconsistency at the
   12th-13th digit could compound across the integration.
3. **Affine-parameter coverage** — the eikonal integrator's affine
   range may not match the closed-form Shapiro-delay endpoint
   precisely.

**File this as "PC-1.5 — Shapiro residual floor investigation"** for
v0.5.2 or v0.6.0. The empirical signature is: constants are NOT
the dominant contributor; instrumentation should target the
GL4-step-count vs null-IC-reconstruction axis next.
