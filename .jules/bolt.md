## 2024-06-30 - Metric Closure Evaluation Hoisting in GL4 Updates
**Learning:** In the GL4 integrator stage and momentum updates (`updateFromStages` and `updateMomentumFromStages`), evaluating metric closures (like `gInverseFn` and `dgInverseFn`) inside the coordinate iteration loop (`mu`) resulted in redundant evaluations. Because the inputs (`stageX[i]`) only depend on the stage `i` and not on the coordinate axis `mu`, computing them `dim` times instead of once per stage causes unnecessary overhead, especially for expensive metric closure functions.
**Action:** Always hoist metric closure evaluations out of coordinate or nested iteration loops when their inputs are invariant across those inner loops to minimize redundant computations.

## 2024-05-24 - GL4 Stage Solver Memory Optimization
**Learning:** The nested loops in the GL4 stage solver (`solveGL4Stage` in `src/numerical/gl4-integrator.ts`) were recalculating identical quantities and doing redundant nested iterations inside the `i` loop, which executes twice per Picard iteration. By pre-allocating state buffers, reducing calls to metric inverse and derivative to exactly twice per Picard iteration, and unrolling/hoisting the intermediate stages (dx and dp terms) out of the `i` loop, we can make the computation substantially faster (measured a 5x speedup in the core routine logic with isolated testing).
**Action:** Always identify redundant evaluations and computations happening inside hot loops (like RK4/GL4 integrators or Picard solver inner loops) and precompute/hoist them. Pre-allocating and re-using `Float64Array` buffers avoids allocation pressure and GC pauses inside hot loops.
## 2024-05-18 - TypedArray to Array Conversion Overhead
**Learning:** In V8 (Node.js), converting a TypedArray (like `Float64Array`) to a standard Array using `Array.from()` carries massive allocation overhead. This can significantly degrade performance when used inside tight numerical integration loops (like RK4 or GL4 integrators).
**Action:** Always prefer manual `for` loops to populate standard Arrays from TypedArrays in performance-critical sections.

## 2024-07-03 - Array.from Overhead in Nested Allocations
**Learning:** V8's `Array.from()` carries significant allocation overhead not just for TypedArray conversions (as noted previously), but also when used to initialize nested multi-dimensional native Arrays (e.g., `Array.from({length}, () => ...)`). In numerical tensor assembly pipelines (like `connection-lowering-helpers.ts` or `lowering.ts`), this creates unnecessary allocation pressure compared to manual explicit loops `for (let i=0; i<N; i++) out[i] = ...`.
**Action:** Always pre-allocate arrays natively with `new Array(size)` and populate them using manual `for` loops in tensor assembly and numerical code.

## 2024-07-11 - flattenNA Recursion and Iterator Overhead
**Learning:** V8/Node.js incurs noticeable overhead for iterator protocol `for...of` loops, particularly when combined with deep recursion (e.g. flattening physics tensors). Replacing the recursive `walk` step in `flattenNA` with an explicit stack and `for (let i = len - 1; i >= 0; i--)` traversal avoids function call depth limits and iterator allocations, while adding explicit pre-allocated `new Array(len)` fast paths for common 1D and 2D physics shapes delivers up to ~1.7x performance improvement across tensor assembly workloads.
**Action:** When walking or flattening heavily nested structures in numerical backends, prefer explicit iterative stacks over deep recursion, and replace `for...of` loops over raw arrays with standard `for` loop traversal.
## 2026-07-13 - Algebraic Factoring of Tensor Loops in Integrator
**Learning:** In deep nested loops for tensor contractions (e.g. `updateMomentumFromStages` calculating `dg * P * P`), straightforward implementation often repeats multiplications of outer loop terms. Algebraically refactoring the sum by factoring out invariant array accesses (`stageP[i][nu]`) from the innermost loop reduces the number of multiplications dramatically (e.g., from ~64 to ~20 per outer loop execution).
**Action:** Always algebraically expand and re-factor multi-dimensional tensor contractions in performance-critical inner loops to minimize total arithmetic operations, moving partial sums out of the innermost loops.
## 2026-08-25 - Loop Unrolling for Constant Stage Counts in Integrators
**Learning:** In the inner loops of fixed-stage numerical integrators (like the 2-stage GL4 method), explicitly unrolling the stage loop (e.g., `i=0, 1`) eliminates intermediate array allocations (e.g., `const gInvs = [gInv0, gInv1]`) and reduces loop control overhead. Furthermore, when accessing data that depends only on indices invariant across stages (like `mu` and `nu`), unrolling allows sharing the single index computation (e.g., `idx = mu_dim + nu`) across all stage iterations, improving CPU data locality and reducing total arithmetic operations.
**Action:** When working with numerical integration stages or fixed-size tensor contractions, manually unroll small loops (e.g., < 4 stages) and hoist shared multi-dimensional array index calculations out of the unrolled evaluation blocks.
